# ADR-0007: 共通予約と種別詳細を分割する

## 状態

採用済み（2026-08-24）

## 背景

通常予約と貸切予約は、予約番号、店舗、予約者情報、基本状態、取消、来店確認、監査、席や時間帯との競合などを共有する。一方、通常予約には1名から12名、標準利用時間、自動席配置などのルールがあり、貸切予約にはイベント時間、準備・片付け時間、貸切対象範囲、作成権限などの異なるルールがある。

ドメインモデルでは共通の予約を集約ルートとし、通常予約と貸切予約の詳細を分けることを確定している。DBでは、共通情報を重複させず、種別固有の列を大量のNULLとして抱えず、さらに1つの予約が必ず正しい種類の詳細を1つだけ持つ構造が必要になる。

## 判断対象

- 共通情報と種別固有情報をどのテーブルへ保存するか。
- 予約と詳細の1対1関係をどのキーで表すか。
- 詳細なし、種別不一致、両方の詳細が存在する状態をDBで拒否するか。
- 親と詳細を一時的に別々に登録する必要があるトランザクションで、いつ整合性を検査するか。

## 検討した選択肢

### 1. すべての列を1つの予約テーブルへ置く

- 詳細表示でJOINが不要になり、初期の実装は単純になる。
- 通常予約では貸切用の列、貸切予約では通常予約用の列がNULLになる。
- 種別ごとの必須列を保証するCHECK制約が複雑になり、将来種別が増えるほど保守しにくい。
- 関係しない列を誤って設定する不正状態を防ぐ条件も増える。

### 2. 通常予約と貸切予約を完全に独立したテーブルへ置く

- 種別ごとの列と制約は分かりやすい。
- 予約番号、連絡先、状態、取消情報などが重複し、共通変更を両方へ反映する必要がある。
- 当日一覧、予約番号検索、席競合、監査など、全予約を扱う処理で常に2テーブルを統合する必要がある。
- 同じ意味の状態遷移や制約に差異が生まれやすい。

### 3. 共通の親と2つの詳細に分け、整合性をアプリケーションだけで守る

- 共通情報の重複と種別固有のNULL列を避けられる。
- ORMからの通常操作では正しい組み合わせを作成できる。
- 不具合、管理スクリプト、直接SQLなどにより、詳細なし、種別不一致、両方の詳細という不正状態をDBが受け入れてしまう。

### 4. 共通の親と2つの詳細に分け、遅延制約トリガーでも守る

- 共通情報と種別固有情報を分離しながら、コミット済みデータが必ず正しい組み合わせになることをDBでも保証できる。
- 親を先に、詳細を後に登録する同一トランザクション内の一時的な未完成状態は許容できる。
- PostgreSQL固有の制約トリガー、マイグレーション、統合テストが必要になり、アプリケーション検証だけの方式より実装量が増える。

## 採用した案

- `reservations` を共通の親テーブルとする。
- `regular_reservation_details` を通常予約の詳細テーブル、`exclusive_reservation_details` を貸切予約の詳細テーブルとする。
- 各詳細の `reservation_id` を主キー兼 `reservations.id` への外部キーとし、詳細に独立したIDを設けない。
- 予約本体と詳細は同じトランザクションで作成し、一部でも失敗した場合は全体をロールバックする。
- `DEFERRABLE INITIALLY DEFERRED` なPostgreSQL制約トリガーにより、コミット時点で予約種別に対応する詳細が1件だけ存在することを検査する。
- 通常予約では通常詳細1件と貸切詳細0件、貸切予約では通常詳細0件と貸切詳細1件を要求する。
- 予約本体および両詳細テーブルの関連する作成・変更・削除をトリガーの検査対象とし、詳細だけを削除して親を残す操作も拒否する。
- 詳細を独立したAPIリソースとして作成、付け替え、削除させない。
- 予約種別の具体値、共通列、詳細列、削除動作は後続のDB設計項目で確定する。

## 採用理由

通常予約と貸切予約は同じ予約一覧、状態遷移、来店確認、取消、競合判定へ参加するため、共通の親を持つ構造が業務モデルに合う。種別固有の詳細を分ければ、多数のNULL列と複雑な条件付き必須制約も避けられる。

共有主キーは1予約につき同種の詳細を最大1件に制限し、詳細が親と別の識別子を持つ必要もなくす。ただし、外部キーと共有主キーだけでは親に詳細がない状態や両方の詳細がある状態を防げないため、トランザクション終了時の制約トリガーを併用する。

遅延検査なら、親を登録した直後に詳細がまだ存在しない一時状態を許しながら、コミットされたデータには完全な整合性を要求できる。予約、詳細、資格情報、席配置をまとめて作成する既存のトランザクション方針とも一致する。

## 実用性評価

この方式はMVPと本番運用の両方に利用できる。共通一覧や予約番号検索では親テーブルを中心に扱い、種別固有の画面や処理だけが対応する詳細をJOINすればよい。予約作成時の追加JOINとトリガー検査は、単一店舗40席規模では問題になりにくい。

一方、制約トリガーはSQLAlchemyのモデル定義だけでは表現できないため、Alembicマイグレーションへ明示的なSQLとして記述し、PostgreSQL上で検証する必要がある。将来3種類目の予約を追加する場合は、詳細テーブルだけでなく制約関数も同時に更新しなければならない。

## デメリット

- 種別固有情報を取得するときにJOINが必要になる。
- アプリケーション側の検証に加えて、PostgreSQL固有の制約関数とトリガーを保守する必要がある。
- ORMの自動生成だけではマイグレーションを完成できず、手書きSQLと巻き戻し処理が必要になる。
- エラーがコミット時まで遅延するため、トランザクション境界で例外を適切に処理する必要がある。
- 予約種別を追加または廃止するときは、親の種別制約、詳細テーブル、制約関数、テストを同じ変更単位で更新する必要がある。

## 将来見直す条件

- 予約種別を追加または統合する。
- 貸切が確定予約とは異なる問い合わせ、見積り、契約のライフサイクルを持つ。
- 詳細テーブルのJOINが主要クエリの性能要件を満たさないことを実測で確認する。
- PostgreSQL以外のDBMSへ移行し、遅延制約トリガーを利用できなくなる。
- 予約作成を単一トランザクションで完結できない分散構成へ変更する。
