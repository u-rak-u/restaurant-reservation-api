# ADR-0025: 13名以上の予約なし利用は共通操作IDを監査記録へ保存する

## 状態

採用済み（2026-08-28）

## 背景

13名以上の予約なし来店は、1件の上限12名を守るため複数の予約なし利用へ分割し、全員分を収容できる場合だけ同じトランザクションで作成する。分割後は人数変更、席移動、利用開始・終了を個別に行い、近接席も保証しないため、利用系列同士を恒久的な団体として扱わない。

一方、一括受付では複数の利用系列と席配置計画を作り、既存予約を複数再配置する可能性がある。後から部分適用や配置計算の問題を調査するとき、どの変更が同じ受付操作によるものか分からなければ、時刻と操作者だけで推測することになる。

同一リクエストの再送を検出する冪等性キーも後続設計で必要になるが、これは成立した変更をまとめる操作識別子とは目的と信頼境界が異なる。

## 判断対象

- 13名以上の一括受付を追跡する識別子を保存するか。
- 保存する場合、利用系列・利用本体と監査記録のどちらへ置くか。
- 席配置世代の原因操作識別子と共通化するか。
- 一括変更、保持期限および冪等性へ流用するか。

## 検討した選択肢

### 1. 一括操作識別子を保存しない

- 追加の列と値生成が不要になる。
- 同じトランザクションなら部分適用は防げるが、後日の調査で複数の利用・再配置を1回の操作として検索できない。
- 近い時刻と同じ操作者の別操作を誤って同一視する可能性がある。

### 2. 利用系列または利用本体へ一括受付IDを保存する

- 分割した利用を通常の業務クエリから直接検索しやすい。
- 個別管理するはずの利用に団体関係が残り、一括変更、一括終了、保持期限共有などへ誤用されやすい。
- 席配置だけが変更された既存予約を同じ操作へ含めるには、結局別の相関値も必要になる。

### 3. 共通操作IDを監査記録と席配置世代へ保存する

- 業務上の団体を作らず、成立した1回の操作に含まれる変更だけを追跡できる。
- 監査記録または席配置世代との結合が必要になり、利用系列だけを検索しても一括受付元は分からない。
- 監査テーブルと席配置世代で同じ識別子の意味を揃える必要がある。

### 4. 一括受付専用の団体テーブルを作る

- 一括受付の状態や所属利用を強い外部キーで管理でき、将来の一括操作へ拡張しやすい。
- MVPでは行わない一括変更・一括終了まで業務モデルへ持ち込み、保持期限と例外訂正も複数系列へ伝播させる複雑さが増える。

## 採用した案

共通操作IDを監査記録と席配置世代へ保存する。

- 13名以上の一括受付で全件を収容できることを確認した後、同じトランザクション内でPostgreSQLの `uuidv7()` を1回だけ評価し、内部の `operation_id` を生成する。
- クライアントが一括受付の `operation_id` を指定するAPIにはせず、生成した値を公開資格情報として使用しない。
- 分割した全件の受付監査記録と、その受付によって作成または変更するすべての席配置世代へ同じ値を保存する。自動再配置した既存予約の新世代も含める。
- 分割した各件には別の利用系列を作り、`walk_in_visit_series` または `walk_in_visits` へ一括受付IDを保存しない。
- `operation_id` は調査上の相関値に限定し、認証・認可、一括変更・一括終了、状態遷移、統計上の団体化または保持・削除単位に使用しない。
- 共通IDを持つ系列でも保持期限を個別に判定し、一方の訂正や削除保留を他方へ伝播させない。監査記録と席配置は各対象の保持方針に従って削除できる。
- `operation_id` と、クライアントの再送を識別する冪等性キーを別の列・意味として扱う。成功済みリクエストの再送で元の結果を返す関係はDB-45で確定する。
- 監査記録の具体的な列、必要なら設ける監査用操作ヘッダーおよび同一店舗制約はDB-40、席配置世代の原因操作列はDB-27で確定する。

## 採用理由

利用系列へ団体関係を持たせなければ、受付後の業務と保持期限を各利用で独立させたまま、監査時だけ同じ操作に含まれた変更を復元できる。席配置世代にも同じ値を渡すことで、新しく作成した利用だけでなく、その受付を成立させるため移動した既存予約まで追跡できる。

冪等性キーはクライアントから送られ、同じ要求かを判断する入力である。`operation_id` はサーバーが成立した変更へ付ける出力側の識別子である。両者を分ければ、内部識別子を知るだけで再送扱いにしたり、異なる要求を同一操作として扱ったりする誤用を防げる。

## 実用性評価

UUIDv7を1回生成して複数行へコピーする処理は軽く、40席・最大6台のテーブル連結を前提とするMVPで性能問題になる可能性は低い。同じトランザクションへ監査記録と席配置世代を含めるため、利用だけ作成されて相関情報が欠ける状態も防げる。

共通 `operation_id` があれば、スタッフ問い合わせや不具合調査で「どの分割利用と既存予約が1回の受付により変更されたか」を検索できる。通常画面に団体操作を追加しないため、個別終了を誤って全件へ適用する危険も増やさない。

一方、監査記録の一部が保持期限で削除された後は、元の一括受付全体を完全には復元できない。これは複数系列を恒久的に結び付けない方針による意図した制約であり、共通IDだけを理由に削除を延長しない。本番相当の監査整合性は、DB-27とDB-40で列・外部キー・同一店舗制約を確定し、同時実行およびロールバック試験を通過してから保証する。

## デメリット

- 利用系列だけから一括受付を検索できず、監査記録との結合が必要になる。
- 監査記録と席配置世代へ同じ値を確実に渡すアプリケーショントランザクションが必要になる。
- 専用の団体テーブルを持たないため、一括変更や一括終了へそのまま拡張できない。
- 各系列の保持期限が異なると、時間の経過後に一括操作の一部だけが残る場合がある。
- 冪等性キーとの名称・用途の違いをAPI設計、コードおよび運用文書で維持する必要がある。

## 将来見直す条件

- 分割した利用へ一括人数変更、一括席移動または一括終了が必要になった。
- 近接席、同一会計、注文または顧客プロフィールを団体単位で管理する必要が生じた。
- 法令または監査要件により、各利用系列の保持期限を越えて一括受付全体を復元する必要が生じた。
- 汎用の監査操作ヘッダーを導入し、すべての業務操作を強い外部キーで管理する方が単純になった。
