# ADR-0011: 貸切予約のイベント時間・準備片付け時間・参加人数

## 状態

採用済み（2026-08-24）

## 背景

貸切予約は通常予約の90分固定と12名上限を使用せず、店舗と代表者が合意したイベント時間と参加予定人数を持つ。イベントの前後には準備と片付けが必要であり、その全期間にわたって対象範囲への別予約と予約なし利用を防がなければならない。

準備・片付け時間には店舗初期値がある一方、貸切ごとに変更できる。既存予約の占有期間が設定変更によって意図せず変わらないよう、初期値と適用済みの値を区別する必要がある。また、貸切の来店確認は代表者と団体を確認するものであり、参加者全員の出席管理ではない。

## 判断対象

- イベント時間を通常予約と同じ90分または10分単位に制限するか。
- 準備・片付け時間の店舗初期値と、貸切へ適用した値をどこへ保存するか。
- イベント時間とは別に予約停止開始・終了日時を保存するか。
- 参加人数へ固定上限を設けるか、選択した貸切範囲の収容人数から判定するか。
- 参加予定人数と実参加人数を両方保存するか。

## 検討した選択肢

### 1. イベント開始・終了と準備・片付け時間を保存し、予約停止期間を算出する

- 顧客と合意したイベント本体と、店舗運用上必要な前後時間を区別できる。
- 店舗初期値を後から変更しても、貸切へ適用済みの時間を維持できる。
- 競合処理のたびに予約停止期間を算出する必要がある。

### 2. 予約停止開始・終了日時だけを保存する

- 競合検索では保存済みの両端をそのまま使用できる。
- イベント本体と準備・片付けの境界が失われ、営業時間の検証、顧客への案内、設定変更の監査が難しくなる。

### 3. イベント時間、前後時間、予約停止開始・終了をすべて保存する

- 表示と競合検索のどちらも保存値だけで行える。
- 同じ事実を重複保存するため、いずれかだけを更新した不整合を防ぐ追加制約が必要になる。

### 4. 参加人数へ通常予約と同じ固定上限を設ける

- 単一列のCHECK制約だけで上限を保証できる。
- 店舗全体、エリア、テーブルによって異なる貸切収容人数を表せず、貸切を通常予約と分ける利点が失われる。

## 採用した案

- `exclusive_reservation_details` に会社・団体名、参加予定人数、イベント開始・終了日時、適用済みの準備・片付け時間を置く。
- 会社・団体名は運用中必須の最大100文字とし、終了後に保持期限に従って削除できるようDB列はNULLを許可する。
- 参加予定人数は正の `integer` とし、通常予約の12名上限を適用しない。貸切範囲の収容人数以下であることを範囲確定と同じトランザクションで検証する。
- イベント開始・終了はタイムゾーン付きの分単位とする。秒以下を拒否するが、通常予約の10分単位は適用しない。
- イベント終了が開始より後であることをCHECK制約で保証し、イベント本体が1つの連続した営業時間帯へ収まることを横断的に検証する。
- 店舗に準備・片付け時間の初期値を保存し、初期値はそれぞれ30分とする。店舗初期値と貸切へ適用した値は0分以上180分以下の10分単位とする。
- 貸切作成時に店舗初期値または管理責任者以上が指定した値を詳細へコピーし、既存の貸切を店舗初期値へ追従させない。
- 予約停止期間はイベント時間と適用済みの前後時間から算出し、貸切詳細へ重複保存しない。
- 準備・片付けは営業時間外へ延びてもよいが、競合判定には予約停止期間全体を使用する。
- 代表者の来店確認を参加者全員の出席確認とせず、MVPでは実参加人数列を持たない。
- 早期完了によって確定済みの予約停止期間を短縮しない。

## 採用理由

イベント本体と準備・片付けを分けることで、顧客へ案内した時間、営業時間の成立条件、店舗資源の占有期間をそれぞれ明確に扱える。適用済みの前後時間を予約へ保存するため、店舗初期値の変更によって既存予約の競合結果が変わらない。

貸切は管理責任者以上が代表者と調整して登録するため、通常予約の公開空席枠と同じ10分単位へ限定する必要はない。分単位に制限すれば18時15分開始などを扱いつつ、秒単位の入力ミスを排除できる。

参加人数の業務上の上限は整数型の上限ではなく、選択した貸切範囲の収容人数である。固定値を詳細テーブルへ持たせず範囲との整合を検証することで、店舗またはレイアウトの変更へ対応できる。

## 実用性評価

この構成は、管理責任者が相談済みの貸切を登録し、営業時間と準備・片付けを含めて通常予約および予約なし利用との競合を防ぐ単一店舗MVPに利用できる。店舗初期値を詳細へコピーするため、設定変更後も過去と将来の予約停止期間を再現できる。

一方、参加人数上限と競合は貸切範囲、席配置、別集約を参照するため、このテーブルのCHECK制約だけでは保証できない。DB-10で対象範囲との関係を定め、後続の共通ロック順序とPostgreSQL統合テストまで完了して初めて、同時受付を含む実運用へ耐える。

MVPでは実参加人数を記録しないため、参加率分析、請求人数の確定、参加者単位の受付には使用できない。貸切予約APIの目的は席資源と予約の管理であり、代表者受付だけなら成立するが、会計またはイベント運営との連携が必要になれば拡張が必要になる。

## デメリット

- 予約停止期間を使用する処理で、イベント時間と準備・片付け時間から両端を算出する必要がある。
- 参加人数と貸切範囲の収容人数、イベントと営業時間、予約停止期間と他の占有の整合には横断的な検証とロックが必要になる。
- 10分単位の通常予約と分単位の貸切が混在するため、一覧表示と競合処理を通常予約のスロット番号だけで実装できない。
- 店舗初期値と適用済み時間を別々に保存するため、貸切作成処理で明示的なコピーが必要になる。
- 実参加人数を使用した分析や請求はできない。

## 将来見直す条件

- 貸切の問い合わせ、仮押さえ、見積り、契約または請求を管理する。
- 最低利用時間、最大利用時間、最低人数または料金プランをシステムで強制する。
- 参加者単位の受付、正確な実参加人数、途中入退場または会計人数が必要になる。
- 競合検索の実測により、予約停止期間をPostgreSQL範囲型または生成可能な検索用データとして保持する方が有利と確認される。
- 複数店舗で店舗初期値以外の貸切テンプレートまたは会場別設定が必要になる。
