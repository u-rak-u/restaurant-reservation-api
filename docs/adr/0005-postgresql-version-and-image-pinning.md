# ADR-0005: PostgreSQL 18とDockerイメージの固定方針

## 状態

採用済み（2026-08-24）

## 背景

DBMSとしてPostgreSQLを採用したため、テーブル設計とマイグレーションの前提になるメジャーバージョンを確定する必要がある。開発開始時のDocker Composeは `postgres:18` を使用していたが、このタグは新しい18系イメージを取得した時点でマイナーバージョンやベースイメージの内容が変わる可能性があり、複数環境の再現性が十分ではない。

一方、イメージをダイジェストへ完全固定すると、同一内容を再現できる代わりに、OSとPostgreSQLのセキュリティ修正を取り込むたびにダイジェストを更新する運用が必要になる。ローカル開発段階とCI・本番段階に分けて固定粒度を決める。

## 判断対象

- PostgreSQL 18と17のどちらを採用するか。
- 開発用Dockerイメージを、メジャータグ、マイナー・ベースOS付きタグ、ダイジェストのどこまで固定するか。

## 検討した選択肢

### 1. PostgreSQL 17

- トランザクション、行ロック、範囲型、GiST、排他制約など、予約競合を扱う中核機能を使用できる。
- PostgreSQL 18より運用実績が長く、配置先や拡張機能によっては対応範囲が広い可能性がある。
- PostgreSQL標準のUUID生成はUUIDv4であり、確定済みのUUIDv7を使用するにはアプリケーション生成などへ変更する必要がある。
- 公式サポート終了は2029年11月8日である。

### 2. PostgreSQL 18

- PostgreSQL 17の中核機能を使用できる。
- 組み込みの `uuidv7()` により、追加拡張や生成ライブラリなしで確定済みの主キー方針を実装できる。
- `WITHOUT OVERLAPS` と `PERIOD` による時間制約が追加され、単純な期間重複の表現に利用できる可能性がある。ただし、席の自動再配置全体をこの機能だけで保証できるとは扱わない。
- 公式サポート終了は2030年11月14日で、17より約1年長い。
- 公式Dockerイメージで起動、永続化、ヘルスチェック、TCP認証を検証済みである。

### 3. `postgres:18`によるメジャー固定

- PostgreSQL 19へ意図せず更新されることを防ぎながら、取得時点の最新18系へ追従できる。
- 開発者やCIがイメージを取得した時期によって、異なるマイナーバージョンまたはベースイメージを使用する可能性がある。

### 4. `postgres:18.4-trixie`によるマイナー・ベースOS系列固定

- PostgreSQLのマイナーバージョンとDebian系列を明示でき、変更をGit差分として管理できる。
- 同じタグがOS修正などで再公開される可能性があるため、イメージ内容の完全な固定ではない。
- 新しいPostgreSQLマイナーリリースを自動では取り込まないため、明示的な更新作業が必要になる。

### 5. SHA-256ダイジェスト固定

- イメージ内容を暗号学的識別子で指定し、取得時期にかかわらず同じ内容を再現できる。
- セキュリティ修正版も自動では取り込まれず、ダイジェスト更新、対象CPUアーキテクチャ、マルチプラットフォームイメージを管理する必要がある。
- CIと配置先が未確定の現在は、追加の運用負荷に対する利益が小さい。

## 採用した案

- PostgreSQL 18を正とする。
- 開発用Docker Composeでは `postgres:18.4-trixie` を使用する。
- `latest`、メジャーバージョンを省略したタグ、PostgreSQL 19以降へ自動追従する指定は使用しない。
- 新しい18系マイナーリリースの公開時は、リリースノートを確認し、Composeのタグ変更、コンテナ再作成、DB接続確認、関連テストを同じ変更単位で行う。
- CIと本番環境を構築するときは、タグに加えてSHA-256ダイジェストを固定するか再検討する。
- PostgreSQL 18公式イメージのデータ配置に合わせ、名前付きボリュームを `/var/lib/postgresql` へマウントする現在の構成を維持する。

## 採用理由

PostgreSQL 18は確定済みのUUIDv7主キーを標準機能で生成でき、現在のDocker環境でも動作確認済みである。17でも予約競合の中核要件は実装できるが、現時点で18から下げる具体的な運用上の利益がなく、UUID生成方法とDockerボリューム構成の見直しが発生する。

開発環境では、マイナーバージョンとベースOS系列まで固定すれば、意図しない大きな差異を避けながら更新作業をGitで確認できる。完全な再現性がより重要になるCI・本番環境ではダイジェスト固定を再検討し、現在は更新負荷を増やさない。

## 実用性評価

単一店舗MVPの機能と性能に対してPostgreSQL 18は十分であり、公式Dockerイメージを使うローカル開発も実用に耐える。`18.4-trixie`へ固定することで、新しい開発環境が意図せず異なるPostgreSQLマイナーまたはDebian系列を使う可能性を減らせる。

本番運用ではタグ固定だけではイメージ内容の完全な再現性を保証できない。配置先のPostgreSQL 18対応、バックアップと復元、マイナー更新の通知、脆弱性対応、ロールバック手順を追加し、必要に応じてダイジェスト固定を採用する。

## デメリット

- 新しい18系マイナーバージョンを手動で確認し、タグを更新する必要がある。
- タグだけではOS修正などによる同一タグの再公開を完全には固定できない。
- PostgreSQL 18に未対応の配置先や拡張機能を採用する場合は、バージョンまたは配置先を見直す必要がある。
- 将来のメジャーアップグレードでは、単なるイメージタグの変更ではなく、`pg_upgrade`またはダンプ・リストアと復旧手順の検証が必要になる。

## 将来見直す条件

- CIまたは本番環境を構築し、同一イメージ内容の再現性が必要になる。
- PostgreSQL 18の新しいマイナーバージョンが公開される。
- 配置先または必須拡張機能がPostgreSQL 18に対応しない。
- PostgreSQL 19以降へ移行するだけの機能、性能、サポート期間上の利益が確認できる。
- 使用中のDebian系列がサポート終了または公式イメージの提供対象外になる。
