# ADR-0029: 貸切の到着期限と明示的な資源解放

## 状態

採用済み（2026-09-01）

## 背景

貸切予約にも代表者の来店確認と無断キャンセル審査が必要だが、通常予約の開始15分後という自動席解放をそのまま適用すると、代表者以外の参加者が先に来ている場合や、店舗全体を使うイベント準備中の場合に大きな範囲を誤って解放する危険がある。一方、到着基準がなければ、代表者が現れない貸切の資源がいつまで確保され、誰が無断キャンセル審査を開始するかが定まらない。

貸切は管理責任者または管理者が代表者との合意後に登録するため、標準期限を持ちつつ、個別合意を予約単位で記録できる必要がある。期限到来、資源解放、正式な `no_show` 確定を分け、現場判断と後日審査の責任も区別する。

## 判断対象

- 貸切へ通常予約と同じ15分期限を適用するか、別の標準期限を持つか。
- 個別合意した到着期限を保存できるようにするか。
- 期限到来だけで貸切範囲を自動解放するか、権限者の明示操作を要求するか。
- 資源解放と `no_show` 確定を同時に行うか、後日審査へ分けるか。
- 解放時に元の予約停止期間を上書きするか、履歴を残して現在の占有だけを短縮するか。

## 検討した選択肢

### 1. 通常予約と同じ開始15分後に自動解放する

- 通常予約と同じ処理を再利用しやすい。
- 貸切の準備状況や参加者の到着を確認せず、店舗全体または広い範囲を誤って再販売する危険が大きい。

### 2. 到着期限を設けず、営業終了時だけ審査する

- 到着時刻に関する追加列と操作が不要になる。
- 代表者が現れない場合も予約停止終了まで資源を解放できず、現場の判断権限と監査経路が曖昧になる。

### 3. イベント開始30分後を標準期限とし、権限者が明示的に解放する

- 通常予約より長い確認時間を確保し、個別合意にも対応できる。
- 大きな範囲の解放前に現場状況を確認でき、操作主体を監査できる。
- 管理責任者または管理者が操作しない限り、期限後も範囲が確保されたままになる。

### 4. 期限到来と同時に `no_show` を確定する

- 処理回数は少ない。
- 現場での資源解放と、顧客へ影響する無断キャンセル確定を同じ即時判断にしてしまい、誤判定を後日確認できない。

## 採用した案

- `exclusive_reservation_details` に `arrival_deadline_at` と `arrival_timeout_processed_at` を保存する。
- 個別合意がなければ `arrival_deadline_at` をイベント開始30分後とする。管理責任者または管理者は、代表者との個別合意に基づく分単位の期限を予約ごとに設定できる。
- 到着期限はイベント開始より後、イベント終了以前とする。既定の30分後がイベント終了より後になる場合は、有効な個別期限を作成時に明示する。
- 期限ちょうどまでは来店確認と期限変更を許可し、期限経過後は元の貸切の来店確認、期限延長または復活を許可しない。期限変更でイベント終了を延長しない。
- 期限経過だけでは資源を自動解放せず、管理責任者または管理者が専用操作で解放する。解放完了までは元の予約停止期間を競合判定へ使用する。
- 専用操作では、元の予約停止終了と処理日時の早い方まで現在の占有を短縮する新しい席配置世代、`arrival_timeout_processed_at`、`open` の `no_show_review` および監査記録を同じトランザクションで保存する。処理が元の終了後になっても占有を延長しない。
- 解放直後も予約の基本状態は `confirmed` とし、管理責任者または管理者が後日 `no_show_review` を承認した場合だけ `no_show` と無断キャンセル電話照合を同じトランザクションで確定する。
- `arrival_timeout_processed_at` は、解放後の `confirmed`、審査承認後の `no_show`、または解放後の定義済み取消による `cancelled` と併存できる。`checked_in` と `completed` では処理日時を持たせない。
- 元のイベント時間、準備・片付け時間、予約停止期間および過去の席配置世代は変更せず、解放した事実を履歴として追跡できるようにする。
- 貸切を通常の営業終了時に行う無断キャンセル候補抽出から除外し、専用の資源解放と案件作成を開始経路とする。
- 未解決の `temporary_closure_response` または `arrival_issue` がある場合は専用解放を拒否し、臨時休業対応または来店確認問題を先に解消する。
- 貸切の `no_show_review` は専用解放だけから作成し、同一予約の未解決案件を最大1件とする。専用解放前に既存の未解決 `no_show_review` を検出した場合は暗黙に再利用せず、整合性警告として処理を拒否する。解放処理済み日時、対応案件および解放後の席配置が揃う同一操作の再送は成功済みとして同じ結果を返す。

## 採用理由

イベント開始30分後を標準にすれば、通常予約より大きい到着確認の余地を持ちながら、期限のない確保を避けられる。個別期限を保存するため、代表者と合意した時刻をイベント時間とは別に再現できる。

広い範囲を扱う貸切では、時計だけを根拠に自動解放するより、権限者が現場状況を確認して明示操作する方が誤解放の影響を抑えられる。一方、顧客への利用制限につながる `no_show` は後日審査へ分けることで、資源を営業へ戻す判断と顧客責任の確定を分離できる。

## 実用性評価

管理責任者または管理者が在席し、代表者の到着状況を確認できる単一店舗MVPでは運用可能である。期限、解放日時、案件、操作者を一体で記録するため、後日の問い合わせでも「いつ資源を解放し、誰が審査を開始したか」を確認できる。

期限後も明示操作までは資源を保持するため、担当者が操作を忘れると空いている席を再利用できない。スタッフ画面では期限超過を強く警告し、管理責任者または管理者へ専用操作を提示する必要がある。自動解放より安全側だが、運用監視を不要にはしない。

既定の期限がイベント終了を超える短時間イベントでは個別期限が必要になる。貸切予約は個別合意後に管理側が登録する前提のためMVPで扱えるが、公開セルフサービスへ拡張する場合は入力案内と検証方法を見直す必要がある。

## デメリット

- 貸切詳細へ2列、権限付きの専用解放操作、期限超過警告が追加で必要になる。
- 権限者が操作するまで期限後も対象範囲が予約停止となり、販売機会を失う可能性がある。
- 元の予約停止期間と現在の有効占有終了を分けて扱うため、競合判定と履歴表示が単一日時だけでは済まない。
- 短時間イベントでは標準30分をそのまま適用できず、個別期限の入力が必要になる。

## 将来見直す条件

- 貸切の受付担当、参加者到着、主催者代理など、代表者以外の受付成立条件を管理する。
- デポジット、キャンセル料、契約条件によって無断キャンセル判定を自動化する。
- 期限超過通知と権限者へのエスカレーションを導入し、自動解放の安全性を実測できる。
- 公開セルフサービスで貸切を受け付け、個別期限を店舗との合意なしに計算する必要が生じる。
- 複数店舗または大規模会場で、期限超過処理の監視と代行権限を中央運用へ移す。
