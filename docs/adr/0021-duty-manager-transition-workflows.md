# ADR-0021: 当日運用責任者の交代手続きを任命と分離して保存する

## 状態

採用済み（2026-08-27、同日更新）

## 背景

ADR-0020では、当日運用責任者を時間範囲の任命履歴として保存し、同じ店舗の同じ瞬間に有効な責任者を最大1名とする方針を決めた。残る判断は、管理者任命、後任承認を伴う引き継ぎ、管理者へ連絡できない場合の緊急就任を、どの列と関連で表すかである。

通常の引き継ぎは、前任者による依頼と後任者による承認の間に未成立期間がある。一方、緊急就任は業務継続のため事後確認を待たず有効にする必要がある。後日の確認で手続きが不適切と判断されても、既に行われた業務操作を一括して遡及無効にすることはできない。この違いを現在の認可、履歴確認、監査のすべてで説明できる構造が必要である。

## 判断対象

- 任命方法と前任・後任の関係を任命本体へ保存するか
- 引き継ぎ依頼中の状態と、後任承認による成立をどう表すか
- 引き継ぎ承認時に再認証を要求するか、依頼をいつ失効させるか
- 緊急就任理由と事後確認を任命本体へ置くか、別の従属行へ分けるか
- 次の営業日を解決できない場合も有限の事後確認期限をどう保証するか
- 事後確認で不適切と判断した場合に、過去の権限と操作をどう扱うか
- 専用の業務履歴と共通監査ログのどちらを現在状態の正とするか

## 検討した選択肢

### 1. すべての手続き列を `duty_manager_assignments` へ追加する

- 現在の任命と方法を1行で取得できる。
- 引き継ぎの依頼・承認・取消・期限切れと、緊急理由・確認結果が同じ行へ混在し、多数の条件付きNULL列と複雑なCHECK制約が必要になる。
- まだ成立していない引き継ぎ依頼を任命として置くと、権限を持たない候補者と有効な責任者を混同しやすい。

### 2. 共通監査ログだけへ手続きイベントを保存する

- 専用テーブルを増やさず、イベントの追記だけで履歴を残せる。
- 現在有効な依頼、前任・後任、未確認の緊急就任をJSONイベント列から復元することになり、外部キー、UNIQUE、CHECKによる整合性保証と業務検索が難しくなる。
- 監査ログの形式変更や欠損が、認可判定へ直接影響する。

### 3. 任命へ共通の成立情報を追加し、引き継ぎと緊急就任を従属テーブルへ分ける

- 任命本体を権限期間の正として維持しながら、依頼中の引き継ぎと緊急就任だけの項目を別の構造化された業務履歴にできる。
- 通常の現在責任者検索には従属テーブルの結合が不要で、手続き詳細が必要な画面だけ結合すればよい。
- テーブル数、外部キー、トランザクション検証、統合テストは増える。

### 4. 緊急就任確認を既存の例外案件へ追加する

- 提起と管理責任者による確認という共通の画面・状態遷移を再利用できる。
- 予約や予約なし利用の事実訂正と、権限昇格手続きの妥当性確認を同じ案件種別へ混在させる。緊急任命は確認前から権限を持つため、承認まで対象状態を変えない既存の例外審査とは意味が異なる。

## 採用した案

- `duty_manager_assignments` へ `appointment_method`、`created_by_staff_account_id`、`predecessor_assignment_id` を追加する。
- 任命方法は `admin_appointment`、`handoff`、`emergency_appointment` の3種類とする。
- 開始済みの交代では、前任任命の終了と後任任命の開始を同じDB時刻にし、後任任命から一意な前任任命を参照する。開始前取消による予定差し替えには前任関係を付けない。
- `duty_manager_handoff_requests` に、前任任命、依頼者、後任候補、依頼日時、15分後の期限、結果、解決者、解決日時、成立した後任任命を保存する。
- 引き継ぎ依頼中は後任候補へ権限を付与しない。後任候補が10分以内のパスワード再認証を満たして承認した場合だけ、前任任命の終了、後任任命の作成、依頼結果および監査記録を同じトランザクションで成立させる。
- 期限切れ、取消済み、または管理者任命や緊急就任など別の交代で無効になった依頼は承認しない。期限切れはDB時刻から即時に判定し、新しい依頼の作成前または定期処理で結果を確定できるため、認可を定期ジョブへ依存させない。
- `duty_manager_emergency_appointments` を緊急任命と1対1で作成し、空でない緊急理由、事後確認期限、確認結果、確認者、確認日時、確認理由を保存する。
- 緊急就任では、同じ店舗の有効かつパスワード設定済みのスタッフが直前10分以内に本人のパスワードで再認証し、自分自身を即時に任命する。既存任命があれば同じトランザクションで終了し、前任関係を残す。
- 事後確認期限を次の営業日の最後の閉店日時から2時間後とする。次の営業日を解決できない場合は緊急就任から72時間後へフォールバックし、期限の計算根拠と営業カレンダー設定警告を残す。就任者本人以外の同じ店舗の `manager` または `admin` が、`confirmed` または `unjustified` と確認理由を記録する。
- `unjustified` でも過去の任命と任命中の操作を遡って削除または無権限扱いにしない。任命中なら確認時点で終了し、問題のある業務操作は個別に調査・訂正する。
- 専用テーブルを業務状態と関係の正とする。共通監査ログには操作主体、日時、対象、理由、変更前後を追記するが、監査ログだけから現在の権限を復元しない。
- 保存済み終了日時への自然到達は追加の書込みを要求せず、終了日時を設定または短縮した操作を監査する。

## 採用理由

任命は「誰がいつ権限を持つか」、引き継ぎ依頼は「まだ権限を持たない後任候補が承認するまでの手続き」、緊急就任情報は「即時の権限付与を後から検証する手続き」であり、状態の意味が異なる。任命本体へ共通項目だけを置いて手続きごとの従属表を分ければ、有効な権限を単純な時間範囲検索で判定しながら、条件付きNULL列を抑えて外部キーと一意制約を適用できる。

後任者の再認証は、前任者が指定しただけ、または後任者の放置されたセッションだけで責任者権限が移ることを防ぐ。15分の依頼期限により、勤務状況が変わった後で古い依頼が成立する危険を抑えられる。

緊急就任を事後確認待ちにすると、責任者不在時に本来守るべき業務継続性を失う。一方で、後日の `unjustified` を遡及無効として扱うと、その時間に行われた席移動や例外提起などの結果まで不定になり、現在状態を安全に復元できない。任命の事実を残したまま、現在権限の終了と問題操作の個別訂正を行う方が一貫している。

事後確認期限を必須にしたまま「次の営業日」だけへ依存すると、無期限休業やカレンダー設定不備のときに緊急就任そのものが成立せず、最も業務継続が必要な状況で権限復旧を妨げる。72時間の固定フォールバックなら、通常は営業日に沿った期限を維持しつつ、解決不能時にも有限の確認期限を必ず保存できる。計算根拠を列で残すことで、通常期限と設定異常時の期限を画面・監査で区別できる。

## 実用性評価

40席の単一店舗では、任命と交代は通常1日数件以下であり、引き継ぎ依頼と緊急就任情報の追加結合が性能問題になる可能性は低い。現在責任者の認可判定は `duty_manager_assignments` だけで行えるため、日常的なAPIへ手続き履歴の結合負荷を加えない。

通常引き継ぎは前任者の依頼と後任者のパスワード入力の2操作になる。忙しい時間帯には1操作より負担があるが、権限移行を本人が認識し、盗難セッションによる昇格を抑える効果がある。15分を超えた場合は依頼を作り直せるため、業務停止にはならない。

緊急就任は理由入力と再認証だけで即時成立するため、管理者不在でも業務を継続できる。ただし、虚偽の理由、不要な就任、現場事情の誤認を技術だけで完全には防げない。本人以外による事後確認、期限超過警告、削除しない業務履歴、共通監査ログによって、濫用を抑止し後から検出する設計である。

事後確認期限を超えても自動失効させないため、管理責任者が確認しなければ未確認行が残る。スタッフ画面の常時警告と管理者向け件数表示を実装し、運用試験で確認漏れが続く場合は通知またはエスカレーションを追加する必要がある。

72時間フォールバックは営業シフトに一致する保証がなく、通常の確認期限より早すぎる場合も遅すぎる場合もある。これはカレンダー異常時に緊急就任を止めないための安全網であり、フォールバック使用中は営業カレンダー設定警告を消さず、設定修正後も保存済み期限を遡って変更しない。

## デメリット

- 任命、引き継ぎ依頼、緊急就任情報、共通監査ログを一括して扱うトランザクションと統合テストが必要になる。
- 前任・後任の時間一致や、任命方法に対応する従属行の存在は複数テーブルにまたがるため、アプリケーション検証と遅延制約トリガーが必要になる。
- 15分の引き継ぎ依頼期限と10分の再認証有効期間が、実店舗の交代手順に合わない可能性がある。
- 緊急就任を後から `unjustified` としても、過去の操作を一括して取り消せないため、必要に応じて個別調査が残る。
- 次営業日の探索範囲と解決不能の判定は、後続の営業カレンダー設計と整合させる必要がある。
- 72時間フォールバックは実際の次回勤務日時を表すとは限らない。

## 将来見直す条件

- 実店舗で15分以内に引き継ぎ承認できない事例が頻発した、または短すぎて誤承認を防げないと判明した。
- パスワード入力以外の多要素認証、端末認証または生体認証をスタッフ認証へ導入する。
- 緊急就任や期限超過が頻発し、管理者通知、自動エスカレーションまたは就任可能者の事前指定が必要になった。
- 複数店舗兼務、複数責任者の共同担当、シフトシステムとの自動連携が必要になった。
- 事後確認を既存の例外審査画面と統合しても、権限手続きと予約訂正の意味を分離できるUI・API設計が確定した。
- フォールバックが頻発し、長期休業専用の確認担当、通知または期限規則が必要になった。
