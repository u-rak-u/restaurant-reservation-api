# ADR-0009: 共通予約の種別・状態・ライフサイクル日時

## 状態

採用済み（2026-08-24、2026-08-27更新）

## 背景

共通予約は通常予約と貸切予約の集約ルートであり、店舗、予約番号、予約種別、予約者連絡先、現在状態、取消情報、作成と状態変更の日時を一元管理する。種別固有の予約対象時間、人数、コメント、貸切範囲は詳細テーブルへ分離済みである。

基本状態は5種類に確定しているが、状態名だけでは来店、利用完了、取消、無断キャンセル確定の発生日時を効率よく検索できない。保持期限の起算点や当日業務でも使用するため、現在の有効なライフサイクル日時を共通予約へ保存する必要がある。

一方、予約者名と電話番号は予約作成時に必須だが、予約終了から1年後に削除または不可逆な匿名化を行う。DBのNOT NULLだけで入力必須を表すと、確定済みの削除方針を実行できない。

## 判断対象

- `reservations` に置く共通列と、種別詳細へ置く列の境界。
- 予約種別と基本状態をPostgreSQL ENUM、テキストとCHECK、マスターテーブルのどれで表すか。
- 状態変更日時を現在状態の変更日時1列にするか、出来事ごとの列にするか。
- 予約者連絡先の入力必須と保持期限後の削除を両立する方法。
- 状態遷移をDBとアプリケーションのどちらでどこまで保証するか。

## 検討した選択肢

### 1. PostgreSQL ENUMで種別と状態を表す

- 未定義値をDBで拒否でき、型名から用途も識別しやすい。
- 値の追加、名前変更、削除に専用のマイグレーションが必要で、通常のCHECK制約より変更手順が複雑になる。
- DBMS固有型としてORMとテスト環境でも扱いを揃える必要がある。

### 2. テキストとCHECK制約で種別と状態を表す

- 未定義値をDBで拒否しながら、値の見直しを通常のマイグレーションで管理できる。
- アプリケーションではPython Enumへ変換して型安全に扱える。
- 列自体は汎用テキスト型なので、CHECK制約を外す不適切な変更があれば未定義値を保存できる。

### 3. 種別と状態をマスターテーブルで表す

- DB行の追加により値を増やせる。
- 種別と状態は店舗が設定するデータではなく、アプリケーションの検証、認可、状態遷移、詳細テーブル構造と結び付くため、行だけ追加しても動作しない。
- 外部キーとJOINの管理対象が増える。

### 4. 現在状態と状態変更日時1列だけを保存する

- NULL可能な日時列を減らせる。
- 来店日時と利用完了日時を同時に参照できず、保持期限や滞在時間の判定を監査履歴から復元する必要がある。
- 監査履歴の匿名化または削除によって業務上必要な現在値を失う可能性がある。

### 5. 出来事ごとの現在有効な日時を保存する

- 来店、完了、取消、無断キャンセル確定を直接検索でき、保持期限の起算点も明確になる。
- 状態に応じてNULL列が生じ、状態と日時の整合CHECKが必要になる。
- 過去の誤操作や訂正経緯は別の監査・訂正記録に残し、親には現在有効な値だけを保持できる。

## 採用した案

- `reservations` に内部ID、店舗ID、予約番号、予約種別、基本状態、予約者連絡先、作成・更新日時、来店・完了・取消・無断キャンセル確定日時、管理終結日時、キャンセル主体と理由を置く。
- 予約種別は `regular`、`exclusive`、基本状態は `confirmed`、`checked_in`、`completed`、`cancelled`、`no_show` とし、`text` とCHECK制約で保存する。
- アプリケーションでは同じ値をPython Enumとして定義する。
- 予約種別は作成後に変更できないよう、DB更新トリガーでも拒否する。
- 状態ごとに必要な日時、NULLであるべき日時、取消情報をCHECK制約で対応付ける。
- `created_at` と状態変更日時はクライアント入力にせず、DBサーバー時刻を使用する。`created_at` は不変とし、オンライン取消の訂正猶予へ使用する。
- 予約者名とE.164電話番号は作成時と有効状態で両方必須にするが、保持期限後に削除できるよう列自体はNULLを許可する。片方だけを残さない。
- 状態遷移は専用のアプリケーション操作で行い、任意状態へ変更する汎用APIを作らない。定義済みの前向き遷移を `confirmed -> checked_in`、`confirmed -> cancelled`、`confirmed -> no_show`、`checked_in -> completed` に限定し、DB更新トリガーでも更新前後と承認済み例外案件の有無を検証する。`confirmed -> no_show` は承認済み `no_show_review` と電話照合値を同じトランザクションに要求する。
- 承認済み例外案件による訂正だけは通常遷移以外を許可できる。後続の例外・監査テーブル設計で、同じトランザクション内にある案件種別と許可遷移の対応を更新時に検査し、承認済み案件、訂正後状態、訂正記録および資格情報が揃わなければコミットできない遅延制約トリガーも追加する。
- 予定終了から30日後も未解決の `arrival_issue` がある `checked_in` は、基本状態を推測変更せず `management_closed_at` を設定して通常業務上だけ終了する。設定後は資格情報を削除し、通常操作と未終了一覧へ戻さない。具体的な判断はADR-0030を正とする。
- 予約対象時間、人数、通常予約コメント、貸切団体名、貸切範囲は種別詳細へ置く。
- 楽観的ロック版、個人情報削除予定日時、予約番号の最終制約は後続項目で確定する。

## 採用理由

テキストとCHECK制約は、DBで未定義値を拒否する強さを保ちながら、PostgreSQL ENUMより変更とマイグレーションを扱いやすい。種別や状態は店舗設定ではないため、マスターテーブルで動的に追加できるようにする必要もない。

出来事ごとの日時を親へ保存すれば、当日一覧、状態別検索、利用完了、取消、無断キャンセル、保持期限を監査ログの復元に依存せず処理できる。状態との組み合わせをCHECKで限定することで、NULL列による不正状態を抑えられる。

予約者連絡先を物理的にNULL可能にすることは入力省略のためではなく、終了後または管理終結後の個人情報削除を実行するためである。有効状態での必須条件と2列同時削除をCHECKで保証し、アプリケーションの入力検証だけに依存しない。

## 実用性評価

この構成は、単一店舗MVPの予約一覧、電話受付、来店確認、営業終了後の無断キャンセル審査、保持期限処理に利用できる。共通テーブルだけで現在状態と主要ライフサイクル日時を取得でき、通常予約と貸切予約の処理を同じ状態モデルへ載せられる。

状態別のNULL制約は実装量を増やすが、状態と出来事の不一致を早期に検出できる。更新前後を比較するトリガーも併用することで、現在値だけは正しい不自然な飛び越し遷移を、アプリケーションの不具合やDBへの誤更新でも拒否できる。例外訂正は承認済み案件との横断検査が必要なため、DB-37からDB-40の遅延制約が完成するまでは実装完了とみなさない。

連絡先をNULLへ更新した後は顧客問い合わせへ回答できる範囲が狭くなる。保持期限、削除保留、dry-run、バックアップ復元後の再適用はDB-42からDB-44で具体化する必要がある。

## デメリット

- 状態ごとの日時列と取消列にNULLが生じ、CHECK制約が比較的長くなる。
- PostgreSQL ENUMと異なり、型そのものではなくCHECK制約が許可値を保証する。
- 通常遷移トリガーに加えて、例外案件と訂正記録を検証するPostgreSQL固有の遅延制約トリガーを保守する必要がある。
- 予約者連絡先の列はNULL可能なので、初期登録と有効状態での必須条件を複合CHECKで保守する必要がある。
- 種別固有の日時や人数を表示する一覧では、対応する詳細テーブルとのJOINが必要になる。

## 将来見直す条件

- 予約種別または状態を追加、統合、廃止する。
- 顧客アカウント導入により、予約時点の連絡先と現在の顧客情報を分けて参照する。
- 予約訂正の種類が増え、現在値と操作履歴の関係を別の状態履歴テーブルとして持つ必要が生じる。
- 状態別CHECK制約が変更のボトルネックになり、別の整合性表現が必要になる。
- 保持期限後に予約行全体を削除する方針へ変更し、連絡先を途中でNULLにする必要がなくなる。
