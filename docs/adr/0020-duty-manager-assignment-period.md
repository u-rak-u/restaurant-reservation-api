# ADR-0020: 当日運用責任者を時間範囲の任命履歴として保存する

## 状態

採用済み（2026-08-27）

## 背景

MVPでは各営業日に1人の当日運用責任者を置くことを基本とし、営業日前、開店直前、営業途中の任命と交代を許可する。急な退勤時にも業務を止めず、通常は管理者任命または承認を伴う引き継ぎ、管理者へ連絡できない場合は緊急就任で復旧する。

当日運用責任者は基本ロールではなく、その営業日の一定期間だけ追加される権限である。前任者と後任者が同時に有効にならず、履歴を失わず、日付をまたぐ営業と閉店後の締め作業にも対応できる保存方式が必要である。

## 判断対象

- スタッフアカウントまたは店舗の現在値として保存するか、任命履歴として保存するか
- 対象営業日、開始、終了、開始前取消をどの列で表すか
- 営業日終了を最後の閉店時刻と同時にするか、締め作業時間を含めるか
- 同じ店舗の同じ瞬間に有効な責任者を最大1名とする方法
- 責任者が存在しない状態をDBで禁止するか、警告と復旧操作を許可するか

## 検討した選択肢

### 1. `staff_accounts` のロールまたはフラグを上書きする

- 現在の責任者を1回のスタッフ検索で取得できる。
- 対象営業日、有効期間、営業途中の交代履歴を失い、基本ロールと一時的な職務を混同する。

### 2. 店舗ごとに現在の責任者IDを1件だけ保存する

- 現在値の重複を単純な主キーで防げる。
- 将来任命、過去の交代、日付をまたぐ営業を別の履歴と同期する必要があり、現在値と履歴が食い違う可能性がある。

### 3. 営業日ごとに1行を作り、担当者を上書きする

- 営業日単位の検索は単純になる。
- 1営業日に複数回の交代を表せず、前任者がいつまで権限を持っていたかを汎用監査ログから復元しなければならない。

### 4. 任命ごとの時間範囲を保存して重複を排他制約で拒否する

- 前任・後任を別の不変な主体として保存し、現在、将来、過去の任命を同じ構造で検索できる。
- `btree_gist` と範囲演算を使うためPostgreSQL固有になり、店舗ロックと排他制約の統合テストが必要になる。

## 採用した案

- `duty_manager_assignments` にUUIDv7、店舗、対象営業日、担当スタッフ、開始、終了、開始前取消、作成・更新日時を保存する。
- 店舗とスタッフIDの複合外部キーにより、別店舗のスタッフを任命できないようにする。有効かつパスワード設定済みのスタッフだけを任命できる。
- 有効期間を `[starts_at, ends_at)` とし、開始前の予定変更は `cancelled_at` を設定して新しい任命を作る。開始済みの行は取消さず、引き継ぎ成立時刻へ終了を短縮する。
- 営業日前の通常任命は最初の開店を開始候補とし、開店前準備で必要なら管理者が対象日内の開始時刻を明示できる。即時任命はDBサーバー現在日時から開始し、遡及させない。
- 通常の終了上限を対象営業日の最後の閉店から2時間後として各任命へ保存する。複数営業時間帯の中休みと、日付をまたぐ営業の締め作業も同じ期間に含める。
- `btree_gist` と `EXCLUDE USING gist (store_id WITH =, tstzrange(starts_at, ends_at, '[)') WITH &&) WHERE (cancelled_at IS NULL)` により、同じ店舗の時間重複を拒否する。
- 任命操作では対象店舗をロックして現在・将来任命を再取得し、排他制約を実装漏れと並行書き込みへの最終防御とする。
- DBでは同時に最大1名だけを保証する。最低1名は強制せず、未任命・責任者不在の警告、管理者の即時任命、ADR-0021の緊急就任で復旧する。
- 任命中のスタッフを無効化または管理者用パスワード再設定待ちにする場合は、現在任命の終了と将来任命の取消を同じトランザクションへ含める。

## 採用理由

時間範囲を正にすれば、現在の責任者は現在日時を含む1行、当日の交代は隣接する複数行として取得できる。前任者の行を後任者へ上書きしないため、誰がどの時間に責任者だったかを監査ログの差分復元だけに依存せず説明できる。

半開区間なら前任者の終了と後任者の開始を同じ時刻にできる。店舗ロックで競合の処理順を安定させ、排他制約で別経路や並行実行からの重複もDBが拒否する。営業日を排他制約の比較キーに含めないため、深夜営業で誤った営業日が入力されても同じ実時間の二重任命を防げる。

閉店時刻ちょうどに失効すると、無断キャンセル候補確認、例外案件の提起、締め作業を当日運用責任者が実行できない。閉店後2時間を明示的な上限として保存すれば、定期ジョブなしで自動失効し、翌日まで無期限に権限を残さない。

## 実用性評価

40席の単一店舗では、任命は通常1日1件、交代があっても数件であり、GiSTインデックスと営業日別B-treeインデックスで十分軽く検索できる。任命がない状態を許容することで、急な退勤や資格情報事故の処理をDB制約が妨げず、緊急就任による復旧を行える。

排他制約だけでは責任者の不在、資格情報の失効、現場に本人がいることを保証できない。権限判定で現在のスタッフ状態を確認し、開店前と営業中の警告をスタッフ画面へ出す。緊急就任と監査の構造はADR-0021で補完する。

閉店後2時間は実店舗の締め作業時間を測定する前の暫定値である。各行に適用済みの終了日時を保存するため、将来値を変更しても過去履歴は変わらない。実運用で不足または過剰なら、店舗設定として0～数時間の範囲を定め、変更後の任命だけへ適用する。

## デメリット

- `btree_gist` 拡張、時間範囲の排他制約、店舗ロックにより、単純な現在値より実装とテストが増える。
- PostgreSQL以外へ移行する場合は、範囲重複を直列化または別の制約で実装し直す必要がある。
- 閉店後2時間を超える例外対応では、当日運用責任者固有の権限が失効し、管理責任者または管理者による後続処理が必要になる。
- DBは責任者が常に存在することを保証しないため、警告を見落とすと責任者不在の時間が生じる。
- 営業時間の変更と、既に保存した将来任命の終了日時をどう同期するかを営業カレンダー設計で完成させる必要がある。

## 将来見直す条件

- 実店舗の締め作業時間から、閉店後2時間が短すぎる、または長すぎると判明した。
- 1営業日を複数責任者で分担する予定管理、スタッフシフト連携または複数店舗兼務が必要になった。
- PostgreSQL以外のDBMSへ移行する。
- 任命件数または店舗数が増え、現在責任者検索、GiSTインデックスまたは店舗単位ロックが実測上の問題になった。
- 営業時間変更と任命期間を自動調整する要件が確定した。
