# ADR-0015: 予約番号を店舗単位の12桁とし3年後に解放する

## 状態

採用済み（2026-08-25）

## 背景

予約番号は、顧客が電話で予約を照会し、予約確認コードと組み合わせてQRコードを再表示するための公開識別子である。内部主キーのUUIDより読み上げやすくする必要がある一方、番号だけで予約の閲覧、変更、取消または来店確認を許可してはならない。

予約番号をシステム全体で永久に一意とすると、単一店舗MVPには不要な全店舗横断調整が必要になり、発行総数が番号空間へ永続的に蓄積する。使用率に応じて番号世代や生成方式を人手で切り替える設計も、通常運用へ将来の定期作業を埋め込むことになる。

一方、店舗単位で一意にし、業務上の問い合わせ期間を終えた番号を自動解放すれば、1店舗が同時に保持する番号数だけを考えればよい。予約者名、連絡先、業務履歴および監査履歴には既に保持期限と日次削除ジョブがあるため、予約番号も同じ仕組みで処理できる。

## 判断対象

- 予約番号の桁数、文字種、チェックディジットをどうするか。
- 一意性をシステム全体または店舗単位のどちらで保証するか。
- 乱数衝突時に安全に再生成する方法と打切り条件をどうするか。
- 予約番号を永久保持するか、期限後に解放するか。
- 顧客とスタッフが対象店舗をどのように指定するか。

## 検討した選択肢

### 1. 10桁をシステム全体で永久に一意とする

- 予約番号だけで全店舗から対象候補を検索できる。
- Luhn用の1桁を除くと有効な番号は10億通りであり、累積発行数が永久に増える。
- 単一店舗MVPでも全店舗共通の番号空間と将来の移行時期を管理することになり、店舗をまたいだ調整が必要になる。

### 2. 番号世代または形式を使用率に応じて切り替える

- 既存形式を維持しながら新しい番号空間を追加できる。
- 切替条件、複数形式の受付、移行試験および告知を将来の担当者が管理し続ける必要がある。
- 同じ桁数の内部を世代へ分割するだけでは番号空間そのものは増えない。

### 3. 連番を独自変換または暗号学的置換で並べ替える

- 適切な全単射であれば使用中の番号同士を衝突させずに発行できる。
- 独自の剰余演算は出力を推測されやすく、暗号学的な形式保持暗号は鍵管理、実装選定、更新および障害時復旧を追加する。
- 予約番号は認証情報ではなく、今回の規模では複雑な変換方式の運用負荷が利点に見合わない。

### 4. 店舗単位の12桁乱数とし、3年後に自動解放する

- 先頭11桁によって店舗ごとに1000億通りを使用でき、10桁方式の100倍の空間を持つ。
- 既存の日次削除ジョブで期限後の番号を解放するため、累積発行総数ではなく保持中の番号数だけが一意制約の対象になる。
- 10桁より電話で2桁長く読み上げる必要があり、乱数方式なので衝突時の再試行は残る。

## 採用した案

- 予約番号の正規形を、先頭0を許すASCII数字12桁の文字列とする。
- 先頭11桁をOSが提供する暗号学的に安全な乱数生成器で生成し、末尾1桁を先頭11桁に対するLuhnチェックディジットとする。
- 表示時は `XXXX-XXXX-XXXX` の4桁区切りとし、DBには区切りを保存しない。
- 12桁形式とLuhn整合をDBのCHECK制約およびアプリケーションで検証する。
- 保持中の予約番号を `UNIQUE (store_id, reservation_number)` によって店舗単位で一意にする。
- 単一店舗MVPの公開処理ではデプロイ設定の店舗コード、将来の複数店舗向け公開処理ではURLまたは入力の店舗コード、スタッフ処理では認証済みスタッフの所属店舗から店舗IDを解決する。顧客には表示用店舗名と予約番号を合わせて案内する。
- 予約作成時は同じ店舗の一意制約に対する `INSERT ... ON CONFLICT DO NOTHING RETURNING` を使用し、衝突した場合だけ新しい番号で最大32回再試行する。
- 32回すべてが衝突した場合は、乱数生成器または実装の異常として作成を失敗させて記録し、連番、日時または弱い乱数へ切り替えない。
- 発行済み番号を別の非NULL値へ変更しない。`management_closed_at` がある `checked_in` では予定終了から3年後、それ以外の終了予約では予約終了から3年後を期限とし、削除保留中でない場合だけ、既存の日次削除ジョブが番号NULLと解放日時の記録へ更新する。
- 解放後の番号は同じ店舗の新しい予約へ再利用できる。解放済みの予約は内部UUIDで識別し、番号世代または使用率に応じた手動切り替えを設けない。
- 業務履歴、監査履歴およびジョブログへ予約番号を複製せず、対象の追跡には内部UUIDを使用する。
- 予約番号を認証情報として扱わず、公開操作には予約確認コード、来店確認にはチェックイントークンまたは予約確認コードを引き続き要求する。

## 採用理由

店舗名は変更または重複しうるが、店舗IDはDB内の所属を安定して表せる。店舗IDと予約番号の複合一意制約により、番号空間を店舗ごとに独立させながら、顧客には理解しやすい「店舗名と予約番号」で案内できる。

11桁の乱数部分は1000億通りあり、3年後の自動解放によって保持件数も有限になる。40席の1店舗が通常利用で空間全体へ近づく現実的な経路はなく、使用率を見ながら世代を切り替える担当者を置く必要がない。

Luhnは認証強度を上げるものではないが、表示または電話入力時の誤りをDB検索前に発見する補助になる。暗号学的乱数、一意制約、衝突時の再試行はそれぞれ推測困難性、永続化後の重複防止、可用性を分担し、独自の暗号変換や鍵管理を追加しない。

## 実用性評価

1店舗で毎分1件を4年間連続して発行するという実店舗には大幅に過大な想定でも、保持候補は約210万件で1000億通りの約0.0021%である。1回の候補が既存番号と衝突する確率は同じ割合であり、32回連続衝突は通常の負荷として考えるより、乱数生成器、実装または制約の故障を疑うべき状態になる。

番号の解放は既存の日次削除ジョブへ統合し、停止中の未処理分は次回起動時に冪等に処理する。ジョブが一時的に失敗しても既存番号が残るだけで予約APIを直ちに停止させず、失敗が継続した場合だけ運用者へ警告する。これにより定期的な人手作業は不要になるが、ソフトウェア、DBまたはスケジューラー自体の継続障害まで無人で必ず修復できるわけではない。

予約終了または `management_closed_at` の設定時に確認コードとチェックイントークンの保存値を削除し、新しい予約には資格情報を新規発行するため、3年後に同じ番号が再利用されても、以前の番号だけで新しい予約を操作できない。ただし、8桁の確認コードは独立生成でも偶然同じ値になりうる。番号再利用の時期を知ることも必要な極めて小さい残余リスクだが、公開検証APIのRate Limit、存在を判別できない応答、およびADR-0016で確定した資格情報の生成・検証によって対処する。また、3年経過後は古い番号による問い合わせ検索ができず、番号だけを提示されたスタッフが新しい予約との同一性を判断してはならない。

12桁は電話で扱える範囲と判断するが、8桁の予約確認コードも続けて確認する場面では読み上げ量が増える。4桁区切り、復唱、Luhnによる事前検査を画面へ反映し、電話受付の試作で入力時間と誤入力率を確認する必要がある。

## デメリット

- 10桁より電話での読み上げと手入力が2桁長くなる。
- 乱数方式なので衝突の可能性自体はなくならず、DBの一意制約と再試行処理が必要になる。
- 予約番号を解放した後は、その番号から古い個別予約を検索できない。
- 同じ予約番号が別店舗または同じ店舗の異なる時期に存在しうるため、番号だけを店舗横断の識別子として扱えない。
- Luhn検査は偶発的な入力誤りの検出用であり、悪意ある改変、本人性または操作権限を保証しない。
- DBでLuhn整合を検査する関数と、期限後に番号を解放するジョブおよび制約が必要になる。

## 将来見直す条件

- 電話受付の実測で、12桁と確認コードの組み合わせが許容できない誤入力率または対応時間になる。
- 1店舗の保持中番号数または衝突再試行率が、予約作成の性能目標へ影響すると実測される。
- 予約番号を3年を超えて照会可能にする法令、契約または業務要件が生じる。
- 外部予約サービスとの連携で、番号の桁数、文字種または全体一意性を指定される。
- 複数の予約データベースをまたいで、店舗コードを伴わない単一の公開識別子が必要になる。
