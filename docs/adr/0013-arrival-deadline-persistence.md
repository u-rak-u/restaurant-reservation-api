# ADR-0013: 通常予約の到着期限と遅延実行による席解放

## 状態

採用済み（2026-08-24、境界規則を2026-08-25更新）

## 背景

通常予約は、無連絡なら開始15分後ちょうどまで、遅刻連絡があれば到着予定15分後ちょうどまで来店を受け付ける。ただし、着席、注文、料理提供、食事の時間を確保するため、終了30分前を過ぎた後の来店は受け付けない。遅刻連絡によって元の90分の予約期間は変更せず、正式な無断キャンセル確定も営業終了後の審査まで行わない。

この規則を実装するには、現在の到着予定と連絡日時、適用した期限、期限超過を席配置へ反映した事実を区別する必要がある。また、毎分の定期処理を導入しなくても、期限どおりの空席として安全に再利用できる設計が必要になる。

## 判断対象

- 到着期限を現在時刻のたびに計算するか、予約ごとに保存するか。
- 到着予定と連絡受付日時を通常予約詳細へ置くか、専用履歴テーブルへ分けるか。
- 業務上の席解放日時と、DBへ解放を反映した処理日時を分けるか。
- 期限到来時に毎分の定期処理を必須とするか、必要時の遅延実行を許可するか。
- 終了30分前の境界と、期限後に届いた連絡をどう扱うか。

## 検討した選択肢

### 1. 期限を保存せず、参照のたびに現在の規則から計算する

- 保存列を減らせる。
- 将来15分または30分の規則を変更すると、既存予約の顧客へ提示済みの期限まで変わる。
- 期限超過を席配置へ反映したかを通常予約だけから判別できない。

### 2. 連絡ごとに専用履歴行を作る

- 複数回の連絡を構造化して完全に保持できる。
- MVPの空席判定に必要なのは現在の到着予定と期限であり、履歴テーブルと現在値を同期する実装量が増える。

### 3. 現在値を通常予約詳細に置き、変更履歴を共通監査へ残す

- 来店確認と空席判定が1件の通常予約詳細から現在値を取得できる。
- 過去の連絡を確認するには監査記録の参照が必要になる。

### 4. 毎分の定期処理で期限到来と同時に全件解放する

- DB上の席配置が実時間に近い状態で更新される。
- 常駐スケジューラ、重複実行防止、障害監視、再試行がこの機能だけでも必要になる。

### 5. 期限を有効な解放日時として保存し、席が必要になった時点で遅延実行する

- 毎分のジョブなしで、予約作成または予約なし利用受付のトランザクション内に解放を組み込める。
- 保存済みの席配置は処理が起きるまで古い占有終了を指すため、読み取り上の期限超過と、書き込み時の解放反映を区別する必要がある。

## 採用した案

- `regular_reservation_details` に `expected_arrival_at`、`arrival_notice_received_at`、`arrival_deadline_at`、`arrival_timeout_processed_at` を置く。
- 到着予定と連絡受付日時は両方NULLまたは両方値ありとし、連絡受付日時はDBサーバー時刻を使用する。
- 到着予定は元の開始より後、終了30分前以前の分単位とする。終了30分前ちょうどを許可し、それを過ぎた時刻は受け付けない。
- 連絡なしの期限は開始15分後、連絡ありの期限は到着予定15分後と終了30分前の早い方とし、適用した期限を予約へ保存する。
- 来店確認、遅刻連絡、顧客都合キャンセルは期限ちょうどまで許可し、期限を過ぎた後に拒否する。
- 遅刻連絡があっても元の開始・終了日時を変更しない。
- 期限ちょうどまでの到着予定変更だけを許可し、変更前後とスタッフは共通監査記録へ残す。期限を過ぎた後の連絡は予約を変更せず、無断キャンセル審査へ記録する。
- `arrival_timeout_processed_at` はDBへ解放を反映した実際の処理日時とし、業務上の有効な解放日時は `arrival_deadline_at` とする。
- 期限超過による席解放は、予約作成、予約なし利用受付、営業終了時の候補抽出で遅延実行できる。毎分の定期処理を必須にしない。
- 遅延実行では予約と席配置をロックし、占有終了を期限へ変更した新しい席配置世代、現在世代の切り替え、処理日時、新しい割り当てを同じトランザクションで確定する。
- 期限到来だけで `no_show` へ変更せず、営業終了後の提起と管理責任者の承認を維持する。
- `checked_in`、`completed`、期限内に成立した通常の `cancelled` では期限超過処理日時を持たず、正式な `no_show` では必須とする。期限超過による席解放後も未解決案件が残り、予定終了30日後の日次処理が店舗側の管理終結として `cancelled` にした場合だけ、解放済みの事実として処理日時を維持する。

## 採用理由

到着期限を保存すれば、将来店舗規約を変更しても、予約時または遅刻連絡時に顧客へ適用した期限を維持できる。連絡受付と到着予定を分けることで、期限内に有効な連絡を受けたか、顧客が何時に来ると伝えたかを区別できる。

有効な解放境界と処理日時を分ければ、19時15分が期限の予約を19時18分の新規受付で初めて処理しても、業務上は19時15分を過ぎた後から空席として扱える。席を必要とする書き込みと解放を同じトランザクションへ入れるため、古い席配置を無視して二重割り当てする必要がない。

## 実用性評価

4つの列と現在値の更新で、無連絡、複数回の遅刻連絡、終了30分前の打切り、期限後の再販売、営業終了後の審査を扱える。40席の単一店舗では列数と期限超過候補の検索量は小さく、毎分ジョブを運用しなくてもMVPとして利用できる。

ただし、読み取りだけで席配置が更新されるわけではない。新しい予約または予約なし利用を確定するトランザクションが、期限超過した占有を必ず先に新世代へ反映する必要がある。これを一部の受付経路で省略すると、空席表示とDB制約が食い違う。

期限直前の来店、電話連絡、席解放、新規割り当ては競合する。サーバー時刻、共通ロック順序、冪等な期限超過処理、PostgreSQL実環境の同時実行テストが完了するまでは、本番相当の競合安全性を保証できない。

## デメリット

- 通常予約詳細に4列が増え、親状態との横断制約も必要になる。
- 現在の連絡情報は上書きされるため、過去の連絡確認が共通監査記録に依存する。
- DBへ解放を反映する前は、保存済み席配置と現在時刻から見た有効な占有状態が一時的に異なる。
- 期限超過処理を利用するすべての書き込み経路で、同じロックと再検証を実装する必要がある。
- 終了30分前に近い到着予定では、顧客に与えられる猶予が15分未満になる。

## 将来見直す条件

- 遅刻連絡そのものを業務履歴として長期間、構造化検索する必要がある。
- 店舗ごと、予約プランごとに遅刻猶予または最低利用可能時間を変更する。
- 期限超過件数が増え、遅延実行より定期処理の方が検索性能または運用監視に適する。
- 顧客が公開ページ、SMSまたは自動音声から到着予定を登録する。
- コース料理、注文、会計と連携し、最低利用可能時間を料理提供時間から動的に決める。
