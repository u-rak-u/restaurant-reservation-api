# ADR-0018: スタッフアカウントを店舗所属の個別アカウントとして管理する

## 状態

採用済み（2026-08-27）

## 背景

MVPでは、通常スタッフ、当日運用責任者、管理責任者、管理者を区別し、誰が予約、予約なし利用、席配置または例外案件を操作したか監査する。これまでスタッフアカウントは初期データとして用意し、店舗設定全体の汎用管理CRUDとともに変更機能をMVP後へ回す予定だった。

しかし、実店舗では入職、退職、権限変更、ログインIDの訂正、パスワード忘れまたは漏えい疑いが発生する。これらを開発者によるDB操作や再デプロイだけで扱う構成では、退職者のアクセス停止が遅れ、実運用と監査の両方に耐えにくい。

一方、席構成や営業時間を含む店舗設定全体の汎用CRUDまでMVPへ追加すると、既存予約への影響確認と競合制御が大きく広がる。スタッフ管理に必要な範囲だけを独立して判断する。

## 判断対象

- スタッフを共有アカウントと個別アカウントのどちらで管理するか
- アカウントを店舗へ直接所属させるか、複数店舗関連を最初から作るか
- 基本ロールと当日運用責任者を同じ列で表すか
- ログイン識別子にメール、全体一意ID、店舗内IDのどれを使うか
- 初期データだけで運用するか、汎用CRUDまたは限定管理操作をMVPへ含めるか
- 無効化、匿名化、物理削除および最後の管理者をどう扱うか

## 検討した選択肢

### 1. 受付やホール単位の共有アカウント

- シフト中のログイン回数を減らせる。
- 実際の操作者を監査できず、退職者だけのアクセスを止めることもできない。
- パスワードが複数人へ広がり、漏えい時の変更と責任分界が難しい。

### 2. グローバルなアカウントと店舗所属の中間テーブル

- 同じ人物の複数店舗兼務、店舗ごとの異なるロール、全店舗共通ログインへ拡張しやすい。
- 単一店舗MVPでは使用しない所属選択、複数ロール、認可分岐と初期化順序が増える。

### 3. 1アカウントを1店舗へ直接所属させる

- 所属店舗をすべての認可条件へ直接含められ、単一店舗MVPのモデルと一致する。
- 複数店舗兼務を導入するときは、アカウントと所属を分ける移行が必要になる。

### 4. 当日運用責任者を基本ロールの値にする

- 現在の肩書だけを見る処理は単純になる。
- 営業途中の交代、有効期間、引き継ぎ、緊急就任の履歴を基本ロールの上書きで失う。

### 5. メールアドレスまたはシステム全体で一意なログインID

- 店舗指定なしで全体からアカウントを検索できる。
- メール所有確認と変更管理、個人情報の追加が必要になり、全体一意IDは別店舗間の命名調整を要求する。

### 6. 店舗内で一意な専用ログインID

- メールを取得せず、店舗単位の認可境界と同じ組み合わせで検索できる。
- 複数店舗を単一画面で扱う場合は、店舗コード、サブドメインまたは所属選択をログインへ追加する必要がある。

### 7. 初期データだけで運用する

- 管理APIと画面を作らずMVPを小さくできる。
- 入退職と資格情報事故のたびに開発者、DB操作または再デプロイが必要になり、アクセス停止を店舗だけで完結できない。

### 8. 任意項目を扱う汎用CRUD

- 少ないエンドポイントで全項目を操作できる。
- ロール変更、無効化、パスワード再設定など影響の異なる操作へ、再認証、理由、監査、セッション失効を確実に結び付けにくい。物理削除も誤って公開しやすい。

### 9. 用途別の限定管理操作

- アカウント作成、ロール変更、無効化などへ個別の権限、検証、監査、セッション失効を定義できる。
- 初期データだけの方式よりAPI、画面、テストの実装量が増える。

## 採用した案

- スタッフごとに個別の `staff_accounts` 行を作成し、共有アカウントを通常運用に使用しない。
- すべてのアカウントを1店舗へ必須所属させ、所属店舗は作成後変更不可とする。MVPの管理者も店舗所属とし、全店舗を無条件に操作する主体を作らない。
- 基本ロールを `staff`、`manager`、`admin` とする。当日運用責任者は別の期限付き任命とし、基本ロールを書き換えない。
- 内部参照にはUUIDv7、ログインにはNFKC正規化後のASCII小文字からなる店舗内ログインIDを使用する。`UNIQUE (store_id, login_id)` で一意にする。
- スタッフ管理だけを店舗設定全体から切り出し、同じ店舗の有効な `admin` による作成、参照、表示名・ログインID・ロール変更、無効化、再有効化、パスワード設定・再設定をMVPへ含める。
- 任意項目を一括変更する汎用更新と物理削除は提供しない。機微な変更は用途別操作とし、理由、変更前後、操作者、日時を監査する。
- 自分自身と店舗最後の有効な管理者を無効化・降格できない。管理者数を減らす処理は店舗をロックし、同時操作後も最低1件を維持する。
- 無効化時と、ログインID・ロール・パスワードの変更時は全セッションを失効する。具体的な資格情報、再認証、ログイン失敗状態およびセッション構造はDB-15で確定する。
- 無効化した行は物理削除せず、3年後にログインIDと表示名を匿名化する。内部ID、所属店舗、最後の基本ロールと監査参照は残し、匿名化後は再有効化しない。

## 採用理由

個別アカウントは、予約と例外操作の責任主体を追跡し、退職者だけを無効化するために必要である。店舗へ直接所属させれば、単一店舗MVPのすべてのスタッフ認可に同じ店舗IDを使用できる。

人が覚えるログインIDと不変の内部UUIDを分けることで、ログインID変更または将来の再利用後も監査の参照先が変わらない。店舗内一意にすれば別店舗間で名前を調整する必要もない。

スタッフアカウントだけを限定管理へ含めれば、入退職とアクセス事故を店舗内で処理できる一方、席や営業時間など既存予約へ影響する汎用設定変更をMVPへ広げずに済む。用途別操作は、一括PATCHよりも再認証、監査、セッション失効を業務上の出来事へ結び付けやすい。

## 実用性評価

40席の単一店舗ではスタッフアカウントは数十件程度であり、UUID主キーと店舗・ログインIDの複合UNIQUEだけでログイン、一覧、管理者確認を十分軽く処理できる。店舗管理者が入退職、ロール変更、無効化、パスワード再設定を画面から行えるため、通常運用を開発者のDB作業へ依存させない。

個別ログインは共有アカウントより手間が増えるが、シフト開始時のログインと適切なセッション期間で抑えられる。操作スタッフを監査する要件がある以上、共有アカウントによる省力化は採用できない。

限定管理機能そのものが権限奪取の標的になるため、DB構造だけでは本番運用に十分ではない。管理操作の再認証、安全な初回パスワード設定、パスワードハッシュ、Rate Limit、セッション失効、監査警告、管理者資格情報を失った場合の非公開復旧手順を後続設計で完成させる必要がある。

## デメリット

- 複数店舗を兼務する人物には店舗ごとに別アカウントが必要になる。
- メールによる招待やパスワード回復を使わないため、初回秘密情報の受け渡しと復旧手順を店舗内で用意する必要がある。
- スタッフ管理API、管理画面、再認証、監査、セッション失効の実装とテストがMVPへ増える。
- 店舗管理者のアカウントが侵害された場合、攻撃者が新しい管理者を追加する可能性がある。
- 最後の管理者を守っても、全管理者がパスワードを失う事態は通常APIだけでは復旧できない。

## 将来見直す条件

- 複数店舗兼務、店舗ごとに異なるロール、全店舗共通ログインが必要になった。
- 外部IdP、OIDC、従業員ディレクトリまたは検証済みメールアドレスを認証へ導入する。
- 店舗設定全体の管理CRUDを導入し、アカウント管理と共通する承認ワークフローが必要になった。
- MFAまたはパスワードレス認証を導入し、初回設定と復旧フローが変わった。

複数店舗化では、既存のスタッフIDと認証情報を維持したまま `store_id` と `base_role` を店舗所属テーブルへ移し、現在行から1件ずつ所属を生成する。移行後も共有アカウントと物理削除を標準運用にはしない。
