# ADR-0028: 席資源の一時ブロックを恒久的なマスター状態と分離する

## 状態

採用済み（2026-08-28）

## 背景

店舗では、物理テーブルの故障、汚損、配置場所付近の雨漏り、通路障害などにより、席構成自体は変わらなくても一部の席を一時的に使用できないことがある。修理後に同じ席を再利用する事象をマスターの無効化、削除または再作成で表すと、過去の席配置との関係を壊し、コードや固定場所を作り直す必要が生じる。

反対に、ブロック前に作成された予約の席配置を一時停止と同時に削除または無条件に再配置すると、固定決定、来店済み利用、店舗が把握すべき将来予約への影響を失う。商用の予約・テーブル管理システムでも、フロアマスターの削除とは別に、テーブルを現在、特定日またはシフト単位でブロックする運用が用意されている。

## 判断対象

- 一時的な使用不能を席構成マスターの有効状態で表すか、別の期間データにするか。
- 一時ブロックをMVPの限定操作へ含めるか。
- ブロック開始時に作成済み席配置を自動変更するか。
- 恒久廃止および物理削除との境界をどうするか。

## 検討した選択肢

### 1. マスターの有効・無効だけで一時停止と恒久廃止を兼ねる

- 列と操作が少ない。
- 使用不能な期間を表せず、修理後の再開と恒久廃止を区別できない。
- 将来の特定日や営業時間帯だけを停止しにくい。

### 2. 故障時にマスターを削除し、修理後に再作成する

- 現在の候補から確実に除外できる。
- 過去の席配置、固定席、貸切範囲および監査参照を維持できず、同じ実体へ別の内部IDが割り当てられる。

### 3. マスターと期間付きの席資源ブロックを分離する

- 席の恒久的な属性を維持したまま、現在または将来の使用不能期間を表せる。
- ブロック開始と解除を日常運用の限定操作にできる。
- ブロック期間と席占有期間の重複判定、作成済み配置への影響警告が必要になる。

## 採用した案

- 物理テーブルと配置場所の恒久的な有効状態を席構成マスターのライフサイクルとして扱う。廃止日時、変更可能列および物理削除の条件はADR-0032を正とする。
- 一時的な使用不能は、物理テーブルまたは配置場所のどちらか一方と期間を参照する独立した席資源ブロックとして保存する。
- 修理完了時期が分からない場合は終了未定で開始でき、解除操作によって終了させる。
- ブロック期間と重なる物理テーブルまたは配置場所を、新しい予約、予約なし利用および自動再配置の候補から除外する。
- ブロック開始時に作成済みの席配置世代を削除、予約を取消または無条件に再配置しない。影響する現在世代をスタッフ画面へ警告し、明示的な席変更またはブロック解除によって解消する。
- ブロック開始と解除だけをMVPの限定操作に含める。マスターの作成、任意項目更新、恒久廃止および物理削除を行う汎用管理CRUDはMVP後とする。
- 正確な対象列と期間制約はADR-0033、権限、監査および警告の解消条件はADR-0034を正とする。

## 採用理由

物理的な席と、その席を使用できない期間は別の事実である。期間を別エンティティにすれば、同じマスターIDと固定席関係を保ったまま、故障中だけ予約在庫から除外できる。テーブル故障と配置場所周辺の危険も別々の対象として表現できる。

作成済み配置を残せば、どの予約または予約なし利用が影響を受けるかを失わず、固定決定や来店中の利用を勝手に動かさない。影響警告はブロックと現在世代の時間的な重なりから導出できるため、予約本体へ解除忘れが起きる要対応フラグを複製する必要がない。

## 実用性評価

40席の単一店舗では、ブロック対象と時間が重なる現在世代の検索件数は小さい。故障した席を新しい割り当てから即時除外しながら、既存予約への影響を一覧化できるため、初期データ更新と再デプロイだけに依存する方式より実店舗で使用しやすい。

一方、ブロックを登録しただけでは、既に着席中の顧客を移動させたり、将来予約の代替席を確保したりできない。スタッフ画面の強い警告、席変更操作、解除忘れの確認、権限と監査をそろえて初めて実用に耐える。MVPでは影響する席配置を無条件に一括再配置せず、明示的な対応を正とする。

## デメリット

- 席構成マスターとは別のテーブル、期間重複判定、開始・解除操作が必要になる。
- 空席検索と自動再配置が、マスター状態に加えてブロック期間も確認する必要がある。
- 終了未定のブロックは解除忘れにより予約可能数を下げ続ける可能性がある。
- 作成済み配置を自動変更しないため、影響予約が多い場合はスタッフの再配置作業が必要になる。

## 将来見直す条件

- 影響予約が多く、明示的な個別再配置では運用負荷が高くなる。
- 修理予定、業者手配、費用または設備保全履歴まで管理する必要が生じる。
- フロア、エリアまたは任意の席集合を一括でブロックする要望が出る。
- 複数店舗化により、ブロック期間の検索性能または解除忘れの監視方法を変更する必要が生じる。
