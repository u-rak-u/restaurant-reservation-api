# ADR-0014: 貸切範囲を種別と正規化した関連で表す

## 状態

採用済み（2026-08-25）

## 背景

貸切予約は、店舗全体だけでなく、複数の移動可能エリア、複数の物理テーブル、またはその組み合わせを対象にできる。予約停止期間中は対象範囲と重なる通常予約、別の貸切、予約なし利用および席配置を拒否し、参加予定人数が範囲の収容人数を超えないことも保証する必要がある。

店舗全体を個々のテーブルへ展開して保存すると、登録時点の構成は固定できるが、「店舗全体を貸し切った」という業務上の意味が失われる。一方、種類と汎用IDだけを持つ多相関連では、参照先が種類ごとに変わり、通常の外部キーで参照整合性を保証できない。

## 判断対象

- 店舗全体、エリア、物理テーブルを1つの汎用関連で表すか、参照先ごとに分けるか。
- 店舗全体を全エリアまたは全物理テーブルへ展開して保存するか。
- 複数エリア、複数テーブル、および両方の混在を許可するか。
- 範囲の完全性、店舗一致、重複および収容人数をどこで保証するか。

## 検討した選択肢

### 1. `target_type` と `target_id` を持つ単一の多相関連

- 1つの表で将来の対象種類を追加しやすい。
- `target_id` の参照先が種類によって変わるため、PostgreSQLの通常の外部キーで存在と削除整合性を保証できない。
- アプリケーションの不具合や直接操作によって、存在しない対象IDを保存できる余地が残る。

### 2. すべての範囲を物理テーブルへ展開して保存する

- 収容人数と競合を物理テーブルIDだけで判定できる。
- 店舗全体またはエリアという選択理由を復元できず、構成変更時に既存の貸切が何を対象としているか不明確になる。
- 店舗全体貸切の作成時に、すべての物理テーブルの関連行を生成する必要がある。

### 3. 関連行が0件なら店舗全体とみなす

- 範囲種別の列を省略できる。
- 部分選択の関連行を誤ってすべて削除した場合、範囲が空になるのではなく店舗全体へ拡大する危険がある。
- 作成途中と正しい店舗全体貸切を区別しにくい。

### 4. 貸切詳細に範囲種別を置き、エリアと物理テーブルを別の関連テーブルで表す

- 参照先ごとに通常の外部キーを設定できる。
- 店舗全体と部分選択を明示的に区別でき、関連行の消失で意味が反転しない。
- 複数の関連テーブルをまたぐ件数、重複、収容人数には横断的な検証が必要になる。

## 採用した案

- `exclusive_reservation_details.scope_kind` を `entire_store` または `selection` の必須テキスト列とし、CHECK制約で値を限定する。
- `exclusive_reservation_areas` を貸切予約と移動可能エリアの関連、`exclusive_reservation_tables` を貸切予約と物理テーブルの関連とする。
- 各関連は2つの外部キーを複合主キーとし、独立したID、作成日時または更新日時を持たせない。
- `entire_store` では関連行を持たず、対象店舗を親予約の店舗から決める。
- `selection` では2つの関連テーブルを合わせて1件以上を必須とし、複数エリア、複数テーブル、および両方の混在を許可する。
- 選択対象を親予約と同じ店舗の有効な資源に限定し、選択済みエリアに所属する物理テーブルの冗長な個別指定を拒否する。
- 店舗全体は店舗内の有効な物理テーブル、部分選択は選択エリア内と個別選択の有効な物理テーブルの和集合を対象とし、物理テーブルID単位で重複を除外して収容人数を算出する。
- 参加予定人数が算出した収容人数以下であることを、貸切作成または範囲変更と同じトランザクションで検証する。
- 範囲種別と関連件数、店舗一致、冗長指定および参加人数の最終状態を、遅延制約トリガーでも検査する。
- 競合判定では予約停止期間全体を使用し、店舗全体は店舗内のすべての席占有、部分選択は同じエリアまたは物理テーブルを使用する席占有と競合させる。

## 採用理由

範囲種別を明示することで、関連行の有無だけに業務上の意味を持たせず、店舗全体貸切と不完全な部分選択を区別できる。エリアと物理テーブルの関連を分ければ、それぞれへ通常の外部キーを設定でき、汎用ID方式よりDBの参照整合性が強い。

範囲を物理テーブルだけへ展開しないため、管理責任者が選択した「店舗全体」または「エリア」という意図を維持できる。収容人数と競合判定時だけ対象物理テーブルの和集合を求めれば、混在指定でも二重計上を防げる。

## 実用性評価

40席の単一店舗MVPでは、1件の貸切が参照するエリアと物理テーブルは少なく、2つの関連テーブルを結合しても検索量は小さい。店舗全体、エリア単位、個別テーブル、および離れた範囲の組み合わせを同じ構造で扱えるため、管理責任者が合意済みの貸切を登録する用途に利用できる。

ただし、外部キーと遅延制約トリガーだけでは、同時に作成される別予約や席配置との時間競合を完全には防げない。貸切確定処理では対象店舗と資源を共通順序でロックし、最新状態で再検証する必要があり、実際のPostgreSQLを使った同時実行テストが完了するまでは本番相当の保証にならない。

MVPではエリアや物理テーブルを汎用管理APIから変更しないため、現在の関連をそのまま参照しても運用できる。将来これらを変更可能にする場合は、確定済みの将来貸切に対する影響確認、変更拒否または安全な移行、および監査を先に実装する必要がある。

## デメリット

- 貸切詳細に加えて2つの関連テーブルが必要になる。
- 範囲種別と関連件数の整合は単純なCHECK制約だけでは保証できない。
- エリアと物理テーブルを混在させるため、収容人数と競合判定で和集合を求める必要がある。
- エリア所属や物理テーブル定員を変更すると、将来の貸切の収容人数または競合範囲へ影響しうる。

## 将来見直す条件

- フロア、個室、屋外席など、移動可能エリアとは異なる貸切対象単位が必要になる。
- 貸切時点のレイアウトと定員を完全なスナップショットとして長期間再現する必要がある。
- 複数店舗や大規模会場で、範囲を物理テーブルへ展開した検索用データの方が性能上有利と実測される。
- エリアまたは物理テーブルの構成変更を、既存貸切と自動調整する管理機能を導入する。
