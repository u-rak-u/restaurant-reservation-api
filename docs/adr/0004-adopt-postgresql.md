# ADR-0004: DBMSにPostgreSQLを採用する

## 状態

採用済み（2026-08-21）

## 背景

このシステムでは、予約、予約なし利用、貸切、物理テーブル、席配置世代、営業時間、スタッフ権限、例外案件、監査記録を関連付ける。空席確認と登録を同一トランザクションで処理し、同時リクエストによる二重予約をアプリケーションとDB制約の両方で防ぐ必要がある。

開発開始時はPostgreSQLを技術上の初期候補としてDocker Compose環境を構築していたが、DB製品として正式には確定していなかった。テーブル設計を具体化する前に、要件へ適合するDBMSを比較して決定する必要がある。

## 判断対象

MVPと将来の本番運用で正とするDBMSを決定する。PostgreSQLのメジャーバージョンとDockerイメージの固定方針は、別の判断であるDB-02へ分離する。

## 検討した選択肢

### 1. PostgreSQL

- ACIDトランザクション、行ロック、外部キー、CHECK制約を使用できる。
- 時間範囲型、範囲の重なり演算子、GiSTインデックス、排他制約によって、席と占有時間の重複禁止をDBへ表現できる。
- 複雑な関連を持つ業務データと、予約時の競合制御を同じDBMSで扱える。
- PostgreSQL固有機能を利用するほど、別DBへの移植には再設計が必要になる。
- 独立したDBサーバーとして、バックアップ、更新、監視、接続管理が必要になる。

### 2. MySQL（InnoDB）

- ACIDトランザクション、MVCC、行ロック、外部キーを備え、今回のAPIを実装できる。
- Webシステムで広く利用され、MySQLを標準とする環境では運用知識を共有しやすい。
- PostgreSQLの範囲型と排他制約に相当する形で時間帯重複を直接表現しにくく、ロック対象、検索条件、アプリケーション処理へ負担が寄りやすい。

### 3. SQLite

- サーバーを必要とせず、単一ファイルで扱えるため、端末内保存や小規模なツールには適する。
- 同一DBファイルへの書き込みは同時に1件であり、複数クライアントの競合を扱う予約APIの主DBには適さない。
- PostgreSQLの行ロック、範囲型、排他制約を再現できず、SQLiteだけのテストでは本番相当の競合制御を検証できない。

### 4. MongoDB

- 予約ごとに完結する柔軟な文書を保存する用途には適する。
- 今回は店舗、席、配置世代、スタッフ、営業時間などを多数の処理から共有し、参照整合性と複数対象の一括更新が重要である。
- 文書間の参照整合性をアプリケーションで管理する範囲が増え、今回のデータ構造では文書モデルの利点が小さい。

## 採用した案

- このAPIの正とするDBMSにPostgreSQLを採用する。
- 通常の開発、マイグレーション、統合テスト、同時実行テストはPostgreSQLで行う。
- PostgreSQL固有機能を使用する場合は、採用理由、制約だけで守れる範囲、アプリケーション側で補う範囲、移植性への影響を設計文書へ記録する。
- SQLiteを高速な代替DBとして使用し、PostgreSQL固有の動作を検証済みと扱わない。
- PostgreSQLのメジャーバージョンとDockerイメージの固定方針はDB-02で確定する。

## 採用理由

今回の中心課題は、単純なCRUDではなく、席と時間帯の競合、複数予約の自動再配置、予約なし利用との競合、関連データの整合性である。PostgreSQLは一般的なRDBMSのトランザクションと行ロックに加え、時間範囲と排他制約を組み合わせられるため、アプリケーションの事前確認だけに依存せず、DBを最後の防御として設計できる。

既存のDocker Compose環境で起動、ヘルスチェック、TCP接続まで検証済みであり、FastAPI、SQLAlchemy、Alembicから利用する構成にも適合する。MySQLでも技術的には実装可能だが、この要件ではPostgreSQLの方が設計意図を直接表現しやすく、競合制御を学ぶポートフォリオとしての説明力も高い。

## 実用性評価

単一店舗40席のMVPに対してPostgreSQLの性能は十分であり、機能面では余裕がある。DBサーバーの起動が必要になるが、すでにDocker Composeで再現できるため、開発上の負担は許容できる。

本番運用へ移す場合は、PostgreSQLを選ぶだけでは不十分である。バックアップと復元テスト、マイナーバージョン更新、監視、接続数管理、障害時の復旧方法、利用するホスティング先の対応バージョンを別途確定する必要がある。

PostgreSQL固有の排他制約を利用すると移植性は下がるが、今回の重要要件をDBでも保証する具体的な利点がある。固有機能をリポジトリ層とマイグレーションへ閉じ込め、設計文書と実DBを使った統合テストを維持する。

## デメリット

- SQLiteよりセットアップ、バックアップ、更新、監視の作業が多い。
- 範囲型、GiST、排他制約などに依存する部分は、MySQLなどへの移行時に再設計が必要になる。
- PostgreSQLを使用できないホスティング先には配置できない。
- PostgreSQL固有の挙動を含むため、単純なSQLiteテストだけでは検証を完結できない。

## 将来見直す条件

- 配置先がPostgreSQLをサポートせず、配置先を変更するよりDB移行の方が合理的である。
- 採用先や共同開発チームの標準DBMSがMySQLなどに固定され、統一による運用上の利益が固有機能の利益を上回る。
- 端末内で完結するオフラインアプリへ目的が変わり、同時アクセスを扱うDBサーバーが不要になる。
- 単一PostgreSQLでは満たせない地理分散や可用性要件が、実測と運用要件によって確定する。
