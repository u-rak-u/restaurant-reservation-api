# ADR-0019: スタッフ認証情報・ログイン制限・セッションを分離する

## 状態

採用済み（2026-08-27、同日更新）

## 背景

ADR-0018で、店舗所属の個別スタッフアカウントと、管理者による限定管理操作をMVPへ含めることを決めた。無効化、ログインID・ロール・パスワードの変更では全セッションを即時失効させ、初回設定とパスワード再設定も店舗内で安全に行う必要がある。

スタッフの識別情報、パスワードハッシュ、ログイン失敗回数、端末ごとのセッションは、更新頻度、機密性、件数、保持期間が異なる。保存境界に加え、ハッシュ方式、初回秘密情報の受け渡し、一時停止方式、セッション形式と期限を決める。

## 判断対象

- パスワードハッシュとログイン失敗状態を `staff_accounts` へ保存するか分離するか
- 初回パスワードと管理者による再設定をどう受け渡すか
- パスワードハッシュ方式と入力規則
- ログイン失敗を永久ロック、一律停止、段階的停止のどれで扱うか
- JWTとサーバー側セッションのどちらを認証の正とするか
- セッション期限、再認証および一括失効をどう扱うか
- 再認証時のトークン交換と最終利用日時をどう整合させるか

## 検討した選択肢

### 1. すべてを `staff_accounts` へ保存する

- テーブル数と単純なログイン検索のJOINを減らせる。
- スタッフ一覧で頻繁に読む識別情報とパスワードハッシュが同じ行にあり、通常の更新や応答へ誤って混入する危険が増える。
- 失敗のたびにアカウント行を更新し、1人に複数あるセッションを同じ行で自然に表せない。

### 2. パスワードと失敗状態をまとめ、セッションだけ分離する

- セッションの1対多を正しく表しつつ、認証関連テーブルを1つ減らせる。
- 低頻度のハッシュ更新と高頻度の失敗回数更新が同じ行で競合し、失敗状態だけを削除または期限リセットしにくい。

### 3. 資格情報、設定トークン、失敗状態、セッションを用途別に分離する

- 機密データを通常のスタッフ取得から隔離し、無効化、再設定、成功時リセット、複数端末失効をそれぞれのライフサイクルで扱える。
- テーブル、外部キー、トランザクション、統合テストが増える。

### 4. 署名付きJWTを認証の正とする

- APIがセッション表を毎回照合せず、複数インスタンスへ配布しやすい。
- 発行済みJWTのロールや有効状態が古くなり、即時失効には拒否リスト、短い有効期限またはセッション世代が別途必要になる。この要件では結局サーバー側状態が必要になる。

## 採用した案

- `staff_accounts` には業務上の識別情報と管理状態だけを置く。
- 現在のパスワードを `staff_password_credentials`、一回限り設定トークンを `staff_password_setup_tokens`、連続失敗状態を `staff_login_throttles`、端末ごとのセッションを `staff_sessions` へ分離する。
- 有効なスタッフは設定待ちまたは利用可能な資格情報を1件持ち、無効または匿名化済みのスタッフは資格情報を持たない。無効化では古いハッシュを削除し、再有効化では新しいパスワード設定を要求する。
- パスワードはArgon2idのPHC形式で保存する。最低条件を `m=19456 KiB`、`t=2`、`p=1` とし、デプロイ先でおおむね250ミリ秒、1秒未満になる範囲へ強化する。MVPではpepperを使用しない。
- パスワードは15文字以上128文字以下とし、Unicode、空白、記号を許可する。文字種の組み合わせ、定期変更、正規化、黙示的な切り捨てを採用しない。
- 初回設定、管理者による再設定、再有効化では32バイトの一回限りトークンを発行し、DBへSHA-256ダイジェストだけを最大60分保存する。管理者が本人のパスワードを決めたり、後から平文を再表示したりしない。
- ログイン失敗は5回目から1分、2分、4分、8分、最大15分の段階的停止とする。停止中の試行で期限を延長せず、成功または最後の失敗から30分経過で状態を削除・リセットする。
- 公開ログイン応答では、ログインID不存在、無効、パスワード設定待ち、一時停止、パスワード不一致を区別しない。アカウント単位に加え、API・基盤側で送信元と全体のRate Limitを設ける。
- 暗号学的乱数32バイトから作る不透明なCookieトークンを使用し、DBにはSHA-256ダイジェストだけを保存するサーバー側セッションを認証の正とする。
- セッションはアイドル60分、絶対12時間で失効する。更新前のDB時刻がいずれかの期限へ到達した時点で拒否し、最終利用日時を更新しない。スタッフ管理の変更操作は最後のパスワード確認から10分以内だけ許可する。
- 有効なセッションで認証を通過したユーザー操作APIへのリクエストは、後続の業務処理の成否を問わずリクエストごとに最終利用日時をDB時刻へ更新する。静的ファイル、ヘルスチェック、自動ポーリングなどの非操作系通信は更新対象外とし、クライアント申告ではなくサーバー側のAPI用途で区別する。成功した再認証では、対象セッション行をロックしてトークンダイジェストを交換し、再認証日時と最終利用日時を同じDB時刻へ更新する。
- 再認証では同じセッションID、作成日時、絶対失効日時を維持する。交換前のトークンを直ちに無効化しつつ、再認証によって12時間の絶対期限を延長しない。
- ログインID、基本ロール、パスワードの変更、無効化、再有効化では全端末のセッションを同じトランザクションで失効させる。認可時はセッション発行時のロールではなく、現在のスタッフ状態と当日任命を確認する。
- 通常の管理操作では、店舗に有効かつパスワード設定済みの管理者を最低1件残す。管理者は自分に管理者用の再設定を実行せず、現在のパスワードを確認する本人用変更操作を使用する。すべての管理者がログインできない場合だけ非公開復旧手順を使用する。

## 採用理由

スタッフ情報の通常取得からハッシュとトークンダイジェストを隔離し、失敗のたびに業務上のアカウント行を書き換えない。セッションの1対多も正規化された関連として扱える。無効化時に資格情報自体を削除すれば、管理フラグだけに依存せず古いパスワードを利用不能にできる。

Argon2idはパスワード総当たりへ計算量とメモリ量の両方を要求し、PHC形式はソルトと計算条件をハッシュごとに保持できる。一回限りトークンは十分なエントロピーを持つため高速なダイジェスト照合ができ、管理者へ一時パスワードを共有させずに済む。

サーバー側セッションなら、退職、権限変更、漏えい疑いの時点で複数端末を即時失効できる。JWTに即時失効用の状態を追加するより構成が単純であり、単一店舗MVPではPostgreSQL参照の負荷も十分小さい。

再認証時にトークンを交換すれば、共有端末や盗まれた古いCookieがその後も同じセッションとして使われ続ける時間を短くできる。同じ行を更新して作成日時と絶対期限を維持するため、再認証の繰り返しによる実質的な無期限セッションにもならない。再認証日時だけを進めず最終利用日時も同じ時刻へ更新することで、DBの日時順序と実際の利用事実も一致する。

## 実用性評価

40席の単一店舗では、スタッフは数十人、同時セッションも多くて数十件程度と見込まれる。ハッシュ照合はログインと再認証時だけであり、通常リクエストのセッションダイジェスト検索はUNIQUEインデックスで処理できる。ユーザー操作APIごとに `last_seen_at` を更新してもこの規模ではPostgreSQLの書き込み負荷は十分小さいと見込むが、運用開始前の負荷試験で更新頻度、行ロック待ち、WAL量を測定する。

個人別アカウント、12時間の絶対期限、60分のアイドル期限は1シフトの操作回数を抑えつつ、共有端末の放置リスクを限定する。ただし、画面を離れる際の明示的なログアウトと端末自体の画面ロックは別途必要である。更新前のDB時刻で期限到達を拒否してから最終利用日時を更新するため、60分境界を正確に保てる。

同じセッションからの並行したユーザー操作では最終利用日時の更新が同じ行へ集中するため、短い認証更新トランザクションとインデックス検索を用い、業務トランザクションの間ずっとセッション行をロックしない。並行再認証では行ロック後に現在トークンを再検証し、一方が交換した旧トークンによる後続処理を拒否する必要がある。実測で問題が出た場合は、正確な60分期限を維持できる外部セッションストアなどを再検討する。

段階的停止は総当たりを遅らせるが、分散した送信元が特定スタッフへ試行を続ける業務妨害を完全には防げない。IPだけを厳しく制限すると店舗の共有回線から全員がログインできなくなるため、アカウント、送信元、店舗、全体の複数軸で測定し、運用開始前に閾値を負荷試験する必要がある。

DBを取得した攻撃者に対してArgon2idは解析を遅くするが、弱いパスワードの推測を不可能にはしない。pepperを省くMVP判断は、DBとアプリケーション秘密情報を分離管理できる本番基盤が整った場合に再評価する。本番運用にはHTTPS、CSRF対策、安全なCookie属性、秘密情報をログへ出さない復旧手順、認証イベントの監視が必要である。

## デメリット

- 4つの認証用テーブルと、複数テーブルを原子的に変更するサービス処理・統合テストが増える。
- パスワード再設定を開始すると以前のパスワードを使えず、設定トークンを失った場合は管理者による再発行が必要になる。
- メールを取得しないため、初回・再設定トークンを店舗内の安全な手段で本人へ渡す運用が必要になる。
- PostgreSQL障害時は既存セッションを照合できず、認証済み機能も利用できない。
- ユーザー操作APIごとに同じセッション行を更新するため、操作量が想定を超えた場合は書き込み量と同一行競合が増える。
- 60分のアイドル期限は、予約管理画面を長時間操作しなかったスタッフへ再ログインを要求することがある。
- 再認証のたびにCookieトークンが変わるため、レスポンス喪失時は新しいCookieを受け取れず再ログインが必要になる場合がある。

## 将来見直す条件

- MFA、WebAuthn、パスキー、OIDCまたは従業員ディレクトリを導入する。
- 複数店舗・多数インスタンス化により、セッション参照またはRate LimitのDB負荷が実測上の問題になった。
- DB外の秘密管理とpepper更新時の安全なパスワード移行手順を用意できた。
- 店舗端末の運用調査で、60分・12時間・再認証10分が業務を妨げる、または長すぎることが判明した。
- セキュリティ基準、依存ライブラリまたはデプロイ先の性能変化により、Argon2id条件を更新する必要が生じた。
