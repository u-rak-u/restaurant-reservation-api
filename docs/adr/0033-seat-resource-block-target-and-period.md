# ADR-0033: 席資源ブロックを対象選択付きの半開期間として保存する

## 状態

採用済み（2026-09-04）

## 背景

物理テーブルの故障や汚損は、そのテーブルをどの配置場所へ動かしても続く。一方、雨漏りや通路障害は配置場所側の問題であり、別のテーブルを置いても使用できない。ADR-0028では、これらの一時的な使用不能を席構成マスターの恒久廃止と分離し、物理テーブルまたは配置場所と期間を参照する席資源ブロックとして保存する方針を決めた。

DB設計では、2種類の対象を同じテーブルと別テーブルのどちらで表すか、終了時期が未定の期間をどう表すか、同じ対象へ重複したブロックを作成できるかを具体化する必要がある。

## 判断対象

- 物理テーブルと配置場所のブロックを同じテーブルへ保存するか。
- 1件のブロックが参照できる対象をどう制約するか。
- ブロックの開始、終了未定および境界時刻をどう表すか。
- 同じ対象に対する期間重複をどこで拒否するか。

## 検討した選択肢

### 1. 対象種別と対象IDを持つ汎用的な関連にする

- 列数が少なく、将来ほかの対象種別を追加しやすい。
- 対象IDに通常の外部キーを設定できず、存在確認と店舗一致がアプリケーションへ依存する。

### 2. 物理テーブル用と配置場所用のブロックテーブルを分ける

- 各対象をNOT NULLの外部キーで表せる。
- 同じ期間制約、検索、開始・解除処理および監査関係が2テーブルへ重複する。

### 3. 1つのテーブルに2つのNULL許容対象列を置き、どちらか一方だけを必須にする

- 共通のライフサイクルと期間制約を1テーブルで扱える。
- CHECK制約と対象別の排他制約が必要になる。

## 採用した案

- `seat_resource_blocks` を独立したテーブルとして作り、UUIDv7の主キー、店舗、物理テーブルまたは配置場所、開始日時および終了日時を保存する。
- `physical_table_id` と `placement_location_id` はNULL許容とし、CHECK制約によって必ずどちらか一方だけを指定する。対象種別を表す列は重複して保存しない。
- 対象参照は `store_id` と組にした複合外部キーにし、別店舗の資源を関連付けられないようにする。削除動作は `ON DELETE RESTRICT` とする。
- ブロック期間は `tstzrange(starts_at, ends_at, '[)')` で表す。開始を含み終了を含まない半開区間とし、`ends_at` がNULLなら将来に上限のない期間とする。
- `ends_at` がある場合は `starts_at < ends_at` をCHECK制約で保証し、長さ0または逆転した期間を拒否する。
- `btree_gist` と対象別のGiST排他制約を使用し、同じ物理テーブル同士または同じ配置場所同士で、取消されていないブロック期間が重なる行を拒否する。物理テーブルのブロックと配置場所のブロックは別の資源を表すため、両者の期間重複は許可する。
- 時刻が一致する隣接期間は重複としない。例えば10時から11時のブロックがあれば、11時から同じ対象を使用または別のブロックを開始できる。
- 終了日時が到来したブロックは、定期処理で状態を変更しなくても候補除外の対象外になる。終了未定のブロックは、解除操作がDBサーバー時刻を終了日時として設定するまで、将来すべての重なる割り当て候補から除外する。
- 終了済みブロックは履歴として保持し、通常操作では物理削除しない。具体的な保持・削除方針はDB-49で全体を再確認する。
- 新しいブロックは有効な席構成マスターだけを対象にする。ブロック開始処理は対象を再取得して恒久廃止済みでないことを確認する。恒久廃止時は現在または将来のブロックを先に解消し、終了済みブロックの参照は残す。
- ブロック開始時に既存の席配置を変更しない。対象期間と重なる新しい割り当ての拒否はDB-30、開始・解除権限、理由、監査、予定開始前の取消および既存配置への警告はADR-0034を正とする。

## 採用理由

物理テーブルと配置場所は対象こそ異なるが、「一定期間だけ使用不能にし、終了後も履歴を残す」というライフサイクルは同じである。1テーブルにまとめて外部キーの排他選択をCHECK制約で保証すれば、型と参照整合性を失わず、開始・解除処理と履歴検索を共通化できる。

半開区間なら、ブロック終了時刻と次の利用開始時刻が一致する正常な引き継ぎを重複としない。NULL上限は修理完了時期が分からない現場運用を直接表せる。アプリケーションの事前確認に加えて排他制約を置くことで、並行した開始操作から同じ対象に重複行が作られることもDBで防止できる。

## 実用性評価

40席・15テーブルの単一店舗では、対象別のGiST排他制約と期間重複検索の負荷は小さい。テーブル故障と場所の危険を区別でき、終了予定が判明している停止と未定の停止を同じ画面・処理で扱えるため、日常的な故障対応に利用できる。

同じ対象の重複ブロックを許可しないことで、片方だけを解除して使用可能と誤認する事態を避けられる。一方、既にブロック中の対象へ別の原因が加わった場合は、現在のブロックの解消条件としてまとめて管理する必要がある。理由と変更履歴の扱い、解除忘れ、影響予約への警告はADR-0034で補完する。

## デメリット

- 2つのNULL許容外部キーと排他的なCHECK制約が必要になる。
- 対象ごとに部分GiST排他制約を1つずつ定義する必要がある。
- PostgreSQLの範囲型、`btree_gist` および排他制約へ依存するため、他DBMSへの移行時は再設計が必要になる。
- 終了未定のブロックは、解除忘れによって将来の予約可能数を下げ続ける。
- ブロック行だけでは、既存配置の現場対応や複数原因の管理を完結できない。

## 将来見直す条件

- フロア、エリアまたは任意の席集合を一括でブロックする必要が生じる。
- 同じ対象に対する複数の独立した故障・安全上の理由を、別々の担当者と解消期限で同時管理する必要が生じる。
- 修理依頼、業者、費用、写真などを持つ設備保全機能へ拡張する。
- 複数店舗化や大量の配置場所により、期間検索と排他制約の性能が問題になる。
