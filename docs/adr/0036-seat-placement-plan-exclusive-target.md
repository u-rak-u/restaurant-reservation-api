# ADR-0036: 席配置計画は予約または個別の予約なし利用の一方だけを対象にする

## 状態

採用済み（2026-09-04）

## 背景

通常予約、貸切予約および予約なし利用は、席の配置と占有期間を世代付きの席配置計画で管理する。通常予約と貸切予約は共通の `reservations` を集約ルートとする一方、予約なし利用は `walk_in_visits` として予約から分離している。

席配置計画が対象を持たない状態、予約と予約なし利用の両方を対象にする状態、または同じ対象へ複数の計画が作られる状態を許すと、現在世代、競合判定および保持・削除の所属先が一意に決まらない。型とIDだけを持つ汎用的な参照では、通常の外部キーによって対象の存在と店舗一致を保証できない。

## 判断対象

- 予約用と予約なし利用用の席配置計画を同じテーブルで扱うか。
- 1件の計画が参照できる対象をどう制約するか。
- 1つの対象に複数の計画が作られることをどう防ぐか。
- 親である予約または予約なし利用にも計画が必ず存在することをどう保証するか。
- 予約なし利用系列と個別の予約なし利用のどちらを参照するか。

## 検討した選択肢

### 1. 対象種別と対象IDを持つ汎用的な参照にする

- 対象列を共通化し、将来の対象種別を追加しやすい。
- 対象IDの参照先が種別によって変わるため、通常の外部キーで存在、店舗一致および一意性を保証できない。

### 2. 予約用と予約なし利用用に席配置計画テーブルを分ける

- 各計画の対象外部キーをNOT NULLにできる。
- 世代、席割り当て、現在世代切り替え、競合判定および自動再配置の共通処理が2系統になる。

### 3. 1つの計画テーブルに2つのNULL許容外部キーを置き、一方だけを必須にする

- 席配置の世代管理を共通化しながら、各対象へ通常の外部キーを設定できる。
- 排他的なCHECK、対象ごとの一意制約および親側の存在検査が必要になる。

## 採用した案

- `seat_placement_plans` を共通の席配置計画テーブルとし、UUIDv7の `id`、`store_id`、NULL許容の `reservation_id` と `walk_in_visit_id` を持たせる。
- `CHECK ((reservation_id IS NOT NULL) <> (walk_in_visit_id IS NOT NULL))` により、予約または予約なし利用のどちらか一方だけを必須にする。対象種別列は重複して保存しない。
- `(store_id, reservation_id)` から `reservations (store_id, id)`、`(store_id, walk_in_visit_id)` から `walk_in_visits (store_id, id)` へ複合外部キーを設定し、別店舗の対象へ計画を関連付けられないようにする。具体的な `ON DELETE` はDB-49で確定する。
- `reservation_id IS NOT NULL` を条件とする予約用の部分UNIQUEインデックスと、`walk_in_visit_id IS NOT NULL` を条件とする予約なし利用用の部分UNIQUEインデックスを設け、各対象の計画を最大1件にする。
- 通常予約と貸切予約は、種別詳細ではなく共通の `reservations.id` を参照する。予約種別と種別詳細の整合性は予約集約側の既存制約を正とし、席配置計画に予約種別を重複保存しない。
- 予約なし利用は `walk_in_visit_series.id` ではなく、個々の `walk_in_visits.id` を参照する。誤終了または誤中止後の占有継続では、同じ系列へ追加される新しい利用区間ごとに別の席配置計画を作る。
- 通常受付、貸切作成、予約なし利用受付および占有継続登録では、対象、席配置計画、第1世代、席割り当ておよび必要な監査記録を同じトランザクションで作成する。一部だけを確定しない。
- 予約または予約なし利用が存在するのに席配置計画がない状態も、トランザクションのコミット時に検査する `DEFERRABLE INITIALLY DEFERRED` な制約トリガーで拒否する。作成途中の挿入順は固定せず、コミット時には対象ごとにちょうど1件を要求する。
- 計画の `store_id` と対象参照は作成後に変更しない。予約から予約なし利用への付け替え、別予約への付け替え、および既存計画の再利用を通常操作で許可しない。
- 席配置計画の現在世代参照と世代側の外部キー構成はDB-26、削除と保持期限の連動はDB-44とDB-49で確定する。

## 採用理由

予約と予約なし利用では作成主体と状態遷移が異なるが、席配置の世代、物理テーブルと配置場所、占有期間および自動再配置の仕組みは共通である。1テーブルに2本の型付き外部キーを置けば、共通処理を維持しながら多相IDによる参照整合性の喪失を避けられる。

計画側のCHECKと部分UNIQUEインデックスは、対象なし、対象の二重指定および複数計画を直接拒否する。親側の遅延制約トリガーも併用することで、計画を作り忘れた予約または予約なし利用をコミットできず、「最大1件」だけでなく「ちょうど1件」を保証できる。

予約なし利用系列は保持・削除と継続関係の単位であり、1系列に複数の利用区間が存在し得る。個別利用を参照すれば、各区間の実際の占有と席移動履歴を別の現在世代として扱える。

## 実用性評価

通常の予約・受付処理は対象と計画を最初から同じトランザクションで作成するため、遅延検査による追加負荷は小さい。部分UNIQUEインデックスにより、同時または再送による計画の二重作成もDBで拒否できる。

1件の予約または予約なし利用から計画を一意に取得できるため、当日一覧、空席検索、影響警告および保持期限処理で「どの計画が正か」を選ぶ必要がない。40席規模では2本の部分UNIQUEインデックスとコミット時検査が性能問題になる可能性は低い。

一方、複数テーブルを同時作成するため、単純な親行INSERTだけでは予約や受付を成立させられない。アプリケーションサービス、制約トリガー、AlembicマイグレーションおよびPostgreSQL統合テストを一貫させる必要がある。

## デメリット

- 2つのNULL許容外部キーと排他的なCHECK制約が必要になる。
- 計画側の制約だけでは親に計画が存在することを保証できず、複数テーブルを確認する遅延制約トリガーが必要になる。
- 予約または予約なし利用だけを単独で作成する一時的な処理をコミットできない。
- 予約なし利用の系列全体の配置履歴を取得するには、系列内の各利用と席配置計画を結合する必要がある。

## 将来見直す条件

- 予約や予約なし利用以外に、待ち行列、イベントまたは保守作業など、席配置計画を持つ対象が増える。
- 1つの利用が複数の独立した同時配置計画を持つ要件が生じる。
- 予約なし利用を系列単位の単一利用セッションとして再設計し、個別区間ごとの計画が不要になる。
- 遅延制約トリガーの運用・性能負担が実測で問題になる。
