# ADR-0031: 物理テーブルの固定・可動を固定配置場所の有無で表す

## 状態

採用済み（2026-09-03）

## 背景

物理テーブルは店舗に実在する什器、配置場所は時間帯ごとにテーブルを置ける論理的位置として分離している。可動テーブルは同じ移動可能エリア内の複数の配置場所を利用できる一方、固定ボックス席や独立固定席は常に特定の配置場所で利用しなければならない。

空席検索、通常予約、予約なし利用および貸切範囲の収容人数判定には、物理テーブルごとの正の定員が必要である。また、固定・可動の区分と固定配置場所を別々の列で保存すると、「固定だが固定場所がない」「可動だが固定場所がある」という矛盾を作り得る。

## 判断対象

- 物理テーブルの定員をどの型と制約で保存するか。
- 固定・可動を専用の区分列で表すか、固定配置場所の有無から求めるか。
- 固定配置場所と物理テーブルの店舗・移動可能エリア一致をどう保証するか。
- 固定配置場所を別の物理テーブルが利用できるか。

## 検討した選択肢

### 1. 固定・可動の区分列と固定配置場所を別々に持つ

- 区分を直接検索、表示できる。
- 区分列と固定配置場所の組み合わせをCHECK制約などで同期させる必要がある。
- 同じ業務上の事実を2か所へ保存するため、追加する区分が固定と可動だけであるMVPには冗長である。

### 2. NULL許容の固定配置場所を持ち、その有無から固定・可動を求める

- 固定テーブルには必要な場所を必ず保存でき、可動テーブルには固定場所を持たせない構造になる。
- 区分と場所が食い違う状態を作らずに済む。
- 固定・可動の検索ではNULL判定が必要になる。

### 3. 固定テーブルだけを別テーブルまたは関連テーブルへ分離する

- 固定関係を独立した行として表現できる。
- 固定かどうかを判定するたびに追加の結合が必要になる。
- 固定関係に独自の履歴や属性を持たないMVPでは、テーブルを増やす利点が小さい。

## 採用した案

- `physical_tables` に `capacity smallint NOT NULL CHECK (capacity > 0)` を持たせる。
- 定員は物理テーブルだけを正とし、配置場所へ定員を重複保存しない。
- 通常予約の12名上限は利用単位の業務ルールであり、物理テーブル自体の定員上限ではないため、`capacity <= 12` は要求しない。
- `physical_tables` にNULL許容の `fixed_placement_location_id` を持たせる。
- `fixed_placement_location_id IS NULL` を可動、`IS NOT NULL` を固定とし、`is_fixed`、`is_movable` または固定・可動の列挙型を追加しない。
- 固定配置場所は物理テーブルと同じ店舗・同じ移動可能エリアに属することを、`store_id`、`movement_area_id`、配置場所IDを組にした複合外部キーで保証する。
- 1つの配置場所を複数の固定テーブルへ対応付けないよう、NULL以外の `fixed_placement_location_id` を一意にする。
- 固定テーブルの席割り当てでは固定配置場所だけを許可する。固定配置場所は対応する固定テーブル専用とし、別の固定テーブルまたは可動テーブルの割り当て先にしない。
- 可動テーブルは固定配置場所として確保されていない、同じ店舗・同じ移動可能エリアの配置場所だけへ割り当てられる。席割り当て時の具体的な制約はDB-28で確定する。
- 初期データでは、`T01`から`T10`を定員2・固定配置場所なし、`T11`と`T12`を定員4・それぞれ`F-01`と`F-02`へ固定、`B01`から`B03`を定員4・それぞれ`X-01`から`X-03`へ固定する。
- 定員、所属エリアまたは固定配置場所を後から変更する条件と、既存の将来予約への影響はDB-23Aで確定する。MVPでは席構成マスターの汎用管理APIを提供しない。

## 採用理由

固定テーブルには利用可能な配置場所を1つ指定する必要があるため、その参照自体を固定・可動の判定にも使えば、区分列との矛盾を作らずに済む。固定・可動の判定は単純なNULL判定であり、40席・15テーブルのMVPでは検索上の負担にならない。

定員を実在する什器の属性に限定すると、可動テーブルが時間帯によって場所を変えても収容人数は変わらず、貸切範囲でも物理テーブルIDの和集合から一貫して収容人数を算出できる。通常予約の人数上限とは分離するため、将来、大きな固定テーブルを追加してもスキーマ変更を必要としない。

## 実用性評価

初期レイアウトでは可動テーブル10台と固定テーブル5台の対応が明確であり、店舗スタッフは固定席を移動候補から除外した状態で自動配置を利用できる。固定場所を別テーブルが利用できない条件まで適用すれば、論理上は同じ場所へ2台の什器を置く誤配置も防げる。

一方、この設計が表すのは予約または予約なし利用の時間帯ごとの配置計画であり、空き時間中の物理テーブルの現在位置や、スタッフが移動作業を完了したかは追跡しない。MVPでは予約時間までに現在の配置計画をスタッフが実現する運用を前提とし、実店舗で移動漏れが問題になる場合は準備作業の確認機能を別途検討する。

## デメリット

- 固定・可動を表示する際に `fixed_placement_location_id` のNULL判定が必要になる。
- 同一店舗・同一エリアを保証する複合外部キーのため、配置場所側に対応する複合UNIQUE制約が必要になる。
- 固定場所を可動テーブルの候補から除外する条件は、物理テーブル単体のCHECK制約だけでは保証できず、席割り当て設計と連携する必要がある。
- 定員に店舗固有の上限を設けないため、将来の管理APIでは店舗規模に対して不自然な値を入力しないための確認が必要になる。

## 将来見直す条件

- 補助椅子などにより、通常定員と拡張定員を分ける必要が生じる。
- 時間帯または営業形態によって同じ物理テーブルの定員が変わる。
- 半固定、複数の許可場所、エリア間移動など、固定と可動の2区分では表せない運用を導入する。
- 物理テーブルの現在位置または移動作業の開始・完了をリアルタイムに管理する。
