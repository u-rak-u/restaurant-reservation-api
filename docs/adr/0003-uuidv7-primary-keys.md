# ADR-0003: 内部主キーにUUIDv7を使用する

## 状態

採用済み（2026-08-21）

## 背景

データベース設計を開始するにあたり、すべてのテーブルへ影響する内部主キーの形式を先に決める必要がある。

このシステムは単一PostgreSQLのMVPであり、連番主キーでも規模上は十分である。一方、スタッフAPIが内部IDを受け取る場合、連番IDは隣接値を容易に推測でき、オブジェクト単位の認可漏れがあったときに多数の対象を列挙されやすい。

公開予約には内部主キーとは別に、予約番号、予約確認コード、チェックイントークンが存在する。予約番号は後続のADR-0015で店舗単位の12桁に確定した。したがって、主キーを公開資格情報として使わず、識別子の推測困難性と認可を別々に設計する必要がある。

## 判断対象

独立したエンティティの内部主キーに連番整数、UUIDv4、UUIDv7のどれを使用し、従属データへどのように適用するかを決定する。

## 検討した選択肢

### 1. `bigint GENERATED ALWAYS AS IDENTITY`

- 8バイトであり、主キーと外部キーのインデックスを小さくできる。
- 単一DBでの生成、結合、調査が単純である。
- 連番をAPIへ出すと隣接する有効IDを容易に推測できる。
- 将来、独立した複数DBで生成したデータを統合する場合は、ID範囲の調整または変換が必要になる。

### 2. UUIDv4

- ランダムで推測しにくく、DBの外でも生成できる。
- 時系列順にならず、今回のPostgreSQL 18ではUUIDv7を直接利用できるため、積極的に選ぶ理由が少ない。

### 3. UUIDv7

- 作成時刻に基づく順序とランダム部分を持ち、連番のように隣接IDを列挙できない。
- PostgreSQL 18の組み込み `uuidv7()` で生成でき、追加拡張を必要としない。
- 独立した環境で生成しても衝突しにくい。
- 16バイトであり、`bigint`より主キー、外部キー、インデックスが大きくなる。
- 作成時刻に近い情報を値から読み取れるため、UUID自体を秘密情報にはできない。

### 4. 内部連番と外部公開UUIDの二重管理

- 内部の結合を`bigint`に保ちながら、APIでは推測困難なUUIDを使用できる。
- すべての公開対象へ追加列と一意制約が必要になり、今回の規模では二重の識別子管理が複雑さに見合わない。

## 採用した案

- 独立した同一性を持つエンティティの代理主キーへUUIDv7を使用する。
- PostgreSQL 18の `uuidv7()` を列のデフォルト値としてDB側で生成する。
- 一対一の詳細、世代、純粋な関連は、親UUIDまたは親UUIDと世代番号などの複合主キーを使用する。
- 業務上の作成日時はUUIDから導出せず、タイムゾーン付き日時列へ明示的に保存する。
- UUIDは顧客向け資格情報、認証、認可、冪等性キーとして流用しない。
- APIではUUIDが推測困難でも、所属店舗、ロール、対象状態のオブジェクト単位認可を必ず行う。

## 採用理由

このプロジェクトはPostgreSQL 18を使用するため、追加依存なしで時系列順のUUIDv7を生成できる。単一店舗40席では`bigint`との差による保存量と性能の不利益は小さく、連番による機械的な列挙を難しくする追加防御の方が有用と判断した。

ポートフォリオとしても、推測困難なIDを採用しながら、それを認可の代替とせず、異なる店舗の有効なIDを使った認可テストまで説明できる。

## デメリット

- `bigint`よりすべての主キー、外部キー、インデックスが大きくなる。
- ログや手作業でのID確認が長くなり、口頭伝達に向かない。
- PostgreSQL 18の組み込み生成へ依存するため、旧バージョンまたは別DBへの移行時に生成方法の変更が必要になる。
- DBで生成する間は、INSERT前にIDが確定していることを前提にしたアプリケーション設計を採用できない。
- UUIDv7の時刻部分から生成時刻に近い情報を推測できる。

## 将来見直す条件

- 実測したテーブル件数とインデックスサイズによって、UUID主キーが主要クエリの性能要件を満たさない。
- PostgreSQL 18より前のバージョンまたはUUIDv7を生成できないDBへ移行する。
- 外部システムとの連携で、アプリケーション側における永続化前のID生成が必要になる。

見直す場合も、公開識別子を認可の代わりにせず、すべての対象操作でオブジェクト単位の認可を維持する。
