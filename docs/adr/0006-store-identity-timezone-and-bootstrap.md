# ADR-0006: 店舗の識別・タイムゾーン・初期データ方針

## 状態

採用済み（2026-08-24）

## 背景

MVPは単一店舗を対象とするが、予約、スタッフ、営業時間、席配置、監査記録などの主要な業務データは店舗との所属関係を持つ。店舗をアプリケーション設定だけで表現すると、これらの関連をDBで保証できず、将来の複数店舗化では広範囲なテーブル変更が必要になる。

また、予約日時は絶対的な瞬間として保存する一方、営業時間、営業日、予約受付期限、日次削除ジョブなどは店舗のローカル日時で判断する。このため、固定UTCオフセットではなく、地域の時間規則を識別できるタイムゾーンを店舗に保持する必要がある。

汎用的な店舗管理CRUDを提供しないMVPでも、最初の店舗行を安全かつ複数の開発環境で再現可能に作成する方法が必要になる。

## 判断対象

- 店舗をDBエンティティとして作成するか。
- 内部主キー以外の安定した店舗識別子を持つか。
- 店舗タイムゾーンをどの形式で保存するか。
- 単一店舗という制限をDB制約にするか、アプリケーションの提供範囲にするか。
- 初期店舗をマイグレーション、API起動時処理、明示的な初期化コマンドのどれで作成するか。

## 検討した選択肢

### 1. 店舗テーブルを作らず、設定だけで単一店舗を表す

- 初期実装は最も少なくなる。
- 予約、スタッフ、営業時間、席配置の所属店舗を外部キーで保証できない。
- 複数店舗化すると、多数のテーブルへ店舗IDを追加して既存データを移行する必要がある。

### 2. 店舗テーブルを作り、DBで1行だけに制限する

- 単一店舗という現在の前提をDBでも強制できる。
- 2店舗目を追加するときに制約の撤去と、単一行を仮定した処理の見直しが必要になる。
- 「MVPで提供しないこと」を永続的なデータ制約として表す利益が小さい。

### 3. 固定UUIDの店舗行をAlembicマイグレーションで登録する

- すべての環境で同じ店舗UUIDを使用でき、マイグレーションだけで起動準備が完了する。
- 店舗名やタイムゾーンのような環境固有データがスキーマ変更履歴へ混ざる。
- 本番環境の値を変更するために、過去のマイグレーション編集または追加のデータマイグレーションが必要になりやすい。

### 4. API起動時に不足する店舗行を自動作成する

- 初回起動の手順が少なくなる。
- 通常のAPI起動が暗黙のDB書き込みを伴い、設定ミスや複数ワーカー起動時の問題を診断しにくい。
- 本番データをいつ、どの設定で作成したかが運用手順から見えにくい。

### 5. 安定した店舗コードを持ち、明示的な初期化コマンドで登録する

- 環境ごとにUUIDが異なっても、`main` などのコードで対象店舗を安定して選択できる。
- スキーマ変更と環境固有の初期データを分離できる。
- コマンドを冪等にすれば、初回かどうかを人が判断せず安全に再実行できる。
- マイグレーションとは別に、初期化コマンドを実行する手順が1つ増える。

## 採用した案

- 店舗を `stores` テーブルとして作成する。
- 内部主キーにはDB生成のUUIDv7を使用する。
- 設定から参照する安定した `code`、表示用の `name`、IANAタイムゾーン名を保存する `timezone`、`created_at`、`updated_at` を持つ。
- `code` は一意かつ原則不変とし、小文字英数字をハイフンで区切った1文字以上50文字以下の形式にする。
- `name` は前後の空白を除いて1文字以上100文字以下、`timezone` は1文字以上64文字以下とする。
- タイムゾーンの実在確認は、初期化処理とアプリケーションでIANAタイムゾーンデータを使用して行う。
- 単一店舗はMVPのアプリケーション上の提供範囲とし、DBの行数制約にはしない。
- 顧客向けAPIは外部入力から任意の店舗を選ばせず、デプロイ設定の店舗コードから対象店舗を解決する。
- Alembicはテーブル構造と制約だけを管理し、環境固有の店舗行を登録しない。
- 初期店舗はマイグレーション後に明示的な初期化コマンドで作成し、API起動時には自動作成しない。
- 初期化コマンドは、対象コードがなければ作成し、同じ内容なら成功し、異なる内容なら上書きせずエラーにする。
- 開発環境の初期値は `main`、`サンプルレストラン`、`Asia/Tokyo` とする。

## 採用理由

単一店舗の段階から所属店舗を外部キーで表現すれば、予約やスタッフなどの整合性と認可範囲をDB設計へ反映できる。DBを1行に制限しなければ、MVPのAPI範囲を増やさないまま将来の複数店舗化に備えられる。

UUIDは内部参照に適しているが、環境ごとに生成値が異なる。人が設定しやすい不変の店舗コードを併用することで、UUIDを設定ファイルへコピーする作業を避けられる。

IANAタイムゾーン名は固定オフセットと異なり、地域ごとの夏時間や将来の時間規則変更を扱える。日本の単一店舗でも `Asia/Tokyo` を明示することで、サーバーやDBセッションのタイムゾーン設定に業務判定を依存させずに済む。

明示的な初期化コマンドは1手順増えるが、通常起動とデータ作成を分離できる。既存行を自動上書きしないため、別環境の設定や本番の店舗情報を誤って変更する危険も抑えられる。

## 実用性評価

この方式は単一店舗MVPで実用に耐える。利用者は店舗を選択する必要がなく、アプリケーションは一貫して設定済み店舗を使用できる。2つの開発環境で店舗UUIDが異なっても、同じ店舗コードを使えば手順を共通化できる。

本番では、初期化コマンドの実行をデプロイ手順へ明記し、対象環境、店舗コード、店舗名、タイムゾーンを実行前後に確認する必要がある。複数店舗化するときは、顧客が店舗を選択する方法、スタッフの所属変更、店舗コードの運用、店舗単位の設定分離を追加で設計する。

## デメリット

- 単一店舗MVPでも、すべての主要業務テーブルに店舗との関連が必要になる。
- マイグレーションに加えて、初期店舗作成コマンドを1回実行する必要がある。
- 店舗コードを変更しない運用が必要になる。
- タイムゾーン文字列の有効性を通常のDB制約だけでは完全に保証せず、初期化処理とアプリケーション検証にも依存する。
- DB自体は複数店舗行を保存できるため、MVPで2件目を作成させないことはAPIと運用手順で保証する。

## 将来見直す条件

- 複数店舗運用をMVP後の機能として実装する。
- 店舗コードの変更または公開URL用スラッグが必要になる。
- 店舗情報を管理画面から変更する汎用CRUDを実装する。
- 配置地域が増え、利用可能なタイムゾーン一覧や表示名の管理が必要になる。
- 初期データ作成をデプロイ基盤の標準的なシード機構へ統合する。
