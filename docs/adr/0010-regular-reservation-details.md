# ADR-0010: 通常予約の人数・予約期間・顧客コメント

## 状態

採用済み（2026-08-24）

## 背景

通常予約は、1名から12名、店舗ローカル時刻で10分単位の開始、標準利用時間90分という規則を持つ。予約時の人数と実際の来店人数は異なる可能性があり、欠員を受け入れても席を自動解放せず、増員は席と権限の条件を満たした場合だけ認める。

また、顧客は予約時に店舗への要望をコメントとして入力できる。コメントは任意だが、個人情報やアレルギーなどの重要事項が含まれる可能性があり、入力上限、表示時の安全性、保持期限が必要になる。

予約なし利用は予約番号、連絡先、資格情報を持たず、受付時点の人数と独自の状態遷移を使用するため、通常予約詳細へ混在させない。

## 判断対象

- 予約人数と実来店人数を同じ列で上書きするか、別々に保存するか。
- 実来店人数を来店時の一回限りの値にするか、遅れて来た参加者を反映できる累計人数にするか。
- 90分後の終了日時を都度計算するか、開始日時とともに保存するか。
- 10分単位をUTCの固定間隔で判定するか、店舗ローカル時刻で判定するか。
- 顧客コメントの長さ、正規化、禁止文字、保持期限をどうするか。

## 検討した選択肢

### 1. 予約人数を来店時に実人数で上書きする

- 現在値の列は1つで済む。
- 何名で予約して何名来店したかを直接比較できず、欠員、増員、席配置判断の根拠を監査履歴から復元する必要がある。
- 来店時の口頭確認に使用する予約人数が失われる。

### 2. 予約人数と実来店人数を分ける

- 予約内容と来店実績を明確に比較できる。
- 欠員があっても予約人数に基づく席を維持し、条件を満たした増員だけを予約人数へ反映できる。
- 親予約の状態と実来店人数の必須条件を横断的に検査する必要がある。

### 3. 開始日時だけを保存して終了日時を常に計算する

- 重複値を保存せず、90分規則との不一致が起きない。
- 空席、期間重複、一覧の終了時刻を扱うすべてのクエリで計算が必要になる。
- 将来の標準時間変更時に、既存予約へ適用済みの終了時刻を維持する設計を追加する必要がある。

### 4. 開始・終了日時を保存して90分をCHECKする

- 空席と時間範囲検索で両端を直接使用でき、既存予約へ適用した期間を保持できる。
- 2列の不一致を防ぐCHECK制約と、変更時に両方を更新する処理が必要になる。

## 採用した案

- `regular_reservation_details` に共有主キー、予約人数、実来店人数、開始・終了日時、顧客コメントを置く。
- `party_size` は1以上12以下とする。
- `actual_party_size` は来店前にはNULL、来店後は1以上 `party_size` 以下の累計受入人数とし、通常操作では減らさない。
- 欠員では予約人数と席配置を自動縮小しない。増員は権限、全予約を維持できる再配置、連結、転換時間を検証してから関連データを同じトランザクションで更新する。
- `starts_at` と `ends_at` をタイムゾーン付きで保存し、終了は開始の90分後とする。
- 開始は秒とマイクロ秒を0にし、店舗ローカル時刻で10分単位にする。店舗タイムゾーンが必要な検査は制約トリガーで行う。
- 日時変更では営業時間と全競合を同じトランザクションで再検証する。
- 顧客コメントは任意の最大500文字とし、空白だけをNULLへ正規化し、改行以外の不適切な制御文字を拒否する。
- コメントをHTMLとして扱わず、予約終了から90日後に削除する。
- 予約なし利用は別集約とし、同じ詳細テーブルへ保存しない。

## 採用理由

予約人数と実来店人数を分ければ、口頭確認、欠員、条件付き増員、利用実績を現在値として扱える。遅れて来た参加者を累計人数へ反映しても、退店によって減らさないため、リアルタイムの在店人数管理を予約APIへ持ち込まずに済む。

終了日時は開始日時から計算できるが、予約期間は空席、競合、営業時間、最終入店、席配置で繰り返し使用する。両方を保存し90分のCHECKを設けることで、検索の単純さと整合性を両立できる。

10分単位は顧客とスタッフが見る店舗ローカル時刻の規則である。UTCのエポック秒だけで判定すると、UTCオフセットが10分単位でない地域でローカル表示と一致しないため、店舗タイムゾーンで検証する。

## 実用性評価

この構成は、単一店舗MVPの予約作成、電話変更、来店確認、欠員、条件付き増員、当日一覧、空席検索に利用できる。列数とCHECKは少なく、1予約1詳細の主キーJOINも40席規模で負担になりにくい。

コメントは500文字あれば一般的な座席希望や簡潔な要望を記録できるが、店舗が見落とす可能性、入力誤り、対応不能な要望は残る。特にアレルギー対応をコメント送信だけで保証せず、電話確認の案内、スタッフ画面での視認性、HTMLエスケープを実装時に検証する必要がある。

実来店人数の更新は席占有を自動縮小しないため、人数が減っても空席販売数は増えない。一方、遅れて来た参加者の入力をスタッフが忘れる可能性があるため、最終人数を厳密な会計情報として扱わず、予約運用上の参考値として使用する。

## デメリット

- 予約人数と実来店人数の2列、および開始・終了日時の2列を同期して管理する必要がある。
- 親予約の状態と実来店人数の必須条件は、単一テーブルのCHECKだけでは表せず制約トリガーが必要になる。
- 10分単位の検査に店舗タイムゾーンの参照が必要になる。
- コメントには重要情報や個人情報が入力される可能性があり、アクセス制御、表示、削除を誤るリスクがある。
- 遅れて来た参加者の累計人数はスタッフ入力に依存し、実際の最終人数を完全には保証しない。

## 将来見直す条件

- 店舗または予約ごとに標準利用時間を変更できるようにする。
- 13名以上の予約を1件として扱う。
- 注文・会計・参加者単位の受付と連携し、正確な在店人数または最終人数が必要になる。
- 顧客コメントを要望種別、アレルギー情報、内部メモへ構造化する。
- 空席と競合検索で期間型または生成列を利用する方が有利であることを実測で確認する。
