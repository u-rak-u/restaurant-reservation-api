# ADR-0022: 予約なし利用を状態と操作日時を持つ独立した行として保存する

## 状態

採用済み（2026-08-27、2026-08-28更新）

## 背景

予約なし利用は、顧客が事前に作成する予約ではなく、認証済みスタッフが来店時に登録する。1名から4名は受付時に利用中、5名以上は席の準備中として開始し、利用開始、利用終了または準備中止へ進む。氏名、電話番号、予約番号、確認コードを持たず、予約の状態や資格情報も流用しない。

準備中・利用中の人数変更、準備遅延、予定終了後の時間超過、誤終了後の占有継続があるため、現在状態と操作日時が矛盾せず、通常経路と訂正経路を混同しない保存方式が必要である。

## 判断対象

- 予約なし利用を予約へ追加するか、独立したテーブルにするか
- 状態ごとに別テーブルを使うか、1行の状態とNULL可能な操作日時で表すか
- 状態をPostgreSQL ENUM、状態マスター、`text` とCHECKのどれで表すか
- 受付日時と行作成日時を分けるか、占有継続登録でも使える登録日時に統一するか
- 人数を受付時人数と現在人数に分けるか
- 準備中の人数変更を許可するか
- CHECK制約で守る範囲と、更新トリガー・専用操作で守る範囲

## 検討した選択肢

### 1. 予約なし利用を `reservations` へ保存する

- 予約と予約なし利用を同じ一覧から取得しやすい。
- 予約番号、連絡先、資格情報、来店確認、取消、無断キャンセルなど、予約なし利用では使わない項目と状態が混在する。
- 顧客による予約作成とスタッフによる店頭受付の認証・認可境界が曖昧になる。

### 2. `preparing`、`active`、終了状態を別テーブルにする

- 各テーブルではNULL列を減らせる。
- 利用開始や終了のたびに行を移動する必要があり、同じ利用の識別、外部キー、監査、同時操作が複雑になる。

### 3. 状態を保存せず、操作日時のNULL組み合わせから導出する

- 状態列と日時の重複を避けられる。
- APIの状態絞り込みと状態遷移の可読性が下がり、`preparing` と未完了の異常行を日時だけで判別する必要がある。

### 4. 1行に明示的な状態と操作日時を保存し、CHECKで組み合わせを制約する

- 同じ内部IDのまま受付から終了まで扱え、当日一覧と状態絞り込みが単純になる。
- 状態と日時は同じ事実の異なる表現になるため、CHECK制約を漏らすと矛盾する。
- 更新前状態、現在時刻、席配置定員、訂正元との関係はCHECKだけでは検査できない。

## 採用した案

- 予約なし利用を予約から独立させる。通常受付と誤終了後の占有継続をまとめる `walk_in_visit_series` を内部集約ルート、`walk_in_visits` を系列内の利用区間とし、各利用へUUIDv7、店舗、系列、継続元、現在人数、基本状態、登録・予定・実績日時、各操作スタッフ、中止理由、更新日時を保存する。
- 基本状態を `preparing`、`active`、`completed`、`aborted` の4種類とし、`text` とCHECK制約で表す。アプリケーションではPython Enumを使用する。
- 状態と、開始・終了・中止日時、操作スタッフ、中止理由の必須・NULL条件をCHECK制約で揃える。
- 通常遷移を `preparing -> active`、`preparing -> aborted`、`active -> completed` に限定し、更新前後を比較するDBトリガーと用途別アプリケーション操作で検証する。終了状態を通常操作で戻さない。
- `registered_at` をDBサーバー時刻で保存し、通常受付では受付日時兼行作成日時、誤終了後の占有継続では新しい継続行の登録日時とする。同じ値になる `created_at` は追加しない。
- 全行で `planned_start_at < planned_end_at` を保証する。継続元がない通常受付では `registered_at <= planned_start_at` とし、継続行では元の過去の予定日時を引き継げるようにする。
- 予定利用時間は予定開始・終了の差から求め、分数列へ重複保存しない。90分未満では受付を確定した登録スタッフと受付日時を、終了予定時刻の案内確認主体・日時として扱う。
- 通常受付、通常の `preparing -> active`、および `completed` からの占有継続では `started_at >= planned_start_at` とする。`aborted` から直接 `active` を作る占有継続だけは、現実の利用開始を記録するため予定開始前の `started_at = registered_at` を許可する。準備が `planned_end_at` 以後まで遅れた利用開始も保存して直ちに時間超過とし、開始の遅れを理由に予定終了を変更しない。
- 人数は現在受け入れている人数を `party_size smallint` の1列で持ち、1名以上12名以下とする。受付時人数を別列へ重複保存せず、変更前後は監査履歴へ残す。
- `preparing` と `active` のどちらでも、現在の割り当て定員内に限って人数を変更できる。減員時も席、予定日時、適用済み転換時間を縮小せず、`preparing` 中に5名未満へ減っても状態を変えない。
- 通常受付では1名から4名を登録と同時に `active`、5名から12名を `preparing` とする。5名以上は登録確定を準備開始として扱い、別の準備開始操作または日時を持たない。現在人数は後から変わるため、この対応を永続的なCHECKにせず通常INSERT時に検証する。
- `completed_at` は顧客の利用終了とし、終了後転換時間を含む席の占有終了は席配置計画で別に管理する。
- 実終了を反映した席占有が後続予定と重なっても利用終了を拒否せず、現実の競合として保存して強い警告と追加割り当て拒否へつなげる。
- 終了状態は戻さず、`completed` からは新しい `active`、`aborted` からは現場に応じた新しい `preparing` または `active` を同じ系列へ追加する。系列と継続関係の詳細はADR-0024を正とする。

## 採用理由

予約なし利用は予約と認証情報、作成主体、状態遷移が異なるため、共通テーブルへ多数の例外を入れるより独立させる方が安全である。一方、準備、利用中、終了ごとに別の行へ移動すると、席配置計画や例外案件が参照する内部IDまで変わる。1行の状態遷移にすれば、関係を維持したまま現在状態を検索できる。

状態と日時を両方保存する重複は、APIの可読性と状態別検索のために許容する。状態ごとの必須・NULL条件をDBでも保証し、アプリケーションの不具合や管理操作から矛盾行が入ることを防ぐ。

`accepted_at` という名称と「登録日時は必ず予定開始以前」という全行制約は、誤終了後に元の予定終了を引き継ぐ継続行と矛盾する。`registered_at` と通常受付に限定した時刻条件なら、通常経路の意味を保ちながら訂正経路を塞がない。

準備中も人数変更を許可すれば、席を用意している間の欠員・増員を、いったん中止して受付し直さず記録できる。席と適用済み時間を変更しないため、人数減少を理由に将来予約との競合条件を緩めることもない。

## 実用性評価

40席の単一店舗では、同時に未終了となる予約なし利用は物理的な席数以下である。店舗、状態、予定開始日時のインデックスと対象行ロックで、当日一覧、準備遅延、終了間近、時間超過を十分軽く検索できる。

通常スタッフは、受付、準備中・利用中の人数修正、利用開始、利用終了または理由付き中止を同じ利用カードから操作できる。準備中の人数変化で再受付を強制しないため、混雑時の入力負担を抑えられる。

CHECK制約だけでは、以前の状態、DB現在時刻、割り当て席の定員、通常受付か占有継続登録か、継続元との状態関係を判定できない。更新トリガー、用途別操作、店舗・利用系列・席配置のロック、監査記録およびPostgreSQL統合テストが必要である。これは実装量を増やすが、任意更新APIで終了状態を戻したり、人数だけを増やして定員を超える危険を抑えられる。

準備中に5名未満へ減っても適用済み準備時間を維持するため、実際には早く案内できる場合にも予定開始まで待つことになる。まずは安全側のMVPとして運用し、頻繁に不便が生じる場合だけ、席と全予約を再検証して受付を差し替える専用操作を検討する。

## デメリット

- 状態、日時、操作スタッフの組み合わせを保つCHECK制約と状態遷移トリガーが必要になる。
- 人数の初期値を現在行だけから取得できず、変更前の人数を確認するには監査履歴が必要になる。
- 占有継続登録は通常受付と時刻順序が異なるため、継続元の有無による条件付き制約と系列をまたぐ遅延制約トリガーが必要になる。
- 人数変更時の割り当て定員は席配置計画との横断検査になり、`walk_in_visits` 単体のCHECKでは保証できない。
- `completed` 後も終了後転換時間中は席を占有するため、基本状態だけを見て空席と判断できない。
- 時間超過による実績占有と既存予定の重なりを許容するため、受付時の重複禁止とは異なる制約経路が必要になる。

## 将来見直す条件

- 準備中の減員後に予定開始を早めたい要望が多く、受付差し替えまたは準備完了操作が必要になった。
- 待ち行列、注文、会計または顧客プロフィールを予約なし利用へ関連付ける。
- 13名以上の分割利用を恒久的な団体として一括変更・一括終了する必要が生じた。
- 状態追加が頻繁になり、`text` とCHECKより別の状態機械またはイベント履歴を正とする利点が上回った。
- 予約と予約なし利用を統合した利用セッションモデルへ移行する具体的な要件が生じた。

利用日時と席占有の保存責務、短時間案内および時間超過時の競合は `docs/adr/0023-walk-in-time-and-occupancy.md`、占有継続の系列と削除単位は `docs/adr/0024-walk-in-continuation-series.md` で具体化する。
