# ADR-0035: 配置場所の連結可能関係を正規化した無向ペアで保存する

## 状態

採用済み（2026-09-04）

## 背景

MVPではフロア座標を持たず、店舗が物理的に連結できると確認した配置場所同士の関係を正とする。例えば、`A-01`、`A-02`、`A-03`が一直線に並ぶ場合は、`A-01`と`A-02`、`A-02`と`A-03`の直接関係を保存し、連続した配置場所の組を自動配置時に探索する。

連結可能関係は方向を持たないため、`A-01 -> A-02`と`A-02 -> A-01`は同じ事実である。両方向を別行として許可すると、片方向だけの登録、二重登録および探索結果の重複が起きる。また、同じ配置場所同士、異なる店舗または移動可能エリアをまたぐ連結もDBで拒否する必要がある。

## 判断対象

- 連結可能関係に代理主キーを付けるか、配置場所の組を主キーにするか。
- 無向関係を1行へ正規化する方法。
- 自己連結と逆順の二重登録をどう拒否するか。
- 両端が同じ店舗・移動可能エリアに属することをどう保証するか。
- 直接関係と間接的な連続関係をどう扱うか。

## 検討した選択肢

### 1. 方向付きの行を両方向に保存する

- ある配置場所から隣接先を同じ列だけで検索できる。
- 1つの関係に2行必要になり、片方向だけの登録や削除が起こり得る。

### 2. 代理UUIDを持ち、配置場所の組にUNIQUE制約を置く

- 各関係を単独のIDで参照できる。
- 独立したライフサイクルを持たない純粋な関連に代理IDが増え、逆順正規化のCHECKとUNIQUEも別途必要になる。

### 3. 配置場所IDを不変の順序へ正規化し、その組を複合主キーにする

- 1つの無向関係を必ず1行で表し、主キーだけで重複を拒否できる。
- 登録前にUUIDの大小をそろえ、検索時は両端の列を扱う必要がある。

## 採用した案

- `placement_location_connections` を配置場所同士の直接的な連結可能関係を表す純粋な関連テーブルとする。代理UUID、方向、表示順、推移的な接続先は保存しない。
- `store_id`、`movement_area_id`、`location_a_id`、`location_b_id` をすべてNOT NULLとし、`PRIMARY KEY (location_a_id, location_b_id)` を使用する。
- アプリケーションまたは初期データ生成時に2つのUUIDを比較し、小さい方を `location_a_id`、大きい方を `location_b_id` へ保存する。
- `CHECK (location_a_id < location_b_id)` により、同じ配置場所同士の自己連結と、正規順序ではない逆向きの行を拒否する。主キーと組み合わせることで、同じ無向関係を最大1行にする。
- `(store_id, movement_area_id, location_a_id)` と `(store_id, movement_area_id, location_b_id)` から、`placement_locations (store_id, movement_area_id, id)` へそれぞれ複合外部キーを設定する。これにより、両端が同じ店舗・同じ移動可能エリアに属することを保証する。削除動作は `ON DELETE RESTRICT` とする。
- UUIDの大小は保存形式の正規化にだけ使い、画面表示、連結順または自動配置の優先順位には使用しない。これらには配置場所の `display_order` を使用する。
- 保存するのは直接隣接だけとする。`A-01`と`A-02`、`A-02`と`A-03`が登録されていても、`A-01`と`A-03`の行を推移的に追加しない。
- 複数の配置場所を使用する場合は、選択した配置場所と登録済みの直接関係からなる部分グラフが連結していることをアプリケーションで確認する。`A-01 + A-02 + A-03`は有効だが、間の`A-02`を含まない`A-01 + A-03`は無効とする。
- 新しい関係は有効な配置場所同士に限り、対応する有効な固定テーブルが使用する固定配置場所を含めない。これは別テーブルの現在状態を参照するため単純なCHECK制約ではなく、初期データ検証と、将来管理APIを追加する場合の同一トランザクション検証で保証する。
- MVPの初期データは、エリアAの隣接5組とエリアBの隣接3組の合計8行とする。独立固定席`F-01`、`F-02`と固定ボックス席`X-01`から`X-03`には関係を作成しない。
- MVPの初期データは各エリア内で直線状とし、分岐または循環を作らない。テーブル構造自体には次数や循環を制限する複雑な制約を追加せず、異なる形状のレイアウトを導入するときに同時連結可能性と探索規則を再確認する。
- 席構成マスターと連結可能関係の汎用管理CRUDはMVPへ含めない。将来変更機能を追加するときは、過去配置の解釈、廃止済み配置場所との関係、監査および変更中のロックを再設計する。

## 採用理由

連結可能関係は、独立して外部参照されるエンティティではなく、2つの配置場所間に存在する無向の事実である。正規化した配置場所IDの組を主キーにすれば、代理IDと追加のUNIQUE制約を持たずに同一関係を一意にできる。

UUIDの不変な比較順を使うため、スタッフ向けコードや表示順を変更しても主キーの向きは変わらない。2本の複合外部キーへ同じ店舗・エリアを含めれば、アプリケーションの事前検証だけに依存せず、壁や通路で分けた移動境界をDBでも守れる。

直接関係だけを保存すると、フロア構成の変更時に推移的な全組を同期する必要がなく、どの配置場所が物理的に隣接するかをそのまま説明できる。

## 実用性評価

MVPの初期データは8行だけであり、全関係をエリア単位に取得してメモリ上で探索しても性能上の問題はない。直線状の関係なので、最大6台の連続区間も単純に列挙できる。正規化と複合外部キーにより、逆順重複、自己連結およびエリア越境を初期データの誤りとして早期に検出できる。

一方、ペア関係は座標、テーブルの寸法、接続方向および同時に複数辺を利用できるかを表さない。MVPでは店舗が確認した直線状の初期設定を正とする。将来、分岐、円形配置または複雑な会場へ対応する場合は、単なるグラフの連結性だけで物理的な同時連結を保証できるか再検討が必要になる。

## デメリット

- 登録側でUUIDを比較して正規順序にそろえる必要がある。
- ある配置場所の全隣接先を探す際は、`location_a_id`と`location_b_id`の両方を検索する必要がある。
- 固定配置場所でないことや配置場所が有効であることは、単純な行内CHECK制約だけでは保証できない。
- 過去の連結設定を世代として保存しないため、将来のレイアウト管理機能では履歴設計の追加検討が必要になる。

## 将来見直す条件

- 分岐、循環、複数方向の接続またはテーブル寸法を扱う。
- フロア座標から接続候補を生成する。
- 席構成を営業中に変更する管理画面と、変更履歴または構成世代が必要になる。
- 配置場所数が大幅に増え、両端検索またはグラフ探索が性能要件を満たさなくなる。
