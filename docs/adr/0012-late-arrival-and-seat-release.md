# ADR-0012: 通常予約の15分到着期限と席解放

## 状態

採用済み（2026-08-24、境界規則を2026-08-25更新）

## 背景

通常予約を予約時刻から90分間必ず占有させると、顧客が無連絡で来店しない場合も空席を再利用できず、店舗の機会損失になる。一方、予約時刻を少し過ぎただけで自動的に正式な無断キャンセルとすると、時刻境界の取り違え、電話対応の遅れ、通信障害などによる誤判定が、無断キャンセル履歴へ直結する。

遅刻の連絡があった場合は来店を受け入れたいが、後続予約を守るため元の終了日時は延長できない。また、遅刻に合わせて保存済みの予約開始日時だけを変更すると、通常予約の90分制約と、顧客が元々予約した内容が失われる。

## 判断対象

- 無連絡の予約席をいつ解放するか。
- 席解放と正式な `no_show` 確定を同時に行うか。
- 遅刻連絡時に予約開始日時を変更するか、到着予定日時を別に持つか。
- 解放後に来店した顧客を元の予約として受け付けるか。
- 貸切にも同じ期限を適用するか。

## 検討した選択肢

### 1. 予約終了まで必ず席を保持する

- 遅れて来店した顧客を予約どおり案内できる。
- 無連絡でも最大90分間空席を再利用できず、人気時間帯の店舗運用に耐えにくい。

### 2. 予約開始から一定時間後に自動で `no_show` を確定する

- 状態変更と席解放を完全に自動化できる。
- 電話連絡の記録漏れや境界時刻の競合が、そのまま無断キャンセル履歴と将来の警告へ反映される。

### 3. 一定時間後に席だけを解放し、正式な無断キャンセルは後日審査する

- 営業中に席を再利用しながら、無断キャンセル履歴の誤確定を防げる。
- `confirmed` の基本状態と席確保の終了を分けるため、期限、資格情報、画面表示、競合制御を明示する必要がある。

### 4. 遅刻連絡時に予約開始日時を到着予定時刻へ変更する

- 画面上の開始日時が来店予定と一致する。
- 終了日時を維持すると90分固定に反し、終了も移動すると後続予約へ影響する。元の契約内容も現在値から失われる。

## 採用した案

- 通常予約の来店期限は予約開始から15分後とし、1分の追加猶予を設けない。
- 来店確認、遅刻連絡、顧客都合キャンセルは来店期限ちょうどまで許可し、期限を過ぎた後に元予約として拒否する。
- 遅刻連絡があった場合は予約開始・終了日時を変更せず、到着予定日時を別に記録する。
- 来店受付終了境界は元の終了日時の30分前とし、その時刻ちょうどの来店確認を許可して、境界を過ぎた後に拒否する。
- 到着予定日時は来店受付終了境界以前に限定し、連絡後の来店期限は、到着予定日時の15分後と来店受付終了境界のうち早い方とする。
- スタッフは終了を延長しないこと、来店受付終了境界、残りの利用可能時間を案内する。
- 来店期限以前に受けた来店しない旨の連絡は、顧客都合の `cancelled` として直ちに確定する。期限を過ぎた後の連絡は予約状態を変更せず、無断キャンセル審査へ記録する。
- 無連絡で期限を過ぎた場合は席を解放するが、その場で `no_show` を確定しない。営業終了後の候補抽出と管理責任者の審査を維持する。
- 解放後に来店した顧客は、空席がある場合だけ予約なし利用として新規受付する。元予約は復活させない。
- 貸切は代表者との個別調整を前提とするため、この15分ルールを適用しない。
- 顧客向け文言は `docs/reservation_terms_draft.md` を草案とし、予約確定前に要点と全文への導線を表示する。
- 到着予定日時、適用した席解放期限、実際の解放記録、席配置世代との関係は `docs/adr/0013-arrival-deadline-persistence.md` を正とする。

## 採用理由

席解放と無断キャンセル履歴の確定を分ければ、営業中の空席を再利用しながら、通信や操作の事情を管理責任者が後日確認できる。顧客都合キャンセル、営業中の席解放、正式な `no_show` を別の事実として記録できるため、将来の利用警告へ未審査の候補を混入させない。

元の予約期間を維持して到着予定日時を分ければ、予約内容、90分制約、後続予約を変えずに遅刻を受け入れられる。解放日時を終了30分前で打ち切るため、着席から食事までの最低時間を確保し、遅刻連絡によって席の占有時間も延びない。

## 実用性評価

無連絡時の席解放は、満席時間帯に空席を予約終了まで保持する問題を解消する。通常は時刻による判定だけで済み、スタッフ入力は顧客から遅刻またはキャンセルの連絡があった場合に限られるため、営業中の負担を抑えられる。

ただし、期限直前の来店確認、電話連絡、新しい予約または予約なし利用の受付が同時に発生し得る。フロントエンドの時計や画面表示だけでは実運用に耐えず、サーバー時刻、予約と席配置のロック、同一トランザクション内の再検証、境界値と同時実行のPostgreSQL統合テストが必要になる。

電話が混雑して店舗へつながらない場合や通信障害では、顧客が連絡を試みても席が解放される可能性がある。規約表示だけではこの問題を完全に解消できないため、正式運用前に代替連絡手段または管理責任者による例外判断を検討する必要がある。

## デメリット

- 予約の基本状態が `confirmed` のまま席確保だけが終了する一時的な状態を扱う必要がある。
- 到着予定日時、席解放期限、実際の解放と監査のデータが増える。
- 解放後に来店して空席がない場合は、規約を理解していても顧客とのトラブルになる可能性がある。
- 到着予定が終了30分前に近い場合は、通常の15分より短い猶予になる。
- 貸切と通常予約で遅刻処理が異なる。

## 将来見直す条件

- SMS、Webまたは音声案内から顧客自身が到着予定を登録できるようにする。
- 店舗ごとに遅刻許容時間を変更する。
- デポジット、キャンセル料または自動的な利用制限を導入する。
- 遅刻連絡件数、15分期限経過後の再販売率、解放後の来店件数から現在の期限が実運用に合わないと判明する。
- 貸切にも定型の到着期限が必要になる。
