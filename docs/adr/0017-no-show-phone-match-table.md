# ADR-0017: 無断キャンセル電話照合を予約従属テーブルへ分離する

## 状態

採用済み（2026-08-25）

## 背景

MVPでは、管理責任者または管理者が確定した無断キャンセルについて、同じ店舗の新しい予約と電話番号が一致した場合に認証済みスタッフへ要確認警告を表示する。電話番号はE.164形式へ正規化し、専用秘密鍵によるHMAC-SHA-256照合値として検索する方式をADR-0002で決定している。

HMAC秘密鍵と電話番号正規化方式は更新可能でなければならず、移行中は同じ無断キャンセル予約へ新旧の照合値を一時的に併存させる必要がある。また、照合値は匿名情報ではないため、無断キャンセル確定から1年で全バージョンを削除しなければならない。

## 判断対象

- 照合値を予約本体へ置くか、専用テーブルへ分離するか
- 専用テーブルの識別方法と重複防止方法
- 店舗IDを専用テーブルにも保存するか
- スタッフ照合と期限削除に必要なインデックス
- 鍵更新、訂正、削除保留を含むライフサイクル

## 検討した選択肢

### 1. 予約本体へ現在のHMAC列を置く

- 1つの照合値だけならテーブル結合が不要で単純である。
- 鍵と正規化方式の移行中に旧値と新値を併存しにくく、世代ごとの列追加または別の可変構造が必要になる。
- 予約本体の主要な読み取りへ機微な照合値が混在し、用途と保持期限の分離が弱くなる。

### 2. 専用テーブルへ独立したUUID主キーを設ける

- 後から任意の履歴を追加しやすい。
- 同じ予約、鍵バージョン、正規化方式バージョンの重複を防ぐUNIQUE制約が別に必要になり、この用途では独立UUIDに業務上の意味がない。

### 3. 専用テーブルへ予約と各バージョンの複合主キーを設ける

- 予約への従属関係と、同じバージョンを重複させない条件を主キーで直接表せる。
- 鍵更新と正規化方式更新を独立して行い、移行中だけ複数行を併存できる。
- スタッフ照合では親予約との結合が必要になる。

### 4. 専用テーブルにも店舗IDを保存する

- 店舗を先頭にした検索や将来の行レベルセキュリティ、店舗単位のパーティションには使いやすい。
- 店舗は親予約から一意に決まるため重複データとなり、別店舗との組み合わせを防ぐ複合外部キーなどの整合性管理が増える。

## 採用した案

`no_show_phone_matches` を予約集約内の従属テーブルとし、次を採用する。

- 主キーは `(reservation_id, key_version, normalization_version)` とする。
- `reservation_id` は `reservations.id` を参照し、親予約を物理削除する場合は `ON DELETE CASCADE` で従属行も削除する。
- HMAC-SHA-256照合値を32バイトの `bytea`、各バージョンを正の `smallint` として保存する。
- 作成日時と、無断キャンセル確定から1年後に固定した削除期限をタイムゾーン付き日時で保存する。
- `phone_hmac` は一意にしない。同じ電話番号に複数の確定済み無断キャンセルが存在することを許可する。
- 店舗IDは重複保存せず、スタッフ照合では親予約と結合して所属店舗と `no_show` 状態を明示的に検査する。
- HMAC入力と店舗内予約番号の意味が変わらないよう、予約の所属店舗は作成後に変更不可とする。
- スタッフ照合用に `(key_version, normalization_version, phone_hmac, expires_at)`、期限削除用に `(expires_at, reservation_id)` のB-treeインデックスを作成する。
- `no_show` 確定と最初の照合行作成、訂正時の状態変更と全照合行削除を、それぞれ同一トランザクションで行う。
- 鍵または正規化方式の更新で追加する行には元の削除期限を引き継ぎ、保持期間を延長しない。
- 日次削除ジョブは1予約の全バージョンと親予約の保持期限を迎えた氏名・電話番号を同じ削除単位として扱い、削除保留中は両方を残す。

HMACメッセージは次の固定バイト形式とする。

```text
ASCII("no-show-phone:v1")
|| 0x00
|| UUID_TO_16_BYTES(store_id)
|| ASCII(contact_phone_e164)
```

公開予約作成処理では照合せず、新しい予約へ警告状態を保存しない。スタッフ向け読み取り時に保持中の値から警告を派生させる。

## 採用理由

予約本体と照合用途を分離しながら、鍵と正規化方式を止めずに移行できるためである。複合主キーは従属データの同一性そのものであり、意味のないUUIDと追加の重複防止制約を増やさずに済む。

検索インデックスは先頭の鍵バージョン、正規化方式バージョン、HMACを完全一致させ、最後の保持期限を範囲条件にする主要クエリに合わせている。期限削除は別の先頭列を必要とするため専用インデックスを分ける。

店舗IDを親予約だけへ保持すれば同じ業務上の事実を重複保存せずに済む。HMAC入力へ店舗IDを含めることだけに認可を依存せず、親予約の所属店舗も問い合わせ条件へ含めることで店舗境界を明示する。

## 実用性評価

40席の単一店舗で1年間に保持する確定済み無断キャンセルと一時的な鍵世代の件数は小さい。32バイトのHMAC、複合主キー、2つのB-treeインデックスおよび予約主キーとの結合はMVPのデータ量で十分実用的であり、日常的な手動処理を必要としない。

鍵更新バッチは、保持中の親予約から新しい値を再生成し、複合主キーによる競合無視で安全に再開できる。全件移行を検証するまで旧値と旧鍵を残すため、計画的な更新中も警告を継続できる。鍵喪失時は再生成完了まで警告が欠落するが、公開予約受付は継続できる。

一方、電話番号の一致は本人性を保証せず、誤入力、番号の共有、再割り当てによる別人の一致を防げない。HMACは既知の候補番号と照合可能な個人情報であり、秘密鍵とDBの両方が漏えいした場合の保護にもならない。したがって、警告を自動拒否へ使用せず、所属店舗の認可、鍵管理、保持期限処理、ログの非記録を実装と運用で検証する必要がある。

## デメリット

- スタッフ向け照合で予約本体との結合が必要になる。
- DB制約だけでは秘密鍵を使ったHMACの再計算ができず、照合値の正しさはアプリケーションと統合テストにも依存する。
- 複数バージョンの移行状態と、移行完了後の旧値削除を管理するバッチ処理が必要になる。
- 将来、非常に多くの店舗を同一DBで扱い、店舗単位の行レベルセキュリティやパーティションが必要になった場合は、店舗IDを従属テーブルへ持たせる方が適する可能性がある。

## 将来見直す条件

- 複数店舗化によって、親予約との結合を含む照合性能が要件を満たさなくなった。
- 店舗単位の行レベルセキュリティまたはパーティションを導入し、従属テーブル自体に店舗IDが必要になった。
- 顧客アカウントや検証済み連絡先を導入し、電話番号照合の目的または保持期間が変わった。
- 鍵管理基盤や暗号方式を変更し、現在の世代管理では安全な移行ができなくなった。

店舗IDを追加する場合は、親予約と異なる店舗を保存できない複合外部キーまたは同等のDB制約を必須とする。電話番号一致だけで本人と断定したり、自動的に予約を拒否したりする方式へは変更しない。
