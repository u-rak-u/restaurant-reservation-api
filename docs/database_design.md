## 3. 主キー方針

### 3.1 独立したエンティティ

**確定：独立した同一性を持つエンティティの代理主キーには、PostgreSQL 18が生成するUUIDv7を使用する。**

基本形は次のとおりとする。

```sql
id uuid DEFAULT uuidv7() PRIMARY KEY
```

- 店舗、スタッフアカウント、当日運用責任者任命、予約、予約なし利用、物理テーブル、配置場所、席配置計画、営業時間ルール、定休日ルール、特別営業時間、臨時休業、例外案件、監査記録、削除保留、定期削除実行など、独立して参照するエンティティへ適用する。
- UUIDは通常のAPIリクエストから指定させず、INSERT時にDBで生成する。
- SQLAlchemyはINSERT後の `RETURNING` で生成済みUUIDを受け取り、同じトランザクション内の子データへ使用する。
- UUIDv7に含まれる時刻を業務上の作成日時として使用せず、`created_at` などのタイムゾーン付き日時列を別に保存する。
- 一覧の並び順、保持期限、営業日判定をUUID順へ依存させず、意味のある日時列と一意な追加順序で明示する。

### 3.2 従属データと関連データ

独立したIDを必要としない従属データは、親の主キーまたは業務上の一意な組み合わせを主キーとする。

| 対象 | 主キー方針 |
| --- | --- |
| 通常予約詳細 | `reservation_id` |
| 貸切予約詳細 | `reservation_id` |
| 無断キャンセル電話照合 | `(reservation_id, key_version)` |
| 席配置世代 | `(seat_placement_plan_id, generation_number)` |
| 連結可能関係 | 順序を正規化した `(location_a_id, location_b_id)` |
| その他の多対多関連 | 関係を一意に識別できる外部キーの組み合わせ |

- 複合主キーの構成列はすべて `NOT NULL` とする。
- 関連自体が固有のライフサイクル、外部参照、複数の履歴を持つ場合は、意味のない複合主キーへ固執せずUUIDv7のエンティティへ昇格させる。
- 具体的な主キー構成は各テーブルの設計時に再確認する。

### 3.3 公開識別子と認可

- UUID主キーは内部識別子であり、予約番号、予約確認コード、チェックイントークンの代わりにしない。
- 顧客向け予約照合では、確定済みの10桁予約番号と予約確認コードまたはチェックイントークンを使用する。
- UUIDを知っていることを認証または認可の証明として扱わない。
- スタッフAPIはUUIDで対象を指定する場合も、認証済みスタッフの所属店舗、ロール、当日運用責任者任命、対象状態をサーバー側で毎回検証する。
- 対象取得では、全件からUUIDだけで検索して後から判定する構造を避け、可能な限り対象店舗と許可範囲を検索条件へ含める。
- 異なる店舗の有効なUUIDを使用した読み取り、変更、削除が拒否されることを認可テストで確認する。

### 3.4 生成と移植性

- PostgreSQL 18組み込みの `uuidv7()` を使用し、UUID生成のためだけに拡張機能または追加ライブラリを導入しない。
- 主キーの一意性はUUID生成確率だけに頼らず、`PRIMARY KEY` 制約で保証する。
- PostgreSQL 18未満または別DBへ移行する場合は、同じUUIDv7をアプリケーションで生成するか、移行先の標準機能へ置き換える必要がある。
- DB生成を採用する間は、永続化前にIDが必要な処理を組まず、集約の保存順序とトランザクションで親IDを受け取る。

### 3.5 実用性評価

UUIDv7は連番IDのように隣接値から別レコードを列挙できず、オブジェクト単位の認可漏れに対する追加防御になる。PostgreSQL 18の組み込み関数を使用できるため、生成用の依存関係も増えない。

一方、UUIDは認可の代わりではなく、有効なUUIDが漏れた場合や一覧APIから取得できる場合には、所属店舗と権限の検証がなければ不正アクセスが成立する。UUIDv7は作成時刻に近い情報を含み、`bigint`よりキーとインデックスが大きいが、単一店舗40席のMVPでは許容できる。実装後は認可テストを必須とし、実データ量でインデックスサイズと主要クエリを確認する。

## 4. 店舗

### 4.1 `stores` テーブル

| 列 | PostgreSQL型 | NULL | 初期値・制約 | 用途 |
| --- | --- | --- | --- | --- |
| `id` | `uuid` | 不可 | 主キー、`DEFAULT uuidv7()` | 内部識別子 |
| `code` | `text` | 不可 | 一意、1文字以上50文字以下、小文字英数字と区切りのハイフンだけを許可 | 設定から店舗を選択する安定した識別子 |
| `name` | `text` | 不可 | 前後の空白を除いて1文字以上100文字以下 | 画面表示用の店舗名 |
| `timezone` | `text` | 不可 | 1文字以上64文字以下 | `Asia/Tokyo` などのIANAタイムゾーン名 |
| `created_at` | `timestamp with time zone` | 不可 | `DEFAULT CURRENT_TIMESTAMP` | 作成日時 |
| `updated_at` | `timestamp with time zone` | 不可 | `DEFAULT CURRENT_TIMESTAMP` | 最終更新日時 |

- `code` は `main` のような値とし、作成後は原則変更しない。顧客やスタッフの認証・認可には使用しない。
- `code` の形式は、先頭と末尾を小文字英数字、単語間を単一のハイフンとする。DBでは文字数と正規表現の `CHECK` 制約を設ける。
- `timezone` はUTCオフセットではなくIANAタイムゾーン名を保存する。PostgreSQLの通常の `CHECK` 制約だけでタイムゾーンデータベースとの恒久的な一致を保証しようとせず、初期化処理とアプリケーション入力で有効性を検証する。
- 業務上の瞬間を表す日時は `timestamp with time zone` で保存し、営業時間、営業日、日次処理などのローカル日時判定時に店舗タイムゾーンへ変換する。
- `updated_at` は行を変更するアプリケーション処理で同じトランザクション内に更新する。MVPで汎用的な店舗更新APIは提供しない。
- 住所、電話番号、公開URL、通貨、言語、営業中フラグは現在の予約処理に不要なため、MVPの店舗テーブルへ先回りして追加しない。通常の休業と臨時休業は営業カレンダー領域で扱う。

### 4.2 単一店舗MVPの扱い

- MVPのアプリケーションは単一店舗だけを対象とするが、DBに1行しか保存できない制約は設けない。
- 顧客向けAPIでは任意の店舗IDまたは店舗コードを入力させず、デプロイ設定で選択した店舗をサーバー側で解決する。
- スタッフ向けAPIでは、後続設計で定めるスタッフの所属店舗を必ず認可条件に含める。
- 複数店舗運用を開始するまでは、2件目の店舗を作成する通常APIを提供しない。

### 4.3 初期店舗データ

- Alembicマイグレーションは `stores` テーブルと制約を作成し、環境固有の店舗行は登録しない。
- 初期店舗は、マイグレーション適用後に明示的な初期化コマンドで作成する。APIプロセスの起動時には自動作成しない。
- 初期化コマンドは店舗コード、店舗名、IANAタイムゾーン名を設定から受け取り、形式とタイムゾーンの有効性を検証する。
- 対象コードが存在しなければ1件作成する。同じ内容で既に存在すれば成功として終了し、内容が異なる場合は既存行を上書きせずエラーにする。
- 開発環境の初期値は `code=main`、`name=サンプルレストラン`、`timezone=Asia/Tokyo` とする。これらは秘密情報ではないが、実環境ではデプロイ設定から明示する。
- 環境ごとに生成される店舗UUIDが異なってもよい。アプリケーション設定はUUIDではなく安定した `code` で対象店舗を選択する。

この方針の背景、代替案、実用性は `docs/adr/0006-store-identity-timezone-and-bootstrap.md` を正とする。
