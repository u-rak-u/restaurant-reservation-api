# ドメインモデル

## 1. 文書の目的

この文書は、`docs/requirements.md` と `docs/table_layout.md` で確定したMVP要件を、実装可能なドメイン概念へ整理する。
ここでは業務上の責務、エンティティ、値オブジェクト、集約、状態遷移、ドメインサービスの候補を扱う。

具体的なテーブル名、カラム、外部キー、SQLAlchemyモデル、APIエンドポイントは、ドメインモデルの承認後にデータベース設計とAPI設計で決定する。

## 2. 現在の状態

**初稿・一部確定**

- 要件から直接導ける業務上の事実は、確定事項として記載する。
- エンティティと値オブジェクトの分け方、集約境界、共通化方法は提案であり、重要な判断をユーザーと確認してから確定する。
- 将来機能のためだけにMVPのモデルを複雑化しない。
- 単一店舗のMVPとして設計するが、主要な業務データは店舗との所属関係を明示する。
- MVPでは独立した顧客エンティティを作らず、予約者の氏名と電話番号を予約時点の連絡先として各予約に保持する方針は確定済みとする。

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| 予約者 | 予約時に氏名と電話番号を提供する人物。MVPではログインアカウントを持たない |
| 予約 | 通常予約または貸切予約を表す業務上の約束 |
| 通常予約 | 1名から12名、開始時刻10分単位、標準利用時間90分の予約 |
| 貸切予約 | 店舗全体、エリア、テーブルを対象とし、イベント時間と準備・片付け時間を持つ予約 |
| 営業日 | 店舗が営業を開始した日。日付をまたぐ深夜営業では実際の暦日と異なる場合がある |
| 席配置 | 予約へ割り当てた物理テーブルと配置場所の組み合わせ |
| 例外案件 | 通常操作で状態を直接変更せず、事実記録、提起、後日の審査を必要とする案件 |
| 無断キャンセル履歴 | 管理責任者が確認し、予約状態を `no_show` にした確定済みの履歴 |

## 4. ドメイン領域

```text
予約 ───────────────┐
  │                 │
  ├─ 営業カレンダー ─┤─ 予約可否の判定
  │                 │
  └─ 席配置 ─────────┘─ 席資源の確保と再配置

スタッフ権限 ────────── 各操作の認可
例外審査 ───────────── 通常では訂正できない事実の提起と確定
監査・保持 ──────────── 操作証跡、匿名化、削除保留、定期削除
```

### 4.1 予約領域

予約番号、予約者の連絡先、日時、人数、状態、取消、確認コード、QRチェックイントークンを管理する。
通常予約と貸切予約に共通する状態遷移を扱いながら、利用時間、人数上限、対象範囲など予約種別ごとの条件を分離する。

### 4.2 席配置領域

物理テーブル、移動可能エリア、配置場所、連結可能関係、予約ごとの席配置を管理する。
新規予約によって既存予約を再配置する場合は、複数予約の配置を同じトランザクションで変更する。

### 4.3 営業カレンダー領域

曜日ごとの通常営業時間、定休日ルール、特別営業時間、臨時休業から、指定日時がどの営業日に属し、予約可能かを計算する。
MVPでは営業日を事前生成せず、保存したルールを正として都度評価する。

### 4.4 スタッフ権限領域

スタッフアカウントの認証、基本ロール、所属店舗、当日運用責任者の期限付き任命を管理する。
当日運用責任者は基本ロールを書き換えず、対象営業日と有効期間を持つ任命として扱う。

### 4.5 例外審査領域

来店確認の異常、来店記録の訂正、無断キャンセル候補、臨時休業による要対応などを、予約の基本状態と分離して管理する。
当日の事実記録と提起、管理責任者による後日の承認または却下を扱う。

### 4.6 監査・保持領域

業務操作の変更前後、操作者、理由を追記型の履歴として保存する。
個人情報の保持期限、匿名化、削除保留、日次削除ジョブの実行履歴を扱う。

## 5. エンティティ候補

エンティティは、属性が変化しても同一性を追跡する必要がある概念とする。

| エンティティ候補 | 識別の単位 | 主な責務 |
| --- | --- | --- |
| 店舗 | 店舗ID | タイムゾーンと店舗単位の整合性を支える |
| スタッフアカウント | スタッフID | 認証情報、基本ロール、所属店舗、有効状態を管理する |
| 当日運用責任者任命 | 任命ID | 対象営業日、就任、承認、引き継ぎ、緊急就任、失効を管理する |
| 予約 | 予約ID | 予約番号、予約種別、予約者情報、日時、状態、資格情報を管理する |
| 通常予約詳細 | 予約ID | 人数、標準利用時間、コメントなど通常予約固有の情報を管理する |
| 貸切予約詳細 | 予約ID | イベント時間、準備・片付け時間、参加人数、貸切範囲を管理する |
| 物理テーブル | テーブルID | 定員、固定・可動、所属エリア、有効状態を管理する |
| 配置場所 | 配置場所ID | 所属フロア、所属エリア、配置順、固定席との関係を管理する |
| 連結可能関係 | 2つの配置場所の組 | 直接連結できる配置場所の隣接関係を管理する |
| 席配置計画 | 席配置計画ID | 予約へ適用中の決定区分、転換時間、配置の世代を管理する |
| 席割り当て | 席割り当てID | 1つの席配置計画に含まれる物理テーブルと配置場所の組を管理する |
| 営業時間ルール | 営業時間ルールID | 曜日、開始時刻、終了時刻、終了日の繰り越しを管理する |
| 定休日ルール | 定休日ルールID | 毎週型または月内週番号型の休業規則を管理する |
| 特別営業時間 | 特別営業時間ID | 特定営業日の通常営業時間を置き換える時間帯を管理する |
| 臨時休業 | 臨時休業ID | 単一日または日付範囲の終日休業と理由を管理する |
| 例外案件 | 例外案件ID | 種別、事実、提案、審査状態、決定内容を管理する |
| 監査記録 | 監査記録ID | 操作主体、対象、変更前後、理由、実行日時を保存する |
| 削除保留 | 削除保留ID | 対象、理由、設定者、見直し期限、解除を管理する |
| 定期削除実行 | 実行ID | 実行予定日、開始・終了、結果、処理件数を管理する |

MVPでは顧客を独立したエンティティにしない。
予約者は予約集約内の予約者連絡先として表現し、同じ氏名または電話番号を持つ複数予約を同一人物へ自動統合しない。

## 6. 値オブジェクト候補

値オブジェクトは、独立した識別子よりも値と検証規則に意味がある概念とする。

| 値オブジェクト候補 | 含む値・規則 |
| --- | --- |
| 予約番号 | 先頭9桁の乱数と末尾1桁のLuhnチェックディジットからなる10桁文字列 |
| 予約確認コード | 顧客へ渡す8桁の数字。ドメインでは平文の生成・検証を扱い、保存時はハッシュ化する |
| チェックイントークン | 推測困難なランダム値。保存時は検証用ハッシュへ変換する |
| 予約者連絡先 | 予約時点の氏名、入力された電話番号、正規化した電話番号 |
| 電話番号照合値 | 無断キャンセル履歴との限定的な照合に使う値。個人情報として保持期限の対象にする |
| 予約期間 | タイムゾーン付き開始日時と終了日時。開始より終了が後であることを保証する |
| 営業日 | 店舗タイムゾーン上の営業開始日 |
| 営業時間帯 | ローカル開始時刻、終了時刻、終了日の繰り越し値 |
| 人数 | 通常予約では1名以上12名以下。貸切では対象範囲の収容人数以下 |
| 準備・片付け時間 | それぞれ0分以上180分以下、10分単位 |
| 大人数転換時間 | 店舗初期値10分。予約確定時の適用値を席配置計画へ固定する |
| 席配置決定区分 | `automatic`、`flexible`、`fixed` のいずれか |
| 操作理由 | 例外操作、固定決定、再変更などで空文字を許さない理由 |

## 7. 集約候補

集約は、1つのトランザクションで必ず整合させる変更単位として扱う。

### 7.1 予約集約

**提案**

- 予約を集約ルートとする。
- 予約者連絡先、予約種別ごとの詳細、予約確認コードのハッシュ、現在有効なチェックイントークンのハッシュを予約集約の内部に置く。
- 予約の状態変更は、任意の値を設定する更新ではなく、来店確認、利用完了、取消、無断キャンセル確定という業務操作を通じて行う。
- 席配置は複数予約を同時に再配置する必要があるため、予約集約の内部へ完全には含めない。
- 例外案件は予約の基本状態と独立した審査ライフサイクルを持つため、別集約とする。

### 7.2 席配置計画集約

**提案**

- 予約ごとの席配置計画を集約ルートとし、物理テーブルと配置場所の組を席割り当てとして含める。
- 1つの計画内で、同じ物理テーブルまたは配置場所を重複させない。
- 決定区分、固定理由、適用した転換時間を計画へ保持する。
- 複数予約の席配置計画を変更する自動再配置は、単一集約の操作ではなく席割り当てドメインサービスが調整する。

### 7.3 営業カレンダー集約

**提案**

- 店舗を整合性確認の起点とし、通常営業時間、定休日ルール、特別営業時間、臨時休業を店舗単位で扱う。
- 設定変更時は店舗をロックし、前後の営業日と既存予約への影響を同じトランザクションで検証する。
- 実際の営業日は保存済みエンティティではなく、規則から計算する結果として扱う。

### 7.4 当日運用責任者任命集約

**提案**

- 任命を集約ルートとし、対象店舗、対象営業日、担当スタッフ、有効期間、任命方法を持つ。
- 同じ店舗の同じ時点に有効な任命を1つだけ許可する。
- 引き継ぎでは、前任の終了と後任の開始を同じトランザクションで成立させる。

### 7.5 例外案件集約

**提案**

- 例外案件を集約ルートとし、対象予約、案件種別、報告事実、当日の対応、提案、審査結果を持つ。
- 通常スタッフの報告、当日運用責任者の提起、管理責任者の承認または却下を順序のある操作として扱う。
- 承認によって予約状態の訂正が必要な場合は、例外案件と予約を同じアプリケーショントランザクションで更新し、監査記録を追加する。

### 7.6 削除保留集約

**提案**

- 削除保留を対象データとは別の集約として管理し、理由、設定者、見直し期限を必須にする。
- 定期削除ジョブは削除対象を選ぶときに、有効な削除保留が存在しないことを確認する。

## 8. 予約の状態遷移

```text
                       来店確認
confirmed ─────────────────────────→ checked_in
    │                                      │
    │ 顧客・店舗都合の取消                 │ 利用完了
    ↓                                      ↓
cancelled                              completed
    │
    └─ 終了状態

confirmed ── 管理責任者による確定 ──→ no_show
                                           │
                                           └─ 終了状態
```

- 作成成功時の状態は `confirmed` とする。
- `cancelled`、`completed`、`no_show` は通常操作で元へ戻さない。
- 来店記録の訂正などが必要な場合は、元の操作を削除せず、例外案件の承認と訂正記録を追加する。
- `review_required` は予約の基本状態へ追加せず、未解決の例外案件が存在することから判定する。

## 9. ドメインサービス候補

複数の集約または外部の現在時刻を参照しなければ判断できない処理は、エンティティへ無理に押し込まずドメインサービスまたはアプリケーションサービスで調整する。

| サービス候補 | 責務 |
| --- | --- |
| 営業日判定サービス | 対象日時の営業日、適用営業時間、定休日、特別営業時間、臨時休業を判定する |
| 予約受付ポリシー | 365日前、2時間前、24時間前、10分の訂正猶予、営業時間内完結を判定する |
| 席候補探索サービス | 人数、時間、転換時間、決定区分から利用可能な配置候補を探索する |
| 席再配置サービス | 新規予約と既存予約を維持できる全体配置を探索し、評価順に最適案を選ぶ |
| 貸切競合判定サービス | 貸切範囲と停止期間が通常予約、他の貸切、営業時間と競合しないか判定する |
| 権限判定サービス | 基本ロール、当日運用責任者任命、対象営業日から操作権限を判定する |
| 無断キャンセル警告照合 | 新規予約の電話番号と保持期間内の確定済み履歴を照合し、スタッフ向け警告を判定する |
| 保持期限計算サービス | 予約状態と確定日時から個人情報・履歴の削除予定日時を計算する |

## 10. 集約をまたぐ重要なトランザクション

### 10.1 通常予約の作成

1. 冪等性キーの再利用を確認する。
2. 営業日と受付期限を判定する。
3. 競合する予約、席配置計画、物理テーブル、配置場所を一定順序でロックする。
4. 通常割り当てを試し、必要な場合だけ既存予約を含む再配置を計算する。
5. 予約、予約資格情報、席配置計画、再配置された既存計画、監査記録を一括で保存する。
6. 一部でも失敗した場合は全体をロールバックする。

### 10.2 貸切予約の作成

1. 操作者が管理責任者または管理者であることを確認する。
2. イベント時間、準備・片付け時間、対象範囲、収容人数、営業時間を検証する。
3. 対象範囲と競合しうる予約をロックして再取得する。
4. 競合がなければ貸切予約と監査記録を保存し、競合があれば何も作成しない。

### 10.3 例外案件の承認

1. 管理責任者または管理者の権限を確認する。
2. 対象の例外案件と予約をロックする。
3. 提案内容が現在の予約状態にも適用可能か再検証する。
4. 例外案件の審査結果、必要な予約訂正、監査記録を一括で保存する。

## 11. 最初に確認する設計判断

### 11.1 顧客エンティティをMVPで作るか

**確定：独立した顧客エンティティを作らず、予約者連絡先を予約時点の値として予約に保持する。**

理由は次のとおりである。

- MVPの顧客はアカウントを持たず、電話番号だけでは同一人物と断定できない。
- 同じ電話番号の予約を1人の顧客へ自動統合すると、再割り当て、家族共用、誤入力によって別人の予約を誤って結び付ける。
- 氏名や電話番号が後から変更されても、過去の各予約で実際に受け付けた情報を保持する必要がある。
- 無断キャンセル警告には、独立した顧客IDではなく、保持期間内の電話番号照合値を使用できる。

この案では、同じ人物が複数回予約しても予約ごとに氏名と電話番号を保存する。
顧客アカウントを将来導入する場合は、予約時点の連絡先を残したまま、任意の顧客アカウントIDを予約へ関連付ける。

### 11.2 実用性評価

独立した顧客エンティティを作らない方式は、ログイン不要の単一店舗MVPでは実用に耐える。
予約時点の連絡先が各予約に残るため、電話受付と履歴確認を行いやすく、誤った顧客統合を避けられる。

一方、常連客の情報を一括更新すること、顧客単位の履歴表示、複数予約をまとめた本人確認には向かない。
これらが必要になった場合は顧客アカウントを追加するが、電話番号の一致だけで既存予約を自動的に同じアカウントへ統合しないことを条件とする。

### 11.3 後続設計への影響

- MVPの予約は、顧客IDを必須にせず、予約時点の氏名、入力された電話番号、正規化した電話番号を保持する。
- 電話番号照合値は検索と無断キャンセル警告のために使用するが、顧客の一意識別子または外部キーとして扱わない。
- 予約者名または電話番号を変更した場合は、その予約だけを更新し、同じ値を持つ別予約へ変更を波及させない。
- 将来顧客アカウントを導入する場合は、予約時点の連絡先を残したまま、予約から任意の顧客アカウントを参照できる構造を追加する。
- 既存予約と将来の顧客アカウントを、電話番号の一致だけで自動的に関連付けない。

## 12. 後続の確認事項

1. 通常予約と貸切予約を、共通の予約集約と種別別詳細として扱うか、別集約として扱うか。
2. 例外案件の種類ごとに共通の審査状態を使うか、無断キャンセル審査と臨時休業対応を分けるか。
3. 席配置計画の変更履歴を、現在計画と監査記録だけで表すか、世代を持つ計画として保存するか。
4. 電話番号照合値をどの形式で保存し、番号表記の正規化と鍵更新をどこで扱うか。
5. 貸切予約にも通常予約と同じ予約番号、確認コード、QR来店確認、基本状態を適用するか。
