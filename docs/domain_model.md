# ドメインモデル

## 1. 文書の目的

この文書は、`docs/requirements.md` と `docs/table_layout.md` のMVP要件を、実装可能なドメイン概念へ整理する。
予約なし利用追加による再検討結果は `docs/walk_in_impact_review.md` を参照し、W-01からW-09の確定事項を後続設計の前提とする。
ここでは業務上の責務、エンティティ、値オブジェクト、集約、状態遷移、ドメインサービスを扱う。

具体的なテーブル名、カラム、外部キー、SQLAlchemyモデル、APIエンドポイントは、後続のデータベース設計とAPI設計で決定する。

## 2. 現在の状態

**確定**

- 要件から導いた業務上の事実、エンティティ、値オブジェクト、状態遷移、集約境界をMVPのドメインモデルとして確定する。
- 将来機能のためだけにMVPのモデルを複雑化しない。
- 単一店舗のMVPとして設計するが、主要な業務データは店舗との所属関係を明示する。
- MVPでは独立した顧客エンティティを作らず、予約者の氏名と電話番号を予約時点の連絡先として各予約に保持する方針は確定済みとする。
- 具体的なテーブル名、カラム、外部キー、インデックス、PostgreSQL制約は後続のデータベース設計で確定する。

## 3. 用語

| 用語 | 意味 |
| --- | --- |
| 予約者 | 予約時に氏名と電話番号を提供する人物。MVPではログインアカウントを持たない |
| 予約 | 通常予約または貸切予約を表す業務上の約束 |
| 通常予約 | 1名から12名、開始時刻10分単位、標準利用時間90分の予約 |
| 貸切予約 | 店舗全体、エリア、テーブルを対象とし、イベント時間と準備・片付け時間を持つ予約 |
| 予約なし利用 | 事前予約を持たない顧客について、スタッフが来店時に登録する現在の席利用 |
| 営業日 | 店舗が営業を開始した日。日付をまたぐ深夜営業では実際の暦日と異なる場合がある |
| 席配置 | 予約または予約なし利用へ割り当てた物理テーブルと配置場所の組み合わせ |
| 例外案件 | 通常操作で状態を直接変更せず、事実記録、提起、後日の審査を必要とする案件 |
| 無断キャンセル履歴 | 管理責任者が確認し、予約状態を `no_show` にした確定済みの履歴 |

## 4. ドメイン領域

```text
予約 ───────────────┐
  │                 │
  ├─ 営業カレンダー ─┤─ 予約可否の判定
  │                 │
  └─ 席配置 ─────────┘─ 席資源の確保と再配置

予約なし利用 ──────── 席配置 ── 現在の席資源の占有

スタッフ権限 ────────── 各操作の認可
例外審査 ───────────── 通常では訂正できない事実の提起と確定
監査・保持 ──────────── 操作証跡、匿名化、削除保留、定期削除
```

### 4.1 予約領域

予約番号、予約者の連絡先、日時、人数、状態、取消、確認コード、QRチェックイントークンを管理する。
通常予約と貸切予約は共通の予約を土台とし、予約種別ごとの詳細を分けて管理する。
予約として共通する識別、予約者連絡先、基本状態、取消、監査を共有しながら、利用時間、人数上限、対象範囲、作成権限などの条件は通常予約と貸切予約で分離する。
予約番号、確認コード、QR来店確認、基本状態は両方の予約種別へ適用するが、オンライン取消と変更・キャンセル権限は種別ごとに分ける。

### 4.2 席配置領域

物理テーブル、移動可能エリア、配置場所、連結可能関係、予約ごとの席配置を管理する。
予約なし利用についても、受付日時から必要な終了後転換時間の終了日時までの席配置と占有を管理する。
新規予約または予約なし利用によって既存予約を再配置する場合は、関係する配置を同じトランザクションで変更する。

### 4.3 営業カレンダー領域

曜日ごとの通常営業時間、定休日ルール、特別営業時間、臨時休業から、指定日時がどの営業日に属し、予約可能かを計算する。
MVPでは営業日を事前生成せず、保存したルールを正として都度評価する。

### 4.4 スタッフ権限領域

スタッフアカウントの認証、基本ロール、所属店舗、当日運用責任者の期限付き任命を管理する。
当日運用責任者は基本ロールを書き換えず、対象営業日と有効期間を持つ任命として扱う。

### 4.5 例外審査領域

来店資格確認の異常、予約なし利用の記録訂正、無断キャンセル審査、臨時休業による要対応を、予約または予約なし利用の基本状態と分離して管理する。
共通の例外案件集約を使いながら、履歴訂正を伴う審査と、システムが矛盾解消を確認できる要対応を案件種別と状態遷移で区別する。

### 4.6 監査・保持領域

業務操作の変更前後、操作者、理由を追記型の履歴として保存する。
個人情報の保持期限、匿名化、削除保留、日次削除ジョブの実行履歴を扱う。

## 5. エンティティ

エンティティは、属性が変化しても同一性を追跡する必要がある概念とする。

| エンティティ | 識別の単位 | 主な責務 |
| --- | --- | --- |
| 店舗 | 店舗ID | タイムゾーンと店舗単位の整合性を支える |
| スタッフアカウント | スタッフID | 認証情報、基本ロール、所属店舗、有効状態を管理する |
| 当日運用責任者任命 | 任命ID | 対象営業日、就任、承認、引き継ぎ、緊急就任、失効を管理する |
| 予約 | 予約ID | 予約番号、予約種別、予約者情報、日時、状態、資格情報を管理する |
| 無断キャンセル電話照合 | 予約ID、鍵バージョン、正規化方式バージョン | 確定済み無断キャンセルの店舗内電話番号照合値、正規化方式、鍵バージョン、保持期限を管理する |
| 通常予約詳細 | 予約ID | 人数、標準利用時間、コメントなど通常予約固有の情報を管理する |
| 貸切予約詳細 | 予約ID | イベント時間、準備・片付け時間、参加人数、貸切範囲を管理する |
| 貸切対象エリア | 予約IDとエリアID | 店舗全体以外の貸切が対象とする移動可能エリアを管理する |
| 貸切対象テーブル | 予約IDと物理テーブルID | 店舗全体以外の貸切が対象とする個別の物理テーブルを管理する |
| 予約なし利用系列 | 利用系列ID | 通常受付と誤終了後の継続区間をまとめ、保持期限と物理削除の単位を管理する |
| 予約なし利用 | 予約なし利用ID | 系列内の1利用区間として、人数、受付、準備、利用開始、予定・実際の終了、状態、登録スタッフ、継続元との関係を管理する |
| フロア | フロアID | 店舗内の階と、移動可能エリアの所属先を管理する |
| 移動可能エリア | エリアID | 1フロア内でテーブルが越えて移動できない境界と貸切対象を管理する |
| 物理テーブル | テーブルID | 実在する什器として、定員、固定・可動、所属エリア、有効状態を管理する |
| 配置場所 | 配置場所ID | テーブルを置ける事前確認済みの論理的位置として、所属エリア、表示順、固定席との関係を管理する |
| 席資源ブロック | ブロックID | 物理テーブルまたは配置場所が一時的に使用できない期間、理由、開始・解除操作を管理する |
| 連結可能関係 | 2つの配置場所の組 | 直接連結できる配置場所の隣接関係を管理する |
| 席配置計画 | 席配置計画ID | 予約または予約なし利用との対応、現在世代番号、世代の切り替えを管理する |
| 席配置世代 | 席配置計画IDと世代番号 | ある時点の決定区分、転換時間、占有期間、変更原因を不変のスナップショットとして管理する |
| 席割り当て | 席割り当てID | 1つの席配置世代に含まれる物理テーブルと配置場所の組を管理する |
| 営業時間ルール | 営業時間ルールID | 曜日、開始時刻、終了時刻、終了日の繰り越しを管理する |
| 定休日ルール | 定休日ルールID | 毎週型または月内週番号型の休業規則を管理する |
| 特別営業時間 | 特別営業時間ID | 特定営業日の通常営業時間を置き換える時間帯を管理する |
| 臨時休業 | 臨時休業ID | 単一日または日付範囲の終日休業と理由を管理する |
| 例外案件 | 例外案件ID | 対象、種別、事実、当日対応、提案、審査状態、決定内容、訂正対象間の関係を管理する |
| 監査記録 | 監査記録ID | 操作主体、対象、変更前後、理由、実行日時を保存する |
| 削除保留 | 削除保留ID | 対象、理由、設定者、見直し期限、解除を管理する |
| 定期削除実行 | 実行ID | 実行予定日、開始・終了、結果、処理件数を管理する |

MVPでは顧客を独立したエンティティにしない。
予約者は予約集約内の予約者連絡先として表現し、同じ氏名または電話番号を持つ複数予約を同一人物へ自動統合しない。

## 6. 値オブジェクト

値オブジェクトは、独立した識別子よりも値と検証規則に意味がある概念とする。

| 値オブジェクト | 含む値・規則 |
| --- | --- |
| 予約番号 | 先頭11桁の暗号学的乱数と末尾1桁のLuhnチェックディジットからなる12桁文字列。店舗内で一意とし、予約終了から3年後に自動解放する |
| 予約確認コード | 暗号学的乱数から生成する8桁の数字。予約と世代に結び付け、専用秘密鍵によるHMAC-SHA-256で保存する |
| チェックイントークン | 32バイトの暗号学的乱数をURL安全なBase64形式で表した来店専用値。SHA-256ダイジェストだけを保存する |
| 予約者連絡先 | 予約時点の氏名とE.164形式へ正規化した電話番号。正規化前の入力値は別に永続化しない |
| 電話番号照合値 | 用途識別子、店舗ID、E.164形式の電話番号を専用秘密鍵でHMAC-SHA-256処理した値、鍵バージョン、正規化方式バージョン |
| 予約期間 | タイムゾーン付き開始日時と終了日時。開始より終了が後であることを保証する |
| 予約なし利用期間 | サーバー受信時刻を使う受付日時、必要な準備時間から求める予定利用開始日時、60分以上180分以下・10分単位の予定利用時間、予定・実際の終了日時 |
| 営業日 | 店舗タイムゾーン上の営業開始日 |
| 営業時間帯 | ローカルの開店、最終入店、ラストオーダー、閉店の各時刻と日付繰り越し値。経過分数へ変換した順序を保証する |
| 人数 | 通常予約と予約なし利用では1名以上12名以下。貸切では対象範囲の収容人数以下 |
| 準備・片付け時間 | それぞれ0分以上180分以下、10分単位 |
| 大人数転換時間 | 店舗初期値10分。予約確定時の適用値を席配置計画へ固定する |
| 席配置決定区分 | `automatic`、`flexible`、`fixed` のいずれか |
| 席配置世代番号 | 席配置計画ごとに1から始まり、変更のたびに1増える正の整数 |
| 例外案件種別 | `arrival_issue`、`walk_in_record_correction`、`no_show_review`、`temporary_closure_response` のいずれか |
| 例外案件状態 | `open`、`proposed`、`approved`、`rejected`、`resolved` のいずれか |
| 操作理由 | 例外操作、固定決定、再変更などで空文字を許さない理由 |

## 7. 集約

集約は、1つのトランザクションで必ず整合させる変更単位として扱う。

### 7.1 予約集約

**確定**

- 予約を集約ルートとする。
- 予約は、店舗、予約番号、予約種別、予約者連絡先、基本状態、作成日時、取消情報など、通常予約と貸切予約に共通する情報を持つ。
- 予約の所属店舗は作成後に変更しない。誤った店舗の予約は別店舗へ付け替えず、取消後に正しい店舗で作成する。
- 1つの予約は、通常予約詳細または貸切予約詳細のどちらか一方だけを持ち、予約種別と詳細の種類を一致させる。
- 通常予約詳細は、開始日時、人数、標準利用時間、顧客コメントなどを持つ。
- 貸切予約詳細は、イベント開始・終了日時、準備・片付け時間、参加人数、対象範囲種別などを持つ。
- 貸切範囲は店舗全体または部分選択とし、部分選択では1つ以上の移動可能エリアまたは物理テーブルを関連付ける。複数選択とエリア・テーブルの混在を許可するが、選択済みエリア内の物理テーブルを重ねて個別指定しない。
- 貸切範囲の収容人数は、店舗全体なら店舗内、部分選択なら選択エリアに所属する物理テーブルと個別選択した物理テーブルの和集合から算出する。同じ物理テーブルを二重計上しない。
- すべての種別固有項目を1つの予約へ詰め込み、多数の未使用項目を `null` にする構造は採用しない。
- 通常予約と貸切予約は、作成API、操作権限、入力検証、受付ポリシーを分けることができる。共通の予約集約を使うことは、業務ルールまで同一にすることを意味しない。
- 予約確認コードのハッシュと現在有効なチェックイントークンのハッシュを、通常予約と貸切予約の両方で予約集約内に保持する。DBでは予約本体と別の1対1従属テーブルへ分離し、独立した集約またはAPIリソースにはしない。
- 貸切の確認コードは作成または再発行直後に管理責任者または管理者へ1回だけ返し、通常スタッフまたは後続の取得処理から平文を参照できないようにする。
- 予約の状態変更は、任意の値を設定する更新ではなく、来店確認、利用完了、取消、無断キャンセル確定という業務操作を通じて行う。
- 管理責任者または管理者が `no_show` を確定するトランザクションで、予約時点の正規化電話番号から無断キャンセル電話照合を作成する。候補または却下された案件からは作成しない。
- 無断キャンセル電話照合は予約集約に従属し、照合値、鍵バージョン、正規化方式バージョン、作成日時、保持期限を持つ。鍵または正規化方式の更新中は同じ予約へ複数バージョンを一時的に関連付けられるが、保持期限を開始し直さない。
- 承認済みの訂正によって `no_show` を取り消す場合は、予約状態の訂正とすべての無断キャンセル電話照合の削除を同じトランザクションで行う。
- 席配置は複数予約を同時に再配置する必要があるため、予約集約の内部へ完全には含めない。
- 例外案件は予約の基本状態と独立した審査ライフサイクルを持つため、別集約とする。

この構造は、Pythonのクラス継承またはORMの継承マッピングを採用することまで決めるものではない。
データベースでは共通の予約と種別別の詳細を関連付ける構成を基本候補とし、具体的な制約はDB設計で確定する。

### 7.2 予約なし利用系列集約

**確定**

- 予約なし利用系列を予約とは別の内部集約ルートとし、個々の予約なし利用を系列内の利用区間として扱う。通常受付では系列と最初の利用を同時に作成し、通常は1系列1利用になる。
- 誤終了または誤中止後の占有継続だけを同じ系列へ追加する。13名以上を分割した各利用、収容人数を超えた追加参加者の別受付は、それぞれ新しい系列とする。
- 13名以上の一括受付では、分割した系列同士を業務上の団体として結び付けない。同じ受付操作だったことは、監査記録と席配置世代へ共通の `operation_id` を記録して追跡する。
- 1名から4名は受付時に `active`、5名以上は受付時に `preparing` として作成する。5名以上は受付確定を準備開始として扱い、別の準備開始操作または準備開始日時を持たない。
- 人数、登録日時（通常受付では受付日時）、予定利用開始・終了日時、実際の利用開始・終了日時、登録・操作スタッフを保持する。予定利用時間は予定開始・終了の差から求め、分数列へ重複保存しない。
- 5名以上の予定利用開始日時は受付日時へ大人数転換時間を加えて求め、予定終了日時は予定利用開始日時へ予定利用時間を加えて求める。
- `preparing` の席は作成時から確保し、予定利用開始日時以降に通常スタッフが `active` へ変更する。開始が遅れても予定終了日時を自動延長しない。
- `preparing` の受付中止は理由を必須として `aborted` にし、元の記録を削除しない。
- `preparing` または `active` の現在人数は1名以上12名以下とし、変更前の人数は監査履歴に残す。
- 減員しても席配置計画を縮小せず、増員は現在の席配置計画の収容人数以内に限定する。`preparing` 中に5名未満へ減っても、状態、予定利用開始日時、適用済み転換時間を変更しない。
- 現在の席配置で収容できない追加参加者は、別の予約なし利用として扱う。
- 予定利用時間は受付時に確定し、`active` になった後は延長または短縮しない。
- 90分未満の場合は、受付確定前に顧客へ終了予定時刻を案内し、受付を確定した登録スタッフを案内確認スタッフとして、受付日時と同じDB時刻の案内確認日時を保持する。
- 氏名、電話番号、予約番号、予約確認コード、チェックイントークンを持たない。
- 利用終了操作によってだけ `completed` へ遷移し、実際の終了日時と操作スタッフを記録する。
- 予定終了日時を過ぎても自動終了せず、`active` のまま割り当てた席を占有する。
- 5名以上は `completed` になった後も、実際の終了日時から受付時に確定した大人数転換時間が経過するまで席配置計画による占有を続ける。
- 予定・実際の利用日時は予約なし利用本体、適用した利用前・利用後転換時間と席の占有期間は席配置世代を正とする。転換時間を本体へ重複保存せず、新しい席配置世代と占有継続行へ受付時の値を引き継ぐ。
- 実際の終了から求めた占有終了が既存の後続予約と重なっても、実終了を拒否せず現実の競合として保存する。重なりは強い警告にし、解消まで追加の新規割り当てを拒否する。
- 予約なし利用の受付と席配置計画の作成は、同じアプリケーショントランザクションで成立させる。
- `preparing` または `active` の人数訂正と、権限および理由を伴う利用中の席移動は、現在の利用実態を合わせる通常操作とし、変更前後を監査履歴へ残す。
- `completed` または `aborted` は通常操作で元へ戻さず、過去記録の訂正を `walk_in_record_correction` で扱う。
- 誤終了後も利用が続く場合は、当日運用責任者以上が `walk_in_record_correction` を提起し、元と同じ系列へ元を継続元として参照する新しい利用を作成する。`completed` の継続先は `active`、`aborted` の継続先は現場の実態に応じて `preparing` または `active` とする。
- 新しい利用は現在人数、元の予定開始・終了日時、短時間案内確認および適用済みの前後転換時間を引き継ぎ、新しい標準利用時間を与えない。
- 継続元参照は同一店舗・同一系列内で不変とし、1つの元からの分岐、複数の元からの合流、循環を許可しない。これは13名以上の一括受付を恒久的に同一団体として結び付ける関係とは異なり、誤操作後の占有継続にだけ使用する。
- 同じ物理席を実際に使用中なら、別の予定へ再割り当て済みでもその占有事実を保存する。既存予定は上書きせず、競合を強く警告して解消まで追加の新規割り当てを拒否する。別席へ移動済みなら実際の移動先を保存する。
- 訂正の承認後も元の利用と終了操作を削除せず、承認済み継続関係でつながる区間を集計上は1回の連続利用として扱う。却下時も系列と関係を削除せず、却下された関係の前後を集計上は別利用として扱う。
- 予約なし利用本体、人数、利用日時、席配置、監査履歴は、利用系列内の最新の確定終了または案件終了から3年保持し、期限後は系列単位で個別記録を削除する。
- 利用系列を保持期限と物理削除の単位とし、系列内のすべての利用と案件が終了した最も遅い日時を保持起算点にする。未終了利用、未解決案件または削除保留があれば系列全体を削除しない。

### 7.3 席配置計画集約

**確定**

- 予約または予約なし利用ごとの席配置計画を集約ルートとし、対象との関係と現在世代番号を管理する。
- 店舗の席構成は、フロア、移動可能エリア、物理テーブル、配置場所を別エンティティとして扱う。エリアは1フロア、物理テーブルと配置場所は1エリアに所属し、物理テーブルおよび配置場所のフロアはエリアから求める。
- 単一フロアMVPでもフロアを店舗へ埋め込まず、固定テーブルだけを含むエリアも許可する。正確な座標は持たず、店舗が登録したエリア境界と連結可能関係を正とする。
- 4つの席構成マスターは、店舗内で各種別を識別するコード、表示名称および親の範囲内で一意な表示順を持つ。名称は重複でき、画面ではコードを併記する。
- 表示順は一覧と自動配置の最終決定順に使用し、コードの辞書順や内部UUID順を業務上の優先順位にしない。
- 物理テーブルまたは配置場所の一時的な使用不能を期間付きの席資源ブロックとして席構成マスターから分離する。ブロック中もマスターと作成済み席配置を維持し、期間が重なる新しい割り当てだけから除外する。
- ブロックによって現在世代が影響を受ける予約または予約なし利用は、現在世代とブロックの重なりから要対応として導出する。警告を消すためだけの状態列を予約本体へ重複保存しない。
- 1つの席配置計画は、予約または予約なし利用のどちらか一方だけを対象とし、対象ごとに1つだけ作成する。
- 席配置計画は、世代番号、決定区分、固定理由、適用した前後の転換時間、占有開始・終了日時、作成理由、操作者、作成日時、原因操作識別子を持つ席配置世代を含む。
- 各席配置世代は、物理テーブルと配置場所の組を席割り当てとして含み、同じ世代内で同じ物理テーブルまたは配置場所を重複させない。
- 最初の配置を第1世代とし、配置、決定区分、転換時間、占有期間のいずれかを変更するたびに、現在世代を上書きせず次の世代を追加する。
- 過去と同じ配置へ戻す場合も新しい世代を作り、過去世代を再び現在世代にはしない。
- 作成済みの席配置世代と席割り当ては不変とし、変更前の完全な配置を構造化された履歴として残す。
- 席配置計画は現在世代を必ず1つだけ指し、空席検索、競合判定、自動再配置、スタッフ画面では現在世代だけを有効な席占有として扱う。
- 受付時に競合する計画同士は重複させないが、時間超過した予約なし利用の実績を反映する新世代だけは、既に確定した後続予定との重なりを保存できるようにする。これは新しい受付による重複許可ではなく、現実の競合を記録して警告・追加割り当て拒否へ使う例外である。
- 過去世代は履歴確認専用とし、現在の席重複制約または空席判定へ含めない。
- 複数予約と予約なし利用を自動再配置する場合は、席割り当てサービスが各計画の新世代を作り、すべての現在世代切り替えを同じトランザクションで成立させる。
- 一括変更には共通する原因操作識別子を付け、どの新規予約または予約なし利用によって複数計画が変更されたか追跡できるようにする。
- 席配置世代は配置そのものの業務履歴とし、監査記録は誰が、なぜ、どの操作を実行したかを記録する。どちらか一方だけで代用しない。

### 7.4 営業カレンダー集約

**確定**

- 店舗を整合性確認の起点とし、通常営業時間、定休日ルール、特別営業時間、臨時休業を店舗単位で扱う。
- 通常営業時間または特別営業時間の変更時は店舗をロックし、前後の営業日、既存予約、`preparing` または `active` の予約なし利用への影響を同じトランザクションで検証する。
- 通常の営業時間変更によって既存利用を営業時間外にせず、緊急停止だけは臨時休業として既存利用を残したまま登録できる。
- 実際の営業日は保存済みエンティティではなく、規則から計算する結果として扱う。
- 店舗コードは作成後に変更せず、店舗タイムゾーンはタイムゾーン依存業務データを初めて作成した時点でロックする。ロック後の通常変更と、関連行削除によるロック解除は行わない。

### 7.5 スタッフアカウント集約

**確定**

- スタッフアカウントを集約ルートとし、所属店舗、店舗内ログインID、表示名、基本ロール、有効状態、無効化・匿名化日時を管理する。
- 1人のスタッフへ1つの個別アカウントを発行し、共有アカウント、DB接続主体、定期ジョブなどをスタッフとして扱わない。
- 基本ロールは `staff`、`manager`、`admin` とする。当日運用責任者は基本ロールへ追加せず、対象営業日の任命による権限を基本ロールへ合成する。
- MVPでは全アカウントを1店舗へ必ず所属させ、所属店舗を作成後に変更しない。複数店舗兼務が必要になった場合は、アカウントと店舗所属を分けた関連へ移行する。
- `admin` は同じ店舗のスタッフアカウントを作成、参照し、表示名、ログインID、基本ロール、有効状態および資格情報を、用途別の限定操作で管理できる。任意項目を一括更新する汎用操作と物理削除は提供しない。
- 自分自身の無効化・降格と、店舗で有効かつパスワード設定済みの最後の `admin` の無効化・降格・管理者用パスワード再設定を拒否する。管理操作は対象店舗をロックして再検証し、同時操作でも利用可能な管理者を0人にしない。自分のパスワードには本人用変更操作を使用する。
- パスワード資格情報、初回・再設定トークン、ログイン失敗状態、セッションをスタッフアカウント本体から分離する。有効なアカウントは設定待ちまたは利用可能な資格情報を1件持ち、無効なアカウントは資格情報を持たない。
- 無効化はパスワード資格情報、設定トークン、ログイン失敗状態の削除と全セッション失効を、再有効化は設定待ち資格情報、新しい設定トークン、全セッション失効を同じトランザクションへ含める。以前のパスワードは復元しない。
- ログインIDまたは基本ロール変更、パスワード変更・再設定は理由と変更前後を監査し、全セッションの失効を同じトランザクションへ含める。スタッフ管理の変更操作は10分以内のパスワード再確認を要求する。
- 再認証は現在のセッションを作り直さず、同じセッションの不透明トークンを交換して再認証日時と最終利用日時を同じDB時刻へ進める。作成日時と12時間の絶対期限は維持し、旧トークンを直ちに無効化する。
- 無効化後も過去の操作主体を内部スタッフIDで参照できるよう行を物理削除せず、無効化から3年後にログインIDと表示名を匿名化する。匿名化後は再有効化せず、新しいアカウントを作成する。

### 7.6 当日運用責任者任命集約

**確定**

- 任命を集約ルートとし、対象店舗、対象営業日、担当スタッフ、有効期間、任命方法、成立操作を行ったスタッフ、および開始済みの交代では直前の任命を持つ。
- 任命期間を `[開始日時, 終了日時)` とし、同じ店舗の取消されていない期間が重ならないことをPostgreSQLの排他制約で保証する。DBでは最大1名を保証し、最低1名は警告と緊急就任で補う。
- 営業日前の通常任命は最初の開店を開始候補とし、即時任命はDBサーバー現在日時から開始する。通常の終了上限は対象営業日の最後の閉店から2時間後とし、締め作業を行えるようにする。
- 開始前の予定変更は取消履歴を残して新しい任命を作る。引き継ぎでは、前任の終了と後任の開始を同じ時刻、同じトランザクションで成立させる。
- 任命中のスタッフを無効化または管理者用パスワード再設定待ちにする場合は、現在任命の終了と将来任命の取消を資格情報・セッション処理へ含める。
- 任命方法は、管理者任命、後任承認を伴う引き継ぎ、理由と再認証を伴う緊急就任の3種類とする。引き継ぎまたは緊急就任では成立操作を行うスタッフと任命対象者を同一人物とする。
- 引き継ぎ依頼を任命とは別の従属エンティティとし、前任任命、依頼者、後任候補、15分の有効期間、終了結果および成立した後任任命を持つ。依頼中は後任候補に権限を与えない。
- 後任候補が10分以内のパスワード再確認を満たして承認した場合だけ、前任任命の終了と後任任命の作成を原子的に行う。期限切れ、取消または別の交代で無効になった依頼は成立させない。
- 緊急就任情報を緊急任命と1対1の従属エンティティとし、必須の就任理由、事後確認期限、確認結果、確認者、確認日時および確認理由を持つ。
- 緊急就任は同じ店舗の有効かつパスワード設定済みのスタッフ本人が直前10分以内に再認証して即時に成立させる。既存の任命があれば、その終了と緊急任命の開始を同じDB時刻で記録する。
- 緊急就任の事後確認期限は次の営業日の最後の閉店から2時間後とする。次の営業日を解決できない場合は就任から72時間後を期限とし、計算根拠と営業カレンダー設定警告を残す。就任者本人以外の管理責任者または管理者が `confirmed` または `unjustified` を記録し、期限超過は警告対象とするが自動失効または自動却下にしない。
- `unjustified` は緊急手続きが不適切だったことを示し、まだ有効な任命は確認時点で終了する。ただし、過去の任命と任命中の操作を遡って削除または無権限扱いにせず、必要な操作を個別に確認・訂正する。
- 任命と手続きの構造化された業務履歴を共通監査ログで代用しない。共通監査ログには各操作の主体、日時、理由、対象IDおよび変更前後を追記し、現在の権限判定は任命の有効期間から行う。

### 7.7 例外案件集約

**確定**

- 例外案件を集約ルートとし、対象予約または予約なし利用、関連する臨時休業、案件種別、報告事実、当日の対応、提案、審査結果を持つ。
- 案件種別は `arrival_issue`、`walk_in_record_correction`、`no_show_review`、`temporary_closure_response` の4種類とする。
- 予約の来店資格確認と予約なし利用の記録訂正は同じ集約を使うが、正常操作と訂正結果が異なるため別の案件種別とする。
- 通常スタッフ、当日運用責任者またはシステムによる `open`、当日運用責任者による `proposed`、管理責任者または管理者による `approved` または `rejected` を順序のある操作として扱う。予約の予定終了から30日後の時刻に達した未解決の `no_show_review` だけは、日次処理が判断不能として `rejected` にできる。
- 当日運用責任者は営業中の事実と対応を記録して提起できるが、確定済みの予約状態または過去の予約なし利用を最終訂正できない。
- 臨時休業との矛盾解消または後からの通常来店確認など、解消条件をシステムが検証できる場合は、承認を経ず `resolved` にできる。任意の手動操作で `resolved` にすることは許可しない。
- `walk_in_record_correction` と `no_show_review` は `open` から `proposed`、その後 `approved` または `rejected` へ進む。
- `arrival_issue` は、履歴訂正が必要なら同じ審査経路を使い、通常の来店資格確認だけで解消した場合は `open` または `proposed` から `resolved` へ進む。
- `temporary_closure_response` は `open` から `resolved` へだけ進み、提起、承認、却下の状態を使用しない。
- 予約の予定終了から30日後の時刻に達した未解決案件では、`no_show_review` は顧客ペナルティなしで `rejected`、`temporary_closure_response` は店舗都合キャンセルによる矛盾解消で `resolved` とし、対象予約を店舗側の管理終結による `cancelled` にする。無断キャンセル電話照合は作成しない。
- `open` または `proposed` の案件が対象に存在するかどうかを、`review_required` という派生値として判定する。
- 承認によって予約または予約なし利用の訂正が必要な場合は、例外案件と対象データを同じアプリケーショントランザクションで更新し、元の操作を残したまま訂正記録と監査記録を追加する。
- `approved`、`rejected`、`resolved` は終了状態とし、終了後の判断変更は元の案件を上書きせず、関連する新しい案件として記録する。

### 7.8 削除保留集約

**確定**

- 削除保留を対象データとは別の集約として管理し、理由、設定者、見直し期限を必須にする。
- 定期削除ジョブは削除対象を選ぶときに、有効な削除保留が存在しないことを確認する。
- 削除保留を設定または解除できるのは管理責任者または管理者だけとし、操作を監査履歴へ残す。
- 予約なし利用系列に削除保留対象が1件でも含まれる場合は、系列、すべての利用、席配置、監査履歴、例外案件を削除しない。

## 8. 予約と予約なし利用の状態遷移

```text
                       来店確認
confirmed ─────────────────────────→ checked_in
    │                                      │
    │ 顧客・店舗都合の取消                 │ 利用完了
    ↓                                      ↓
cancelled                              completed
    │
    └─ 終了状態

confirmed ── 管理責任者による確定 ──→ no_show
                                           │
                                           └─ 終了状態

予約なし利用（1～4名）：active ── 利用終了 ──→ completed

予約なし利用（5名以上）：preparing ── 利用開始 ──→ active ── 利用終了 ──→ completed
                              │
                              └─ 理由付き受付中止 ──→ aborted
```

- 作成成功時の状態は `confirmed` とする。
- 定義済みの前向き遷移は `confirmed -> checked_in`、`confirmed -> cancelled`、`confirmed -> no_show`、`checked_in -> completed` だけとし、アプリケーションの専用操作とDB更新トリガーの両方で守る。`confirmed -> no_show` には承認済みの `no_show_review` と電話照合値も要求する。
- `confirmed -> cancelled` には顧客・店舗による通常取消に加え、予定終了から30日後の未解決案件を日次処理が店舗側の管理終結として閉じる経路を含める。後者を顧客都合または確定済み無断キャンセルとして扱わない。
- `cancelled`、`completed`、`no_show` は通常操作で元へ戻さない。
- 来店記録の訂正などが必要な場合は、元の操作を削除せず、例外案件の承認と訂正記録を追加する。
- `review_required` は予約の基本状態へ追加せず、未解決の例外案件が存在することから判定する。
- 予約なし利用は人数に応じて登録と同時に `preparing` または `active` とし、予約の来店確認、キャンセル、無断キャンセル状態を使用しない。
- `aborted` は `preparing` だけから遷移できる利用前中止であり、予約の `cancelled` とは区別する。
- 予約なし利用の `completed` と `aborted` は通常操作で元へ戻さず、誤操作は `walk_in_record_correction` と、必要に応じて作成する関連済みの新しい予約なし利用によって訂正する。
- 予約の誤った来店確認も通常の逆遷移として扱わず、`arrival_issue` の承認時に元の操作を残した訂正記録を追加する。

## 9. ドメインサービス

複数の集約または外部の現在時刻を参照しなければ判断できない処理は、エンティティへ無理に押し込まずドメインサービスまたはアプリケーションサービスで調整する。

| サービス | 責務 |
| --- | --- |

## 10. 集約をまたぐ重要なトランザクション

### 10.1 通常予約の作成

1. 冪等性キーの再利用を確認する。
2. 対象店舗をロックし、営業日、臨時休業、受付期限を最新状態で判定する。
3. 競合する予約、席配置計画、物理テーブル、配置場所を一定順序でロックする。
4. 通常割り当てを試し、必要な場合だけ既存予約を含む再配置を計算する。
5. 新規予約の席配置計画と第1世代、再配置する既存計画の新世代、すべての現在世代切り替え、予約資格情報、監査記録を一括で保存する。
6. 一部でも失敗した場合は全体をロールバックする。

### 10.2 貸切予約の作成

1. 操作者が管理責任者または管理者であることを確認する。
2. 対象店舗をロックし、イベント時間、準備・片付け時間、対象範囲、収容人数、営業時間、臨時休業を検証する。
3. 対象範囲と競合しうる予約、予約なし利用、席配置計画、物理テーブル、配置場所を一定順序でロックして再取得する。
4. `preparing`、`active`、利用終了後転換時間中を含めて競合がなければ貸切予約と監査記録を保存し、競合があれば何も作成しない。

### 10.3 予約なし利用の受付

1. 操作者が有効なスタッフであることを確認する。
2. 対象店舗をロックし、サーバーの現在日時を受付日時として、営業状態、人数に応じた予定利用開始日時、予定利用時間、予定終了日時、転換時間を検証する。90分未満では同じ操作主体とDB時刻で案内済み確認も記録する。
3. 競合する予約、予約なし利用、席配置計画、物理テーブル、配置場所を一定順序でロックする。
4. 席候補を探索し、必要な場合だけ来店前の既存予約を含む再配置を計算する。
5. すべての予約と予約なし利用を維持できる場合だけ、1名から4名は `active`、5名以上は `preparing` として、予約なし利用の席配置計画と第1世代、再配置する既存計画の新世代、すべての現在世代切り替え、監査記録を一括で保存する。第1世代へ利用前・利用後転換時間と、受付から予定終了後の転換完了までの占有期間を保存する。

### 10.4 13名以上の予約なし利用の一括受付

1. 操作者が有効なスタッフであり、各分割人数が1名以上12名以下であることを確認する。
2. 対象店舗をロックし、営業状態を確認してから、分割した全件へ同じ受付日時を適用し、各件の人数、予定利用時間、転換時間から状態、予定利用開始日時、予定終了日時を求める。
3. 競合する予約、予約なし利用、席配置計画、物理テーブル、配置場所を一定順序でロックする。
4. 分割した全件と既存予約を維持できる席配置をまとめて探索する。
5. 全件を収容できる場合だけ、トランザクション内でUUIDv7の `operation_id` を1つ生成する。人数に応じた `preparing` または `active` の複数の予約なし利用、各席配置計画と第1世代、既存計画の新世代、すべての現在世代切り替えを作成し、すべての受付監査記録と作成・変更した席配置世代へ同じ `operation_id` を記録する。
6. 分割した各件には別の利用系列を作り、系列または予約なし利用本体へ一括受付IDを保存しない。`operation_id` を一括変更、状態遷移、認可または削除単位に使用しない。
7. 1件でも収容できない場合は、利用、席配置、監査記録を含む全体をロールバックする。冪等性キーは `operation_id` と区別し、再送時の対応はDB-45で確定する。

### 10.5 予約なし利用の利用開始

1. 操作者が有効なスタッフであり、対象が `preparing` で、予定利用開始日時以降であることを確認する。
2. 対象と席配置計画をロックし、席の占有が維持されていることを確認する。
3. 状態を `active` にし、実際の利用開始日時、操作スタッフ、監査記録を一括で保存する。
4. 予定利用開始日時を過ぎていても、予定終了日時は変更しない。

### 10.6 予約なし利用の席移動

1. 操作者が対象営業日の当日運用責任者、管理責任者、管理者のいずれかであり、移動理由が記録されていることを確認する。
2. 対象の予約なし利用、現在と移動先の席配置、競合する予約と予約なし利用を一定順序でロックする。
3. 安全条件、収容人数、転換時間、後続予約との競合を再検証する。
4. 全件を維持できる場合だけ新しい席配置世代を追加して現在世代を切り替え、変更前後、理由、操作者、操作日時を監査履歴へ保存する。

### 10.7 予約なし利用の利用終了

1. 操作者が有効なスタッフであり、対象が `active` であることを確認する。
2. 対象と席配置計画をロックし、実際の終了日時をサーバーの現在日時で記録して `completed` にする。
3. 5名以上では実際の終了日時へ受付時の大人数転換時間を加えた日時まで席の占有を残し、1名から4名では直ちに占有を終了する。
4. 既存予約の席配置は組み直さず、実際の占有終了日時を反映した新しい席配置世代、現在世代の切り替え、監査記録を一括で保存する。
5. 新しい占有終了が既存の後続予約と重なっても利用終了を拒否せず、現実の競合として確定して現在の席配置から強い警告を判定する。重なりが解消するまで、その席をさらに新しい利用へ割り当てない。

### 10.8 通常営業時間・特別営業時間の変更

1. 操作者の権限を確認し、必ず店舗を先にロックする。
2. 対象と前後の営業日の営業時間、特別営業時間、既存予約、`preparing` または `active` の予約なし利用を再取得する。
3. 変更後も既存予約と、`preparing` では受付日時から予定終了日時まで、`active` では受付日時から予定終了日時または現在日時の遅い方までが1つの連続営業時間帯へ収まることを検証する。
4. 受付後の予約なし利用は最終入店時刻だけを再判定せず、`completed`、`aborted`、終了後転換時間中は検証対象外とする。
5. 1件でも営業時間外になる場合は変更を保存せず、緊急停止が必要な場合は臨時休業操作へ切り替える。

### 10.9 臨時休業の登録

1. 操作者の権限を確認し、店舗をロックして対象営業日の予約と予約なし利用を再取得する。
2. 既存予約または `preparing`、`active` の予約なし利用が存在しても臨時休業を保存し、対象営業日の新規受付を停止する。
3. 既存予約は要対応として検出するが、予約なし利用ごとの例外案件は自動作成せず、未終了の店内利用があることを強い警告として判定する。
4. 予約なし利用の状態と席占有を変更せず、`preparing` の理由付き受付中止または `active` の利用終了を現場操作として残す。

### 10.10 例外案件の承認またはシステム解消

1. 承認または却下では管理責任者か管理者の権限を確認し、システム解消では案件種別ごとの解消条件を確認する。
2. 対象の例外案件と、対象となる予約、予約なし利用または臨時休業をロックする。
3. 提案内容または解消条件が対象データの現在状態にも適用可能か再検証する。
4. 例外案件の審査結果、必要な訂正、監査記録を一括で保存する。`no_show_review` の承認では、予約の `no_show` への変更と、現在の鍵バージョンによる無断キャンセル電話照合の作成も同じトランザクションへ含める。
5. 来店記録の訂正では、本来の予約者が利用したかに応じて正しい来店履歴を残し、利用していなければ訂正後に無断キャンセル審査へ回せるようにする。`checked_in -> confirmed` では、保持中の確認コードを維持し、新しいQRトークンのダイジェストと進めたQR世代も同じトランザクションで保存して、旧QRを復元しない。
6. 無断キャンセル候補の抽出と承認では、未解決の `temporary_closure_response` がないことをロック後に再検証し、存在する場合は候補化または承認を拒否する。
7. 日次処理では予定終了から30日後の時刻に達した未解決の `no_show_review` または `temporary_closure_response` と対象予約をロックし、案件終了、店舗側の管理終結、資格情報の失効および監査記録を同じトランザクションで保存する。

### 10.11 誤終了後の予約なし利用の占有継続

1. 操作者が対象営業日の当日運用責任者、管理責任者、管理者のいずれかであり、理由が記録されていることを確認する。
2. 店舗、利用系列、元の予約なし利用、既存の例外案件があればその案件、現在の実利用席と関連する席配置、競合する予約および予約なし利用を一定順序でロックする。
3. 元が `completed` または `aborted` で、直接の継続先がまだなく、同一系列の直列な継続関係を保てることを再検証する。`completed` なら継続先を `active`、`aborted` なら現場の実態に応じて `preparing` または `active` とする。
4. 未解決の `walk_in_record_correction` がなければ `open` として作成して `proposed` へ進め、既に `open` なら `proposed` へ進め、既に `proposed` ならその案件を使用する。元と同じ系列へ、元の現在人数、予定開始・終了日時、短時間案内確認、適用済みの前後転換時間を引き継いだ新しい利用を作成する。
5. 元の計画には占有終了を継続登録日時へ合わせる新世代を追加し、継続先の計画は同じ日時から占有を始める。元の席を実際に使用中なら既存予定との競合も事実として保存し、別席へ移動済みなら実際の移動先を保存する。既存予定を上書きせず、競合を強く警告して追加の新規割り当てを拒否する。
6. 元の利用、終了操作、元の席配置履歴を削除せず、元の予定終了日時を過ぎていれば新しい利用を直ちに時間超過として扱う。空き候補がないことだけでは処理を拒否しない。
7. 利用系列、継続先、例外案件、元・継続先の席配置世代および監査記録を一括で保存する。構造上の制約違反または保存失敗では全体をロールバックし、同じ元への並行操作は最大1件だけを確定する。

### 10.12 予約なし利用の保持期限処理

1. 日次削除ジョブが、最新の確定終了または案件終了から3年を経過した利用系列を候補として取得する。
2. 利用系列と、属するすべての利用、席配置、監査履歴、例外案件、削除保留を一定順序でロックして再取得する。
3. `preparing`、`active`、`open`、`proposed` または有効な削除保留が1件でもあれば、利用系列全体を今回の処理対象から外す。
4. 営業月、曜日、時間帯、人数帯などの統計を、一意な集計キーによる再計算または上書きで冪等に保存する。
5. 承認済みの継続関係でつながる区間は1回の連続利用、却下された関係の前後は別利用として集計する。個別利用を復元できる識別子、正確な日時、個別席、操作スタッフ、理由、自由記述を統計へ残さないことを確認してから、系列に属する個別記録を外部キー制約に従う順序で処理する。
6. 集計保存または削除の一部が失敗した場合は対象単位をロールバックし、次回のジョブで安全に再試行する。

### 10.13 電話番号照合鍵の更新

1. 新しいHMAC秘密鍵と鍵バージョンを、DB外のシークレット管理へ追加し、新規の無断キャンセル確定では新しい鍵を使用する。
2. 保持期限内の無断キャンセル電話照合を件数で区切って取得し、関連する予約の正規化電話番号から新しい鍵バージョンの照合値を作成する。新しい行へ元の保持期限をコピーし、鍵更新で保持期間を延長しない。
3. 同じ予約、鍵バージョン、正規化方式バージョンの再処理で重複値を作らない一意性を持たせ、途中失敗後も安全に再開する。
4. 移行中のスタッフ向け照合では、旧鍵と新鍵それぞれの候補値を計算する。公開予約作成処理では照合しない。
5. 保持対象の全件が新しい鍵へ移行したことを件数と検証処理で確認してから、旧鍵バージョンの照合値を削除し、最後に旧鍵を読み取り対象から外す。
6. 旧鍵を失った場合も予約受付を停止せず、保持中の正規化電話番号から新しい鍵の照合値を再生成する。再生成が完了するまでは旧値を照合できないため、警告機能の一時的な欠落として監視と運用手順へ通知する。

## 11. 主要な設計判断

### 11.1 顧客エンティティをMVPで作るか

**確定：独立した顧客エンティティを作らず、予約者連絡先を予約時点の値として予約に保持する。**

理由は次のとおりである。

- MVPの顧客はアカウントを持たず、電話番号だけでは同一人物と断定できない。
- 同じ電話番号の予約を1人の顧客へ自動統合すると、再割り当て、家族共用、誤入力によって別人の予約を誤って結び付ける。
- 氏名や電話番号が後から変更されても、過去の各予約で実際に受け付けた情報を保持する必要がある。
- 無断キャンセル警告には、独立した顧客IDではなく、保持期間内の電話番号照合値を使用できる。

この案では、同じ人物が複数回予約しても予約ごとに氏名と電話番号を保存する。
顧客アカウントを将来導入する場合は、予約時点の連絡先を残したまま、任意の顧客アカウントIDを予約へ関連付ける。

### 11.2 実用性評価

独立した顧客エンティティを作らない方式は、ログイン不要の単一店舗MVPでは実用に耐える。
予約時点の連絡先が各予約に残るため、電話受付と履歴確認を行いやすく、誤った顧客統合を避けられる。

一方、常連客の情報を一括更新すること、顧客単位の履歴表示、複数予約をまとめた本人確認には向かない。
これらが必要になった場合は顧客アカウントを追加するが、電話番号の一致だけで既存予約を自動的に同じアカウントへ統合しないことを条件とする。

### 11.3 後続設計への影響

- MVPの予約は、顧客IDを必須にせず、予約時点の氏名とE.164形式へ正規化した電話番号を保持する。正規化前の入力値は別に永続化せず、必要な表示形式は正規化済み番号から生成する。
- 電話番号照合値は検索と無断キャンセル警告のために使用するが、顧客の一意識別子または外部キーとして扱わない。
- 予約者名または電話番号を変更した場合は、その予約だけを更新し、同じ値を持つ別予約へ変更を波及させない。
- 将来顧客アカウントを導入する場合は、予約時点の連絡先を残したまま、予約から任意の顧客アカウントを参照できる構造を追加する。
- 既存予約と将来の顧客アカウントを、電話番号の一致だけで自動的に関連付けない。

### 11.4 通常予約と貸切予約の関係

**確定：共通の予約を集約ルートとし、通常予約詳細と貸切予約詳細を分ける。**

- 予約番号、店舗、予約者連絡先、基本状態、取消情報、監査対象としての識別を共通化する。
- 通常予約の90分利用、1名から12名、10分単位の開始時刻、自動席配置は通常予約詳細と専用ポリシーで扱う。
- 貸切の任意のイベント時間、準備・片付け時間、12名を超える参加人数、対象範囲、管理責任者以上の操作権限は貸切予約詳細と専用ポリシーで扱う。
- 顧客向け通常予約APIと管理責任者向け貸切APIは分け、どちらも確定後は共通の予約一覧と競合判定へ参加させる。
- 貸切の問い合わせ、見積り、相談中、期限付き仮押さえを将来追加する場合は、確定予約とは別のライフサイクルとして扱い、合意後に貸切予約へ変換する。

#### 実用性評価

現在のMVPで扱う貸切は、顧客との合意後に登録する確定済みの予約であり、通常予約と同じ店舗資源、時間帯、予約一覧、取消、監査へ関係する。
このため、共通の予約を土台とする方式は実際の店舗運用と競合防止に適している。

一方、種別判定がアプリケーション全体へ散らばると保守しにくくなるため、作成・変更・競合判定の種別固有ルールは専用のポリシーまたはサービスへ閉じ込める必要がある。
貸切が将来、見積り、契約、請求を含む営業案件へ拡張された場合も、確定前の営業案件を別に管理し、成立した結果だけを共通の予約へ登録する構造を維持できる。

### 11.5 貸切の資格情報と基本状態

**確定：貸切にも予約番号、予約確認コード、QR来店確認、基本状態を適用し、オンライン取消と変更・キャンセル権限は通常予約と分ける。**

- 貸切作成直後に、管理責任者または管理者へ予約番号、確認コード、QRコードを含む代表者受け渡し情報を1回だけ返す。
- 受け渡し情報は印刷またはコピーできるが、確認コードの平文を永続化またはログ出力しない。
- 代表者は予約番号と確認コードを使って公開ページからQRコードを再表示できる。
- 通常スタッフは確認コードの正解を閲覧できないが、代表者から受けたコードを検証し、QRの代替として来店確認に使用できる。
- 貸切の `checked_in` は参加者全員の出席ではなく、代表者を確認して団体の受け入れを開始したことを表す。
- 貸切にも `confirmed`、`checked_in`、`completed`、`cancelled`、`no_show` を使用する。
- 貸切を早く `completed` にしても、確定済みの準備開始から片付け終了までの資源占有期間は変えない。
- 貸切には10分以内のオンライン取消を適用せず、変更・キャンセルは管理責任者または管理者だけが行う。
- 確認コードを紛失した場合は、登録済み電話番号への折り返し後に、管理責任者または管理者が理由付きで確認コードとQRを再発行する。
- 再発行では旧確認コードと旧チェックイントークンを無効化し、新しい確認コードを1回だけ表示して監査履歴を残す。

#### 実用性評価

システムによるSMSまたはメール送信がなくても、対面、電話、印刷物、既存の連絡手段と公開QR再表示ページを組み合わせれば単一店舗のMVPとして運用できる。
スマートフォンを利用できない代表者も予約番号と確認コードで受付できる。

一方、作成担当者が受け渡しを完了しないまま画面を閉じると平文を再取得できないため、再発行操作と店舗側の復唱手順が必要になる。
貸切のQRは参加者管理または本人性を保証するものではなく、スタッフが会社・団体名と代表者名などを確認したうえで団体の受付を確定するための補助手段とする。

#### 通常予約の遅刻連絡と席解放

**確定：予約開始15分後ちょうどまで来店を受け付け、期限経過後の席解放と正式な無断キャンセル確定を分ける。**

- 遅刻連絡がない通常予約は、予約開始15分後ちょうどまで来店確認または遅刻連絡を受け付ける。期限を過ぎた後は予約による席確保を終了する。
- 来店する旨の連絡があった場合は、予約期間を変更せず到着予定日時を別に記録する。来店受付終了境界は元の終了日時の30分前とし、新しい来店期限は、到着予定日時の15分後と来店受付終了境界のうち早い方とする。
- 到着予定日時は来店受付終了境界以前とし、境界ちょうどの来店確認は許可する。スタッフは終了を延長しないこと、来店受付終了境界、残りの利用可能時間を顧客へ案内する。
- 来店期限以前に来店しない旨の連絡があった場合は顧客都合のキャンセルとして直ちに席を解放し、無断キャンセル候補にしない。期限経過後の連絡は審査資料として記録するが、元予約を復活または通常キャンセルへ変更しない。
- 無連絡で期限を過ぎた場合は席を解放するが、その場で基本状態を `no_show` へ変更しない。営業終了後の候補抽出と管理責任者の審査を経て正式に確定する。
- 解放後に来店した場合は、空席があるときだけ予約なし利用として受け付け、元の予約を復活させない。
- 席解放処理後は管理責任者または管理者の締切後例外権限でも、元予約の日時、人数、席、来店期限または基本状態を変更しない。事実追記、審査および定義済みの訂正記録は許可するが、元の席確保を復活させない。予定終了30日後の日次処理による `confirmed -> cancelled` は手動の例外変更ではなく、未解決案件を管理終結する専用のシステム遷移として許可する。
- 貸切にはこの自動席解放規則を適用しない。

#### 実用性評価

無連絡の予約席を90分間保持せず、15分の来店期限を過ぎた後から通常予約または予約なし利用へ再利用できる。連絡した顧客には到着予定時刻を基準に15分の猶予を与えつつ、元の終了日時と30分の最低利用可能時間を維持できる。

一方、期限付近の来店、電話連絡、別予約の確定が競合するため、画面表示だけで処理せず、サーバー時刻、予約行と席配置のロック、同一トランザクションによる再検証が必要になる。来店受付終了境界に近い到着予定では15分の猶予が短縮されるため、スタッフの明確な案内を必須とする。

### 11.6 来店受付時の口頭確認

**確定：QRまたは予約番号・予約確認コードの有効性確認に加え、来店者自身から予約情報を回答してもらい、一致しない場合は追加確認へ切り替える。**

- 有効なチェックイントークンは予約情報を所持していることを示すが、提示者本人であることは示さない。
- 通常予約では、スタッフが予約者名と予約時の人数を来店者へ尋ねる。
- 貸切予約では、会社・団体名と代表者名を来店者へ尋ねる。
- スタッフは画面に表示された正解を先に読み上げず、来店者の回答と照合する。
- 提示された来店資格情報が有効で、口頭回答も一致した場合に、スタッフが来店確認を確定する。
- 口頭回答が一致しない、または回答できない場合は確定せず、予約番号と予約確認コードによる追加確認へ切り替える。追加確認もできない場合は、当日運用責任者へ対応を提起する。
- 通常予約では予約時の人数と実際の来店人数を分けて扱う。人数の不一致だけでは不正とせず、予約時の人数を口頭確認した後に、実際の来店人数と対応内容を記録する。
- 貸切の参加人数は収容可否を判断する予定人数とし、代表者の来店確認を全参加者の出席確認にはしない。MVPでは実参加人数を記録しない。
- 通常予約の欠員は来店確認を妨げないが、遅れて来る参加者の可能性があるため、予約済みの席配置と占有枠を自動的には縮小しない。
- 通常予約の増員は、増員後も12名以下であり、他の確定予約を維持した席配置と必要な連結・転換時間を確保できることを席割り当てサービスで検証した後、当日運用責任者以上が承認する。
- 通常予約の増員に伴う予約人数と席配置の変更は、競合がないことを再検証し、同じトランザクションで確定する。条件を満たせない増員は受け付けない。
- 確定後に不正利用または取り違えの疑いが判明した場合は、来店状態を直接戻さず、例外案件として提起する。

#### 実用性評価

予約者名と予約時の人数を来店者側から答えてもらう手順は、受付の負担を大きく増やさず、別の予約のQRを誤って提示するなどの偶発的な取り違えを発見しやすくする。
人数変更を直ちに不正扱いしないため当日の欠員に対応でき、席の余裕と責任者の承認がある場合だけ増員も扱えるため、単一店舗のMVPとして運用可能である。

増員を無条件に認めると、後続予約の席やテーブル連結の転換時間を侵害する可能性がある。
再配置の成立確認と責任者承認を必須にすることで影響を抑えられるが、満席時には予約人数を超える来店者を断る運用説明が必要になる。

ただし、有効なQRと予約情報の両方を知る第三者を技術的に本人と区別することはできない。
より強い本人確認には身分証、顧客アカウント、SMS認証などが必要になるが、受付時間と顧客負担が増えるためMVPには含めない。

### 11.7 予約なし利用と予約の関係

**確定：予約なし利用は予約集約へ含めず、現在の席占有を表す独立した集約としてMVPへ含める。**

- 予約なし利用はスタッフが来店時にだけ作成し、予約用の資格情報と顧客連絡先を持たない。
- 席候補探索、連結、転換時間、競合制御は予約と共通化する。
- 予約なし利用の席配置は `preparing`、`active`、利用終了後の転換時間中は固定し、新規予約または別の予約なし利用による自動再配置の対象にしない。
- 利用終了によって実際の終了日時を記録し、必要な終了後転換時間が経過した時点で席の占有を終了する。

#### 実用性評価

予約なし利用を席候補探索へ含めることで、現場では使用中なのに予約システム上は空席として販売される問題を防げる。
顧客情報、待ち行列、注文、会計を扱わないため、予約APIの範囲を大きく広げずに最低限の実店舗運用へ対応できる。

一方、予定終了日時は見込みであり、実際の利用が延びれば後続予約と衝突する可能性がある。
MVPではシステムが退店を強制できないため、スタッフが後続予約を確認して予定時間を設定し、超過時に現場対応する必要がある。

### 11.8 最終入店とラストオーダー

**確定：営業時間帯ごとに最終入店と共通ラストオーダーを持ち、受付判定と注文案内の責務を分ける。**

- 通常予約の開始と予約なし利用の受付は最終入店日時以前、終了は閉店日時以前とする。
- 最終入店日時ちょうどの予約開始または予約なし利用受付と、閉店日時ちょうどの終了を許可する。5名以上の予約なし利用は受付後の予定利用開始が最終入店日時を過ぎてもよい。
- 日付をまたぐ時間帯では、最終入店とラストオーダーにも同日または翌日の繰り越し値を持たせる。
- 特別営業時間は最終入店とラストオーダーを明示的に設定する。
- 貸切には最終入店とラストオーダーによる受付制限を適用しない。
- MVPは実際の注文を扱わず、料理とドリンクでラストオーダーを分けない。

#### 実用性評価

最終入店とラストオーダーを分けることで、閉店までに利用を終えられても注文時間を確保できない顧客を受け付ける問題を防げる。
注文管理を導入せず営業時間設定だけで判定できるため、予約APIのMVPとして実装可能である。

### 11.9 予約なし利用の予定利用時間

**確定：予定利用時間は受付時にだけ決定し、MVPでは利用開始後の延長と短縮を行わない。**

- 初期値は90分、最小値は60分、最大値は180分、入力単位は10分とする。
- 予定利用時間は予定終了日時と予定利用開始日時の差から求め、分数列として重複保存しない。
- 90分未満では終了予定時刻を顧客へ案内し、受付を確定した登録スタッフと受付日時を案内確認の主体・日時として記録する。
- 開始後に予定より早く退店した場合は、予定終了を短縮せず利用終了操作で実際の終了日時を記録し、必要な終了後転換時間を実際の終了日時から計算する。
- 予定終了10分前を終了間近、予定終了後を時間超過として現在時刻から判定する。
- 時間超過しても自動終了せず、`active` の間は予定終了後も席を占有中として扱う。
- 時間超過中に後続予約がある場合は強い警告を表示するが、MVPでは予定終了の延長操作を提供しない。

#### 実用性評価

60分から180分までの選択により、90分では収まらない予約間の空きを利用しつつ、極端に短い案内と入力ミスによる長時間占有を抑えられる。
開始後の予定変更をなくすことで競合再計算と権限判断をMVPから除外でき、早期退店と時間超過は実際の利用終了によって一貫して処理できる。

時間超過そのものをシステムが解消することはできないため、後続予約がある場合の退席案内または席移動は現場対応として残る。

### 11.10 予約なし利用の人数変更と13名以上

**確定：準備中・利用中の人数変更は現在の割り当て定員内とし、13名以上は12名以下の複数件を一括作成する。**

- 現在人数は1名以上12名以下とし、全員退店は利用終了で扱う。
- `preparing` と `active` のどちらでも人数を変更できる。`preparing` で全員が利用をやめる場合は0名へ変更せず、理由付き受付中止とする。
- 減員は席配置と占有期間を縮小しない。
- 増員が現在の割り当て定員内なら、通常スタッフが人数だけを変更して監査履歴を残せる。
- `preparing` 中に5名未満へ減っても、準備中のまま受付時の予定利用開始日時と適用済み転換時間を維持する。
- 割り当て定員を超える追加参加者は、別の予約なし利用として席候補を探索する。
- 13名以上で同時に来店した団体は、スタッフが各1名以上12名以下へ分割して入力し、全件を同じトランザクションで作成する。
- 分割した全件を収容できない場合は一部だけ作成しない。
- 分割後の各件は恒久的な団体関係を持たず、近接席を保証せず、変更と利用終了を個別に行う。
- 成立した一括受付ごとにサーバー側でUUIDv7の `operation_id` を1つ生成し、全件の監査記録と関連する席配置世代へ記録する。利用系列には保存せず、団体操作または削除単位には使用しない。
- `operation_id` は成立した変更を追跡する内部識別子であり、リクエスト再送を判定する冪等性キーとは別に扱う。
- 自動配置を使用する限り、合計人数だけを理由とする責任者承認を要求しない。

#### 実用性評価

利用中の席配置を拡張しないため、追加参加者によって既存予約の席や転換時間を侵害する危険を抑えられる。
13名以上を全件一括で確定するため、一部の参加者分だけ席を確保した後に残りを受け付けられなくなる状態を防げる。

一方、追加参加者や13名以上の団体が離れて座る可能性があり、各件の利用終了も個別操作になる。
共通 `operation_id` により、一部作成や自動再配置の調査はできるが、一括変更または一括終了の対象検索には使用しない。恒久的な団体関連付けと近接席保証は、必要性を確認してMVP後に追加する。

### 11.11 予約なし利用の準備・清掃と操作権限

**確定：5名以上は準備中から席を確保し、通常操作は一般スタッフ、席の選択と利用中移動は当日運用責任者以上が行う。**

- 1名から4名は受付時に `active`、5名以上は受付時に `preparing` とする。
- 5名以上の予定利用開始日時は受付日時へ店舗設定の大人数転換時間を加え、予定終了日時はそこから予定利用時間を加える。
- 適用した利用前・利用後転換時間と占有期間は席配置世代へ保存する。1名から4名は両方0分、5名以上は受付時点の店舗設定値とし、後の設定変更、人数変更または席移動で自動変更しない。
- `preparing` からの開始が遅れても予定終了日時を自動延長せず、遅延警告を表示する。
- 利用終了後は、5名以上だけ実際の終了日時から大人数転換時間が経過するまで席を確保し、経過後に自動で割り当て可能にする。
- 早期終了では終了後転換時間を実際の終了日時から計算し直すが、既存予約の席を自動再配置しない。
- 時間超過による実際の占有終了が既存の後続予約と重なっても実終了を拒否せず、現実の競合として保存して強い警告を表示する。重なりが解消するまで追加の新規割り当てを拒否する。
- 通常スタッフは自動配置による受付確定、必要な準備後の利用開始、利用終了を行える。準備中の受付中止は理由を必須とする。
- 当日運用責任者以上は、受付時の別候補選択と、安全上または顧客対応上の理由を伴う利用中の席移動を行える。
- `completed` または `aborted` は通常操作で元へ戻さず、誤った終了状態は `walk_in_record_correction` として提起する。営業中に席占有を継続する場合は、当日運用責任者以上が元の予定終了日時を引き継いだ新しい予約なし利用を関連付けて記録する。

#### 実用性評価

準備開始時点で席を確保するため、スタッフがテーブルを移動している間に同じ席がオンライン予約へ割り当てられる競合を防げる。
通常スタッフだけで自動配置の受付から利用終了まで進められるため、責任者が常に受付操作へ加わる必要はない。

一方、準備遅延によって予定終了日時を延長しないため、店舗は設定時間内に準備を終え、遅延時には顧客へ残り時間を説明する必要がある。
清掃完了操作を設けず時間経過で席を解放する方式はMVPとして単純だが、実際の清掃が間に合わない場合は二重案内につながるため、店舗は転換時間を実測して不足する設定を延長しなければならない。

### 11.12 予約なし利用と貸切・営業設定・臨時休業

**確定：貸切と通常の営業時間変更は既存利用を侵害できず、臨時休業だけは既存利用を残して新規受付を停止できる。**

- 貸切は、対象範囲と予約停止時間が `preparing`、`active`、利用終了後転換時間中の予約なし利用と重なる場合に拒否する。
- 店舗全体の貸切は1件でも重なれば拒否し、エリア・テーブル貸切は指定範囲が重なる場合だけ拒否する。管理責任者以上でも競合を上書きしない。
- 通常営業時間または特別営業時間の変更で、既存予約または `preparing`、`active` の予約なし利用が営業時間外になる場合は変更を拒否する。
- 受付済みの予約なし利用に対して最終入店時刻だけを遡って再判定せず、終了後の転換時間は営業時間外へ延びてもよい。
- 臨時休業は `preparing` または `active` が存在しても登録でき、対象営業日の新しい予約、貸切、予約なし利用を停止する。
- 臨時休業によって予約なし利用を自動終了または自動中止せず、予約なし利用ごとの例外案件も自動作成しない。未終了の店内利用がある間は強い警告を表示する。
- `preparing` は通常の理由付き受付中止、`active` は実際の退店時の利用終了によって処理する。終了後転換時間中は現場対応の対象にしない。
- 貸切、営業時間変更、臨時休業、予約なし利用受付は店舗ロックの後に関連データを再取得し、同時実行時に古い空席・営業状態で確定しない。

#### 実用性評価

通常の設定操作と貸切が店内客の利用を後から無効化することを防ぎながら、災害や設備故障では臨時休業によって新規受付を直ちに止められる。
来店済みで連絡先を持たない予約なし利用へ連絡用の例外案件を量産せず、現場で確認すべき未終了件数だけを警告できる。

一方、臨時休業は物理的な退店を実行しないため、顧客を退席させるか安全に利用を継続させるかは現場判断として残る。
店舗単位のロックは同時更新の整合性を高めるが、複数の設定・受付操作が集中した場合の待ち時間はPostgreSQLによる同時実行試験で確認する必要がある。

### 11.13 例外案件と予約なし利用の訂正

**確定：例外案件は共通集約とし、来店記録、予約なし利用記録、無断キャンセル、臨時休業対応の4種へ分ける。**

- 履歴訂正を伴う案件は、通常スタッフの報告、当日運用責任者の提起、管理責任者または管理者の承認・却下の順で処理する。
- 臨時休業対応と、後から通常手順で資格確認できた来店案件は、矛盾解消をシステムが確認できる場合だけ `resolved` にする。
- 予約の来店記録と予約なし利用記録は同じ審査基盤を利用するが、資格情報、正常状態遷移、訂正結果が異なるため案件種別を分ける。
- 準備中・利用中の人数変更と理由付き席移動は通常操作とし、終了済みの履歴や通常状態遷移で直せない記録だけを訂正案件にする。
- 誤終了後の営業継続では、当日運用責任者が過去の誤りを確定せず、関連付けた新しい予約なし利用によって現在の席占有だけを直ちに正しくする。
- 新しい利用は元と同じ利用系列へ追加し、元の予定開始・終了日時、現在人数、短時間案内確認および適用済み転換時間を引き継ぐ。誤操作を理由に顧客へ新たな標準利用時間を与えない。
- 後日の承認後も元の操作を削除せず、訂正済みであることを追記して、承認済みの継続関係でつながる新旧記録を連続利用として集計する。却下時は同じ系列に履歴を残したまま、関係の前後を別利用として集計する。

#### 実用性評価

1つの例外案件集約へ報告者、提起者、決定者、理由、状態を共通化できるため、MVPで案件種別ごとに別の審査システムを作る必要はない。
一方、任意の対象や訂正内容を文字列だけで扱う汎用案件にすると、権限外の状態変更や不整合を許しやすい。案件種別ごとに許可する対象、提案、訂正操作を固定する必要がある。

占有継続登録によって管理責任者の後日判断を待たず、同じ席が別の予定へ再割り当てされた後も実際の占有を記録できる。ただし、記録によって物理的な席競合が解消するわけではなく、既存予定を自動で奪い返すこともできない。
店舗と系列のロックを使って競合時間を短くし、現実の競合を保存した後は強い警告と追加割り当て停止によって現場調整へつなげる。新旧記録の関連表示、承認・却下後の集計、同時実行時の席引継ぎは、スタッフ画面、集計テスト、PostgreSQL統合テストで検証する必要がある。

### 11.14 予約なし利用の保持期間と監査

**確定：予約なし利用系列を削除単位として最新の確定終了または案件終了から3年保持し、期限後は復元不能な集計だけを残す。**

- 予約なし利用本体、人数、利用日時、席配置、開始・変更・終了・訂正の監査履歴を同じ3年保持の対象とする。
- 利用系列に属するすべての利用と例外案件が終了した最も遅い日時を起算点とし、承認・却下の結果にかかわらず系列の一部だけを削除しない。
- 未終了、未審査、削除保留中の記録を定期削除の対象にしない。
- 承認済み継続関係でつながる利用区間は1回の連続利用として集計し、却下された関係の前後は別利用として集計する。どちらも同じ系列の削除単位を維持する。
- 営業月、曜日、時間帯、人数帯ごとの件数、合計人数、平均利用時間、席稼働、時間超過、訂正件数など、個別利用を復元できない集計値は期限後も保持できる。
- 元の利用ID、正確な来退店時刻、個別席、操作スタッフ、理由、自由記述、例外案件ID、再結合用ハッシュを無期限統計へ残さない。

#### 実用性評価

3年保持は法令による一律の義務ではなく、既存の業務・監査履歴と削除時期を揃え、複数年の同季節比較と事後調査を可能にするためのMVP方針である。
予約なし利用は氏名と電話番号を持たないが、正確な時刻、席、スタッフ、外部の会計情報などとの組み合わせによる推測可能性があるため、個別記録を無期限に保持しない。

単一店舗40席では3年分のデータ量は現実的と見込むが、利用系列全体のロックと集計生成によって日次ジョブが長時間化しないか、実装後に対象件数、バッチサイズ、実行時間を測定する必要がある。
集計を先に保存する処理は、再実行時に二重加算しない一意キーと冪等性を必要とする。削除後は個別の問い合わせへ回答できないため、期限、削除保留、dry-runの境界値テストも必要になる。

### 11.15 予約なし利用のスタッフ画面と表示状態

**確定：予約と予約なし利用を同じ当日一覧へ投影し、業務上の警告を基本状態とは別の派生表示として扱う。**

- 今日の営業画面は予約と予約なし利用を同じ時系列へ表示し、種類ごとの視覚的な区別と絞り込みを提供する。
- `preparing` かつ現在日時が予定利用開始日時を過ぎていれば準備遅延と判定する。
- `active` かつ現在日時が予定終了10分前以上、予定終了日時未満なら終了間近、予定終了日時以上なら時間超過と判定する。
- `completed` かつ現在日時が席配置計画の占有終了日時より前なら転換中と判定し、再利用可能日時を表示する。
- 準備遅延、終了間近、時間超過、転換中は検索時点の現在日時と関連データから計算し、予約なし利用の基本状態として保存しない。
- 後続予約に影響する時間超過、未解決の例外案件、前営業日以前から残る案件は、通常の状態表示より優先度の高い警告として返す。
- 受付画面の席候補は表示用の事前計算とし、席を仮押さえしない。確定コマンドは店舗をロックして候補を再計算し、表示時点から競合した場合は何も作成しない。
- 操作者に応じた表示用の操作候補を返すことはできるが、コマンド実行時の認証、認可、状態遷移、競合検証を省略しない。
- 満席、営業時間外、最終入店後、閉店超過、貸切、臨時休業、同時更新を機械判定可能な受付不可理由として区別し、画面が再試行可能性を判断できるようにする。
- 待ち行列、将来の空席保証、平面座標を使ったフロアマップは、この当日表示モデルへ含めない。

#### 実用性評価

予約と予約なし利用を同じ読み取りモデルへ投影すると、別々の一覧を見比べずに当日の席利用と警告を確認できる。40席の単一店舗では、種類と状態の絞り込みを用意すればMVPとして扱える規模と見込む。

一方、警告を永続状態として保存すると時間経過だけで内容が古くなるため、API取得時の店舗時刻から計算する必要がある。混雑時間帯の視認性、同時更新後の再試行導線、権限の異なるスタッフによる誤操作の起きにくさは、実データ相当の画面試作で確認する。

### 11.16 席配置計画の世代管理

**確定：席配置を現在値へ上書きせず、予約または予約なし利用ごとの計画へ不変の世代を追加する。**

- 最初の配置を第1世代とし、配置、決定区分、転換時間、占有期間を変更するたびに次の世代を作成する。
- 席配置計画は現在世代を必ず1つだけ指し、現在世代だけを空席検索、競合判定、自動再配置へ使用する。
- 過去と同じ席へ戻す場合も新しい世代を作り、既存の世代または席割り当てを変更しない。
- 複数計画の自動再配置では、新世代の追加と現在世代の切り替えを同じトランザクションで行い、共通の原因操作識別子を付ける。
- 席配置世代は配置内容の業務履歴、監査記録は操作主体、理由、操作日時の証跡として分離する。
- 詳細な判断経緯は [ADR-0001](adr/0001-seat-placement-plan-versioning.md) に記録する。

#### 実用性評価

過去の完全な配置を関連データとして検索できるため、複数予約の自動再配置、固定決定、誤終了後の占有引継ぎが正しく行われたかを、汎用監査ログの復元だけに頼らず確認できる。40席、15テーブルの単一店舗では、増える履歴行数は現実的な範囲と見込む。

一方、現在値を上書きする方式より保存行数と実装量が増える。現在世代だけが席を占有する制約、複数計画の世代切り替え、同時更新時の全体ロールバックをPostgreSQLの制約と統合テストで検証する必要がある。

### 11.17 電話番号の正規化と無断キャンセル照合

**確定：電話番号をE.164形式へ正規化し、確定済み無断キャンセルとの照合には店舗単位のHMAC-SHA-256を使用する。**

- Unicode互換正規化（NFKC）後の入力には数字、先頭の `+`、ハイフン、空白、丸括弧だけを許可し、英字または内線番号を受け付けない。
- `+` から始まらない番号は日本の番号として解析し、`+` から始まる国際番号も受け付ける。携帯電話に限定せず、固定電話、IP電話、フリーダイヤルなど、電話連絡に使用できる有効な番号種別を許可する。
- 保守されている電話番号解析ライブラリを使用して番号を検証し、E.164形式へ正規化する。ライブラリ上の形式検証を、番号が現に割り当てられていることまたは予約者本人の所有であることの証明には使わない。
- 予約には正規化済み電話番号を連絡先として保持し、正規化前の入力値は別に永続化しない。
- 管理責任者または管理者が無断キャンセルを確定した場合だけ、ASCIIの `no-show-phone:v1`、NULL区切り、店舗UUIDの16バイト表現、E.164電話番号のASCII表現をこの順で連結し、専用秘密鍵によるHMAC-SHA-256照合値を作成する。
- 照合値は同じ店舗内の無断キャンセル警告だけに使用し、顧客ID、外部キー、本人性の証明、自動的な予約拒否には使用しない。すべての予約へ照合値を保存せず、確定済み無断キャンセルへだけ保存する。
- 電話連絡に必要な正規化済み番号と、復元不能な照合値は目的を分けて保存する。HMACは連絡先の閲覧制御または保存時保護の代わりにはならない。
- HMACの専用秘密鍵はDB、ソースコード、ログへ保存せず、DBパスワード、予約確認コード、チェックイントークンの秘密情報と共用しない。開発環境ではGit管理外の環境設定、本番ではシークレット管理機能から取得する。
- 照合値には鍵バージョンと正規化方式バージョンを記録する。鍵更新中は新旧の読み取り可能な鍵で入力番号の候補値を計算し、既存値を新しい鍵へ段階的に再生成してから旧鍵を廃止する。
- 鍵または正規化方式の更新によって同じ無断キャンセル予約へ複数バージョンの照合値を一時保存する場合も、同じ鍵バージョンと正規化方式バージョンの組み合わせを重複させない。
- 照合値とすべてのバージョンは、無断キャンセル確定から1年の保持期限を迎えた時点で削除する。更新時も元の保持期限を引き継ぎ、HMAC照合値を匿名情報として期限後に残さない。
- 警告状態を予約へ保存せず、認証済みかつ対象店舗所属のスタッフ向け読み取りモデルで、保持中の照合値から派生させる。公開予約作成処理では無断キャンセル照合を行わず、顧客向けAPIまたは処理時間の差から照合結果を判別できないようにする。
- 詳細な判断経緯は [ADR-0002](adr/0002-phone-number-matching.md) に記録する。

#### 実用性評価

正規化によってハイフンや国番号の表記差を吸収し、鍵バージョンと照合値のインデックスで単一店舗の警告を十分軽く判定できる。固定電話を含めるためSMS受信可否には依存せず、海外番号を持つ予約者も `+` 付き形式で受け付けられる。

一方、電話番号の誤入力、家族共用、再割り当てによる別人の一致は防げず、HMAC化しても照合可能な個人情報であることは変わらない。保持中の予約連絡先へアクセスできる主体には電話番号自体が見えるため、HMACはDB全体の漏えい対策ではなく、照合用インデックスの用途分離である。警告を自動拒否へ使わず、秘密鍵の喪失時は再生成完了まで照合が欠落すること、鍵漏えい時は再生成と旧鍵廃止が必要になることを運用手順とテストで確認する。
