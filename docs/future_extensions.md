# MVP後の拡張案

## 1. 文書の目的

この文書は、MVPの完成に必須ではないが、将来の実運用に向けて検討または導入する機能を記録する。
ここに記載した内容はMVP要件ではなく、導入時には外部サービス、費用、運用体制、セキュリティを再評価する。

## 2. 臨時休業時の顧客連絡自動化

### 2.1 MVPとの境界

MVPでは、臨時休業の影響を受ける予約を要対応として表示し、認証済みスタッフが登録済み電話番号を確認できるところまでを実装する。
SMS送信、顧客による受領確認、電話対応履歴、再試行、連絡不能の管理は実装しない。

次のいずれかが発生した場合は、この拡張案の導入を再検討する。

- 臨時休業時の対象予約が多く、手動連絡では対応漏れが発生する。
- 複数のスタッフによる二重連絡や引き継ぎ漏れが問題になる。
- 顧客へ連絡した事実と結果を監査できる必要が生じる。
- 複数店舗対応によって連絡業務を標準化する必要が生じる。

### 2.2 予約時に追加する情報

- 予約作成時に、その電話番号でSMSを受信できるかを登録する。
- SMSを受信できる場合も、SMS送信に失敗したときは電話で連絡する旨を案内する。
- 携帯電話と固定電話の両方を引き続き許可し、SMSを予約成立の必須条件にしない。

### 2.3 予約状態と連絡状態

- 管理責任者または管理者が店舗都合キャンセルを確定した時点で、対象予約を `cancelled` へ遷移させる。
- 店舗都合キャンセルの成立は顧客の受領確認を待たず、予約状態と顧客への連絡状態を分離する。
- 顧客がSMSまたは電話で通知を確認した場合は連絡状態だけを変更し、予約状態を変更しない。
- 店舗都合キャンセルと連絡不能を、顧客の無断キャンセル履歴または利用制限の判断材料にしない。

### 2.4 SMS通知と電話への切り替え

- SMSを受信できる予約には、店舗都合キャンセルの確定後、速やかにSMSを送信する。
- SMSには、通知内容を確認したことを記録する操作と、日時変更について店舗からの電話を希望する操作を用意する。
- SMSで確認済みとなった予約は電話確認対象から除外し、電話希望となった予約は電話対応キューへ残す。
- SMSの配信成功は顧客による確認とみなさず、顧客が確認操作を完了した場合だけ確認済みとする。
- 固定電話などSMSを受信できない予約と、SMS送信に失敗した予約は電話連絡へ切り替える。
- 電話確認の開始期限は、SMSの確認有無と来店営業日までの残り営業日数から次のように決める。
  - 来店3営業日以上前は、SMS送信の翌営業日までに確認がなければ電話する。
  - 来店2営業日前は、SMS送信当日の顧客連絡可能時間内に確認がなければ電話する。
  - 来店1営業日前または当日は、SMS送信後、待たずに電話する。
- 電話へ直接切り替える予約にも、残り営業日数に応じた同じ電話開始期限を適用する。
- SMS送信時または電話対応案件の作成時に、計算済みの電話開始期限を保存する。
- 対象日の臨時休業登録によって営業日数計算や保存済みの電話開始期限を自動的に後ろ倒ししない。

### 2.5 顧客連絡可能時間

- 顧客へ電話できる曜日と時間帯は、通常の店舗営業時間とは別の店舗設定として管理する。
- 顧客連絡可能時間は店舗が決定し、管理責任者または管理者が変更できる。
- 電話開始期限が顧客連絡可能時間外になる場合は、原則として次の連絡可能時刻へ繰り越す。
- 来店当日など、次の連絡可能時刻では来店時刻に間に合わない案件は、スタッフ画面へ緊急警告を表示する。

### 2.6 電話の試行回数と結果

- SMSで確認できなかった通常予約への電話は最大2回とする。
- 5名以上の大人数予約および貸切予約への電話は最大3回とする。
- 再試行は可能な限り前回と異なる時間帯に行う。
- 電話番号が無効または現在使用されていないことを確認できた場合は、上限回数に達する前でも再試行を終了できる。
- 留守番電話には、店舗名、重要な連絡があること、SMS確認または折り返しを依頼することだけを残し、氏名、予約日時、人数などを含めない。
- 留守番電話を残した場合は電話試行1回として数えるが、本人への通知完了とはみなさない。
- 呼び出しのみ、話し中、第三者応答も本人への通知完了とはみなさない。
- 上限回数まで電話しても確認できない場合は、まず連絡試行終了として記録する。
- 当日運用責任者は連絡不能の確定を提起し、管理責任者または管理者が記録を確認して連絡不能を確定する。
- 連絡不能確定後も、顧客によるSMS確認または折り返しがあれば、遅延確認済みを経て対応完了へ変更できる。

### 2.7 スタッフの電話対応操作

- 顧客の電話番号はスタッフ画面で通常時は一部をマスクする。
- スタッフが電話対応開始操作を行ったときに、開始日時と担当スタッフを記録して電話番号を表示する。
- 対応中は、他のスタッフへ担当者を表示して重複発信を防ぐ。
- 電話対応開始操作だけでは電話試行回数へ加算せず、通話結果を確定した時点で加算する。
- 何回目の電話かはスタッフに入力させず、確定済みの電話試行履歴から自動計算する。
- 通話結果は、本人への通知完了、日時変更の相談、不応答、留守番電話、話し中、折り返し待ち、第三者応答、番号無効、発信せず終了、その他を区別する。
- 発信せず終了した場合は電話試行回数へ加算せず、理由を必須とする。
- 第三者応答またはその他を選択した場合も、必要な事情を記録する。
- 電話番号を表示したスタッフと日時、各電話の開始日時、結果、担当スタッフを履歴として保存する。

### 2.8 導入時に追加で必要な設計

- SMS事業者、料金、送信上限、送信元表示
- 配信結果を受信するWebhookと、重複通知に対する冪等性
- SMS事業者の障害、遅延、配信失敗時の電話切り替え
- 確認用公開URLの推測困難なトークン、有効期限、Rate Limit
- 電話対応中の期限切れ、担当者離脱、二重操作への対策
- 電話番号、SMS本文、操作履歴の保持期間と削除方針
- 店舗ごとの顧客連絡可能時間の初期値と変更手順

### 2.9 実用性評価

この拡張は、臨時休業時の対象予約が多い店舗や複数店舗運用では、電話件数と対応漏れを減らす効果が期待できる。
一方で、外部SMSサービスへの依存、送信費用、公開確認ページのセキュリティ、電話業務の状態管理が加わるため、MVPへ含めると予約APIの中核開発を圧迫する。
単一店舗のMVPでは手動連絡と要対応警告で代替可能であり、実際の連絡件数または運用上の問題が導入コストを上回った時点で追加するのが妥当である。

## 3. 営業日カレンダーのキャッシュ

### 3.1 MVPとの境界

MVPでは定休日ルールを正として保存し、予約受付、空席確認、予約変更の対象営業日を都度計算する。
具体的な営業日を事前生成せず、アプリケーション起動時または日付変更時の生成処理にも依存しない。

次のいずれかが実測で問題になった場合は、営業日カレンダーのキャッシュを検討する。

- 多数店舗の営業日を横断して検索する。
- 長期間の営業日カレンダーを繰り返し取得する。
- 定休日、特別営業時間、臨時休業の都度計算が性能要件を満たさない。

### 3.2 キャッシュの原則

- 定休日ルール、特別営業時間、臨時休業を正とし、生成済み営業日は再作成可能な派生データとして扱う。
- `(store_id, business_date)` に一意制約を設定し、同じ日付を複数回生成しても結果が変わらない冪等な処理にする。
- 日次処理では、予約受付期間の365日先に余裕期間を加えた範囲を補充する。
- 日次処理が失敗または未実行でも、予約処理は元のルールから営業可否を計算できるようにする。
- 予約処理で必要な営業日のキャッシュがなければ、その場で計算するか安全に生成する。
- 生成行には、元になったルールのバージョンまたは更新時刻を持たせ、古いキャッシュを識別できるようにする。
- 定休日ルール、特別営業時間、臨時休業を変更した場合は、対象店舗の影響範囲だけを無効化または再生成する。
- 複数のアプリケーションプロセスが同時に起動しても、起動処理の競合によって重複生成しない構成にする。
- 店舗ごとのタイムゾーンを基準に営業日を扱い、サーバーのローカル日付へ依存しない。

### 3.3 実用性評価

1店舗につき1日1行であれば、店舗数が増えてもPostgreSQLで扱える範囲に収まりやすい。
ただし、データ量よりもルール変更時の同期、バッチ失敗、キャッシュの世代管理、複数プロセス間の競合が運用上の負担になる。
このため、キャッシュは最初から導入せず、都度計算の性能を計測して必要性が確認された場合に追加する。
