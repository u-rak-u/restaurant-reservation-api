## 1. バックエンドAPIとは何か

### 1.1 フロントエンドとバックエンド

フロントエンドは、利用者が見る画面や入力フォームを担当します。バックエンドは、入力を受け取り、ルールを確認し、データを保存して、結果を返します。

店舗予約の登録なら、全体は次のように流れます。

```text
画面
  ↓ HTTPリクエスト
FastAPIのルート
  ↓ 入力を検証
サービス（業務ルール）
  ↓ 読み書きを依頼
SQLAlchemy
  ↓ SQL
PostgreSQL
  ↓ 結果
JSONレスポンス
```

バックエンドの役割は「DBへ保存すること」だけではありません。

- 入力が正しいか確認する
- ログインしている人を特定する
- その人に操作権限があるか確認する
- 業務ルールに違反していないか確認する
- 複数の更新を一つの処理として成功・失敗させる
- 誰が変更したか記録する
- エラーをAPI利用者が理解できる形で返す

### 1.2 HTTPリクエストの構成

HTTPリクエストには主に次の情報があります。

| 部分 | 役割 | 例 |
| --- | --- | --- |
| メソッド | 何をしたいか | `GET`、`POST`、`PATCH` |
| パス | どの資源を扱うか | `/customers/12` |
| パスパラメータ | 特定の1件を表す | `12` |
| クエリパラメータ | 検索・絞り込み | `?name=田中` |
| ヘッダー | 認証や形式などの付加情報 | `Authorization` |
| ボディ | 登録・変更するデータ | JSON |

### 1.3 よく使うHTTPメソッド

| メソッド | 主な用途 | 性質 |
| --- | --- | --- |
| `GET` | 取得 | 原則としてデータを変更しない |
| `POST` | 新規作成、特別な操作 | 同じ送信を繰り返すと結果が増える場合がある |
| `PUT` | 全体を置き換える | 同じ内容なら同じ状態になることを期待する |
| `PATCH` | 一部を変更する | 変更する項目だけ送る |
| `DELETE` | 削除 | 対象を削除する |

予約キャンセルは、行を物理削除せず状態を変える業務操作です。そのため、`DELETE /reservations/{id}` より `POST /reservations/{id}/cancel` のほうが意図を表しやすい設計です。

### 1.4 よく使うステータスコード

| コード | 意味 | 店舗予約APIの例 |
| --- | --- | --- |
| `200` | 成功 | 一覧・詳細・変更 |
| `201` | 作成成功 | 顧客・予約の作成 |
| `204` | 成功、返す本文なし | 臨時休業日の削除 |
| `400` | リクエストの意味が不正 | 終了が開始以前 |
| `401` | 誰か確認できない | トークンなし・無効 |
| `403` | 誰かは分かるが権限がない | 店員が営業時間を変更 |
| `404` | 対象がない | 顧客IDが存在しない |
| `409` | 現在の状態と競合 | 席が重複、再キャンセル |
| `422` | 入力形式・型の検証に失敗 | 人数に文字列を送信 |

`400`、`409`、`422`の使い分けは唯一の正解があるわけではありません。プロジェクト内で判断基準を決め、一貫させることが重要です。

### 確認問題

1. `401`と`403`の違いを、自分の言葉で説明してください。
2. 顧客名で検索する場合、パスパラメータとクエリパラメータのどちらが自然でしょうか。
3. キャンセルを物理削除にすると、操作履歴や重複判定にどんな影響がありますか。

## 2. Pythonの実行環境とパッケージ管理

### 2.1 Python本体、仮想環境、pipの違い

```text
Python本体
  └─ .venv（このプロジェクト専用の環境）
       ├─ python.exe
       ├─ pip
       └─ インストールしたライブラリ
```

Python本体はプログラムを実行します。仮想環境は、プロジェクトごとにライブラリを分離します。`pip`は、その仮想環境へライブラリを追加します。

仮想環境を使わないと、別プロジェクトが要求するバージョンと衝突しやすくなります。

### 2.2 Windows PowerShellで使う基本コマンド

プロジェクトのルートで実行します。

```powershell
# Pythonのバージョン
.\.venv\Scripts\python.exe --version

# pipのバージョン
.\.venv\Scripts\python.exe -m pip --version

# requirements-dev.txtに書かれた依存関係を入れる
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt

# インストール済みパッケージを確認する
.\.venv\Scripts\python.exe -m pip list

# 依存関係の矛盾を確認する
.\.venv\Scripts\python.exe -m pip check
```

`python -m pip`と書く理由は、「今使っているPythonに所属するpip」を明確にするためです。`pip`だけを実行すると、別のPythonに所属するpipを呼ぶ事故が起こることがあります。

### 2.3 `requirements.txt`とは

`requirements.txt`は、アプリの実行に必要なライブラリの一覧です。`requirements-dev.txt`には、pytestなど開発・テスト時だけ必要なものを置けます。

現在使う主なライブラリの役割は次のとおりです。

| パッケージ | 役割 |
| --- | --- |
| FastAPI | HTTPリクエストを受けるWebフレームワーク |
| Uvicorn | FastAPIアプリを動かすサーバー |
| Pydantic | 入出力データの型・値を検証する |
| pydantic-settings | 環境変数や`.env`を設定クラスへ読み込む |
| SQLAlchemy | PythonからDBへ問い合わせる |
| psycopg | PostgreSQLと実際に通信するドライバー |
| Alembic | DB構造の変更履歴を管理する |
| pytest | 自動テストを実行する |

### 2.4 バージョン指定の読み方

```text
SQLAlchemy>=2.0,<3.0
```

これは「2.0以上、3.0未満」という意味です。

```text
2.0 ───────── 2.x ───────── 3.0
  ↑ 利用可能な範囲              ↑ 入らない
```

- `>=2.0`: 2.0より古いものを使わない
- `<3.0`: 大きな互換性変更があり得る3系を自動では入れない
- 条件内では、通常pipが利用可能な新しい安定版を選ぶ

`psycopg[binary]`の`[binary]`はバージョンではなく追加機能です。Windowsで始めやすい、ビルド済みのバイナリを一緒に入れる指定です。

### 2.5 バージョンを調べる手順

```powershell
.\.venv\Scripts\python.exe -m pip index versions SQLAlchemy
.\.venv\Scripts\python.exe -m pip index versions pydantic-settings
.\.venv\Scripts\python.exe -m pip index versions psycopg
```

確認するのは次の3点です。

1. 安定版か（`a`、`b`、`rc`などの開発途中版ではないか）
2. 自分のPythonバージョンに対応するか
3. 他の主要ライブラリと対応するか

新しければ必ず良いわけではありません。学習中は、同じメジャーバージョン内で更新を受けつつ、大きな変更は意識して行う指定が分かりやすいです。

### 確認問題

1. `.venv`はGitHubへ含めるべきでしょうか。理由も考えてください。
2. `>=2.0,<3.0`と`==2.0.0`にはどんな違いがありますか。
3. `psycopg`とSQLAlchemyは、なぜ両方必要なのでしょうか。

## 3. アプリケーション設定と`.env`

ここは現在のプロジェクトで最初に実装する章です。

### 3.1 設定をコードから分ける理由

次の値は環境によって変わります。

- DB名
- DBユーザー名
- DBパスワード
- DBホスト
- DBポート
- 将来のJWT秘密鍵

これらをPythonファイルへ直接書くと、開発環境と本番環境の切り替えが難しくなり、秘密情報をGitへ公開する危険もあります。

そこで役割を分けます。

| 場所 | 保存するもの |
| --- | --- |
| `.env` | 自分のPCで使う実際の値。Gitへ入れない |
| `.env.example` | 必要な変数名の見本。秘密値は書かない |
| `config.py` | 値の型、必須か、初期値、読み込み方 |

### 3.2 環境変数とは

環境変数は、プログラムの外側から渡す名前と値の組です。

```text
WAREHOUSE_DB_PORT=5432
```

環境変数として読んだ直後は文字列ですが、Pydantic Settingsのフィールドを`int`にすれば、変換できるか検証してから整数として扱えます。

### 3.3 Pydantic Settingsの役割

`BaseSettings`を継承したクラスは、未指定のフィールドを環境変数などから探し、型を検証します。

別題材の例です。

```python
from pydantic import SecretStr
from pydantic_settings import BaseSettings, SettingsConfigDict


class WarehouseSettings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_file_encoding="utf-8",
        extra="ignore",
    )

    warehouse_db_name: str
    warehouse_db_user: str
    warehouse_db_password: SecretStr
    warehouse_db_host: str = "127.0.0.1"
    warehouse_db_port: int = 5432
```

一行ずつ役割を確認します。

- `BaseSettings`: 外部設定を読み、フィールドの型を検証する基底クラス
- `SettingsConfigDict`: `.env`の場所など、読み込み方を指定する
- `env_file`: 読み込むdotenvファイル
- `env_file_encoding`: 日本語などをUTF-8として読む
- `extra="ignore"`: このクラスが知らない追加変数が`.env`にあっても無視する
- 初期値なしのフィールド: 必須。値がなければ起動時にエラー
- 初期値ありのフィールド: 値がなければ初期値を使う
- `SecretStr`: 表示やログ出力で秘密値を隠しやすくする

`SecretStr`は暗号化ではありません。必要な場所では元の値を取り出せます。「うっかり表示」を減らすための型です。

### 3.4 必須値と初期値の判断

次の問いで決めます。

> 値が設定されていないとき、アプリが勝手な値で起動しても安全か。

- DBパスワード: 勝手な値では接続できず、誤設定に気づきにくいため必須
- ローカルDBホスト: 開発時は`127.0.0.1`が自然なら初期値を持たせてもよい
- DBポート: 標準の`5432`を初期値にしてもよい

秘密情報に「便利な初期値」を置くのは避けます。

### 3.5 接続URLを文字列連結しない理由

DBの接続先は、概念上は次の形です。

```text
DB種類+ドライバー://ユーザー:パスワード@ホスト:ポート/DB名
```

しかし、パスワードに`@`、`:`、`/`などが含まれると、手作業の文字列連結ではURLの区切りと誤解される可能性があります。

SQLAlchemyの`URL.create()`へ部品を個別に渡すと、文字列解析を避けられます。

別題材の例です。

```python
from sqlalchemy import URL


def build_warehouse_database_url(settings: WarehouseSettings) -> URL:
    return URL.create(
        drivername="postgresql+psycopg",
        username=settings.warehouse_db_user,
        password=settings.warehouse_db_password.get_secret_value(),
        host=settings.warehouse_db_host,
        port=settings.warehouse_db_port,
        database=settings.warehouse_db_name,
    )
```

秘密値を取り出すのは、DBドライバーへ渡す境界だけにします。ログへ出すために取り出してはいけません。

### 3.6 `.env`の落とし穴

- `.env`をGitへ追加しない
- `.env.example`に実際のパスワードを書かない
- `KEY = value`のような不要な空白を避ける
- 値の末尾に意図しない空白を入れない
- 実行するカレントディレクトリが違うと`.env`を見つけられない場合がある
- エラー確認のために設定全体を`print`しない

### 現在の店舗予約APIへの応用課題

まだ答えを写さず、次を紙やコメントで整理してください。

1. `.env.example`にあるDB関連の変数名を列挙する
2. 各変数を`str`、`int`、`SecretStr`のどれで受けるか決める
3. 必須値と初期値ありに分ける
4. `SettingsConfigDict`に必要な設定を決める
5. `URL.create()`の各引数へ、どの設定フィールドを渡すか対応表を書く

この対応表をレビューしてから`app/config.py`へ進むと、コピーではなく理解して実装できます。

## 4. リレーショナルDBの基礎

### 4.1 テーブル、行、列

顧客テーブルを表で考えると、列はデータの項目、行は顧客1人分です。

```text
customers
┌────┬────────┬──────────────┐
│ id │ name   │ phone        │
├────┼────────┼──────────────┤
│  1 │ 山田花 │ 090-...      │
│  2 │ 田中葵 │ 080-...      │
└────┴────────┴──────────────┘
```

### 4.2 主キーと外部キー

主キー（Primary Key）は、行を一意に識別する値です。外部キー（Foreign Key）は、別テーブルの行を参照します。

```text
customers                   reservations
┌────┬──────┐               ┌────┬─────────────┐
│ id │ name │◀──────────────│ id │ customer_id │
└────┴──────┘               └────┴─────────────┘
```

外部キーがあることで、存在しない顧客IDを予約に保存することをDB側でも防げます。

### 4.3 制約

制約は、DBに不正な状態を保存させないための最後の防波堤です。

| 制約 | 防げるもの |
| --- | --- |
| `PRIMARY KEY` | IDの重複、未設定 |
| `FOREIGN KEY` | 存在しない関連先 |
| `NOT NULL` | 必須値の欠落 |
| `UNIQUE` | 一意であるべき値の重複 |
| `CHECK` | 人数が0以下など、行単体の不正 |
| `EXCLUDE` | PostgreSQLで時間範囲の競合など |

アプリ側の検証は、分かりやすいエラーを早く返すために必要です。DB制約は、アプリのバグや同時実行があっても不正データを拒否するために必要です。どちらか片方だけではありません。

### 4.4 インデックス

インデックスは、本の索引のように検索を速くする構造です。ただし、追加するほど書き込み時の更新コストと保存容量が増えます。

候補になるのは、よく検索・結合・並び替えに使う列です。

- 外部キー
- 顧客名
- 電話番号
- 予約開始日時
- ステータス

「将来使うかもしれない」だけで全列へ追加せず、実際の問い合わせを基準にします。

### 4.5 1対多と多対多

顧客1人が複数予約を持つ関係は1対多です。

```text
customer 1 ───── * reservation
```

1予約が複数の席を使い、1席も日時の異なる複数予約に使われる関係は多対多です。中間テーブルを使います。

```text
reservation 1 ─── * reservation_tables * ─── 1 table
```

中間テーブルには最低限、両側の外部キーがあります。同じ席を同じ予約へ2回指定できないよう、2列の組に一意制約または複合主キーを置けます。

### 4.6 正規化と重複データ

正規化は、同じ意味のデータを複数箇所に持たず、更新時の矛盾を減らす考え方です。

たとえば予約行へ顧客の現在の電話番号を毎回コピーすると、顧客情報を変更した際に過去の予約と値が食い違います。一方、「予約時点の連絡先を証拠として残す」という要件なら、スナップショットとしてコピーする意味があります。

重複がすべて悪いのではなく、意味を説明できるかが大切です。

### 確認問題

1. 同じ電話番号の顧客を登録可能にする場合、電話番号に`UNIQUE`を付けるべきでしょうか。
2. 中間テーブルの2列に一意制約がないと、何が起こりますか。
3. 席の定員が1以上というルールは、アプリとDBのどちらで守れますか。

## 5. SQLAlchemy 2.xの全体像

### 5.1 SQLAlchemyとpsycopgの役割

```text
Pythonコード
  ↓ SQLAlchemy（SQLの組み立て、ORM、Session）
psycopg（PostgreSQLとの通信）
  ↓ ネットワーク
PostgreSQL
```

SQLAlchemyはDB操作を抽象化します。psycopgはPostgreSQLの通信規約を扱うドライバーです。

### 5.2 Engineとは

Engineは、DB接続方法と接続プールをまとめる、アプリ全体の入口です。

```text
Engine
├─ Dialect: PostgreSQLのSQLの違いを扱う
├─ Driver: psycopgを使う
└─ Pool: 再利用できる接続を管理する
```

`create_engine()`を呼んだ時点で、必ず即座にDBへ通信するとは限りません。初めて接続が必要になった時点で実接続する設計です。そのため、「Engineを作れた」だけでは接続成功のテストにならない点に注意します。

### 5.3 Connection Poolとは

DB接続を毎回ゼロから作ると費用がかかります。接続プールは、使い終わった接続を保持し、次のリクエストで再利用します。

ただし、接続プール内のConnectionと、後述するSessionは同じものではありません。

### 5.4 Sessionとは

Sessionは、1回の業務処理で行うORM操作とトランザクションを管理する作業単位です。

```text
HTTPリクエストA ─ Session A ─┐
HTTPリクエストB ─ Session B ─┼─ Engine ─ PostgreSQL
HTTPリクエストC ─ Session C ─┘
```

Sessionを全リクエストで共有してはいけません。複数の処理の途中状態やトランザクションが混ざるからです。

基本原則は次のとおりです。

> Engineはアプリ全体で再利用し、Sessionはリクエストごとに作って閉じる。

### 5.5 `sessionmaker`とは

`sessionmaker`はSessionそのものではなく、同じ設定のSessionを作る工場です。

別題材の例です。

```python
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker

engine = create_engine(warehouse_database_url)

WarehouseSessionFactory = sessionmaker(
    bind=engine,
    autoflush=False,
    expire_on_commit=False,
)
```

- `bind=engine`: どのDBへ接続するSessionか
- `autoflush=False`: 問い合わせ前の自動flushを抑え、学習中は実行時点を明示しやすくする
- `expire_on_commit=False`: commit後に属性を再取得待ち状態へしない

これらのオプションは絶対の正解ではありません。プロジェクト方針として選びます。

### 5.6 SessionをFastAPIへ渡す

FastAPIの依存性注入と`yield`を使うと、処理の前にSessionを作り、処理後に必ず閉じられます。

別題材の疑似コードです。

```python
def get_warehouse_session():
    session = WarehouseSessionFactory()
    try:
        yield session
    finally:
        session.close()
```

流れは次のとおりです。

```text
リクエスト開始
  ↓ Sessionを作る
ルート関数へ渡す
  ↓ 成功または例外
finallyでSessionを閉じる
```

`yield`より後ろは後片付けです。例外が起きても`finally`は実行されます。

### 5.7 同期版と非同期版

このプロジェクトでは、まず同期版SQLAlchemyを使う方針が分かりやすいです。

| 方式 | 長所 | 注意点 |
| --- | --- | --- |
| 同期 | コードとデバッグが単純、教材が多い | ブロッキング処理を`async def`へ直接混ぜない |
| 非同期 | 待ち時間の多い高並行処理で選択肢になる | Engine、Session、ドライバー、テストが複雑になる |

FastAPIでは、同期DB処理を使うルートを通常の`def`で書けば、FastAPIがスレッドプールで扱えます。MVPで「非同期のほうが速そう」という理由だけで複雑さを増やす必要はありません。

### 5.8 DB接続テスト

Engineを作るだけでなく、実際に簡単なSQLを実行します。

疑似コードは次のとおりです。

```text
Sessionを1つ作る
  ↓
SELECT 1を実行する
  ↓
結果が1であることを確認する
  ↓
必ずSessionを閉じる
```

接続テストが失敗した場合は、次の層を順に確認します。

1. Docker Desktopが起動しているか
2. PostgreSQLコンテナがHealthyか
3. ホストとポートが合っているか
4. DB名とユーザー名が合っているか
5. パスワードが合っているか
6. SQLAlchemyのdrivernameが`postgresql+psycopg`か

### 現在の店舗予約APIへの応用課題

実装前に次の図を、自分の変数名で書いてください。

```text
Settings → URL → Engine → sessionmaker → Session → SELECT 1
```

それぞれについて「アプリ全体で1個」か「処理ごとに作る」かも書き添えてください。

## 6. ORMモデルとPydanticスキーマは別物

名前が似ていて混同しやすい部分です。

| 種類 | 主な役割 | 例 |
| --- | --- | --- |
| SQLAlchemyモデル | DBテーブルとの対応 | `Customer`テーブル |
| Pydantic入力スキーマ | API入力の検証 | `CustomerCreate` |
| Pydantic出力スキーマ | APIで返す形の制御 | `CustomerResponse` |

### 6.1 分ける理由

DBにある全列を、API利用者へ見せたり変更させたりしてよいとは限りません。

たとえばスタッフテーブルに次があるとします。

- `id`
- `name`
- `password_hash`
- `role`
- `created_at`

ログインAPIの入力では平文パスワードを受け取りますが、DBに保存するのはハッシュです。レスポンスへ`password_hash`を含めてはいけません。

```text
API入力                 DB                    API出力
password ──ハッシュ化→ password_hash ──×──→ 返さない
```

### 6.2 作成用と更新用を分ける

- 作成用: 必須項目を要求する
- 更新用: 変更可能な項目を任意にする
- 出力用: IDや作成日時を含める

同じスキーマを使い回しすぎると、更新してはいけないフィールドまで受け付ける危険があります。

### 確認問題

1. 予約作成者IDは、リクエストボディから受け取るべきでしょうか。
2. スタッフ権限を一般のスタッフ更新スキーマへ含めると、どんな問題がありますか。
3. `password`と`password_hash`を同じスキーマへ置かない理由を説明してください。

## 7. トランザクション

### 7.1 トランザクションとは

複数のDB操作を、一つのまとまりとして成功または失敗させる仕組みです。

予約作成では、たとえば次を同じまとまりにします。

1. 予約を作る
2. 予約と席を紐づける
3. 操作履歴を作る

途中で3だけ失敗したのに1と2が残ると、「履歴のない予約」ができます。トランザクションなら全部を戻せます。

```text
BEGIN
  予約をINSERT
  席割当をINSERT
  監査ログをINSERT
COMMIT
```

途中で失敗した場合です。

```text
BEGIN
  予約をINSERT
  席割当で失敗
ROLLBACK  ← 最初のINSERTも取り消す
```

### 7.2 ACID

| 性質 | 意味 |
| --- | --- |
| Atomicity（原子性） | 全部成功か全部失敗 |
| Consistency（一貫性） | 制約を満たす状態から、満たす状態へ移る |
| Isolation（分離性） | 同時処理の途中状態が不適切に干渉しない |
| Durability（永続性） | commitした結果が障害後も保持される |

### 7.3 `flush`、`commit`、`rollback`、`close`

| 操作 | 意味 |
| --- | --- |
| `flush` | 変更SQLをDBへ送るが、まだ確定しない |
| `commit` | トランザクションを確定する |
| `rollback` | 未確定の変更を取り消す |
| `close` | Sessionが使った資源を解放する |

`flush`すると、自動採番されたIDをcommit前に得られます。そのIDを使って監査ログを作り、最後にまとめてcommitできます。

### 7.4 commitをどこで行うか

学習用MVPでは、業務処理全体を把握するサービス層でcommitする方針が分かりやすいです。

```text
APIルート
  ↓ 予約作成を依頼
Service
  ├─ Repositoryで顧客を確認
  ├─ Repositoryで席を確認
  ├─ Repositoryで予約を追加
  ├─ Repositoryで監査ログを追加
  └─ 全体をcommit
```

Repositoryが操作のたびにcommitすると、途中失敗時に全部を戻せなくなります。

### 7.5 基本の疑似コード

```text
try:
    必要なデータを読む
    業務ルールを検証する
    予約を追加する
    flushして予約IDを得る
    席割当を追加する
    監査ログを追加する
    commitする
except:
    rollbackする
    エラーを上位へ伝える
```

一行ごとの意味を説明できるようになってから実装します。

## 8. Alembicとマイグレーション

### 8.1 マイグレーションとは

マイグレーションは、DB構造をどの順番で変更したかを残す履歴です。

```text
revision 001: customersを作る
revision 002: customersへemailを追加
revision 003: reservationsを作る
```

SQLAlchemyモデルは「現在こうあるべき」という設計図です。Alembicのrevisionは「現在のDBをどう変更するか」という手順書です。

### 8.2 `create_all()`だけでは足りない理由

`create_all()`は存在しないテーブルを作る学習には便利ですが、既存列の変更履歴や本番DBへの安全な変更を管理しにくいです。

このプロジェクトでは、DB構造の変更をAlembicへ残します。

### 8.3 基本の流れ

```text
SQLAlchemyモデルを変更
  ↓
alembic revision --autogenerate
  ↓
生成されたupgrade/downgradeを人が確認
  ↓
alembic upgrade head
  ↓
DBの実際の構造を確認
```

自動生成は候補を作る機能です。完全な正解を保証しません。特に列名変更は「旧列を削除して新列を追加」と解釈され、データを失う可能性があります。

### 8.4 `upgrade`と`downgrade`

- `upgrade`: 新しい構造へ進める処理
- `downgrade`: 一つ前の構造へ戻す処理

downできることが常に安全とは限りません。列削除で失ったデータは自動では戻りません。

### 8.5 確認するポイント

- テーブル名と列名は意図どおりか
- `nullable`は意図どおりか
- 外部キーと削除時の動作は意図どおりか
- `unique`、`check`、indexがあるか
- upgradeで既存データを壊さないか
- downgradeの意味は妥当か

## 9. FastAPIのルートと依存性注入

### 9.1 ルート関数の責務

ルート関数はHTTPの入口です。次の役割に絞ると読みやすくなります。

- パス、クエリ、ボディを受け取る
- ログイン中のスタッフやSessionを依存性から受け取る
- サービスを呼ぶ
- HTTPレスポンスへ変換する

複雑な空席計算やトランザクションをルートへ詰め込まないようにします。

### 9.2 依存性注入とは

関数が必要とするものを自分で作らず、外から渡してもらう仕組みです。

```text
FastAPI
├─ DB Sessionを用意
├─ トークンから現在のスタッフを用意
└─ ルート関数の引数へ渡す
```

DB Session、認証、権限確認など、複数ルートで共通する準備に向いています。

### 9.3 `Depends`で括弧を付けない意味

概念例です。

```python
Depends(get_warehouse_session)
```

`get_warehouse_session()`とその場で呼ぶのではなく、関数そのものをFastAPIへ渡します。FastAPIがリクエスト時に適切な順番で呼びます。

### 9.4 シンプルなディレクトリ構成

最初から細分化しすぎず、責務が増えたら分けます。

```text
app/
  main.py          # FastAPIアプリの入口
  config.py        # 環境設定
  database.py      # EngineとSession
  models.py        # 小規模な間はORMモデルをまとめる
  schemas.py       # 小規模な間はPydanticスキーマをまとめる
  api/             # ルートが増えたら分割
  services/        # 業務処理が増えたら分割
tests/
alembic/
docs/
```

モデルが増えて読みにくくなった時点で`models/`ディレクトリへ分ければ十分です。最初から「将来必要そう」という理由だけでrepositoryやinterfaceを大量に作りません。

## 10. CRUDと業務ルール

CRUDは次の4操作です。

- Create: 作成
- Read: 取得
- Update: 更新
- Delete: 削除

しかし、実際のAPIは単純なCRUDだけではありません。

### 10.1 顧客作成の流れ

```text
入力を検証
  ↓
必要なら重複候補を検索
  ↓
顧客を作る
  ↓
commit
  ↓
作成結果を返す
```

同じ電話番号を別顧客として登録可能にする場合、重複をエラーにはしません。ただし、誤登録に気づけるよう「同じ電話番号の候補あり」と画面側へ知らせる設計は将来検討できます。

### 10.2 PATCHの考え方

PATCHでは、「値が送られていない」と「`null`が送られた」を区別する必要があります。

- 未送信: 既存値を変更しない
- `null`: 任意項目を空にする意思かもしれない

Pydanticの更新スキーマから、実際に指定されたフィールドだけ取り出して更新します。

### 10.3 予約は単純なCRUDではない

予約作成には複数の検証があります。

```text
基本入力
├─ 終了 > 開始
├─ 人数 >= 1
└─ 10分単位

参照データ
├─ 顧客が存在
├─ 席が存在
└─ 席が有効

店舗ルール
├─ 営業時間内
├─ 臨時休業日ではない
└─ 合計定員 >= 人数

競合
└─ 同じ席・重複時間の有効予約がない
```

このため、ルートから直接`INSERT`するだけではなく、サービスで処理の順序を表現します。

## 11. 認証と認可

### 11.1 違い

- 認証（Authentication）: あなたは誰かを確認する
- 認可（Authorization）: あなたがその操作をしてよいか確認する

```text
ログイン成功 → 認証済み
店員が営業時間変更を要求 → 認証済みだが認可されない
```

### 11.2 パスワード保存

パスワードは平文保存も復号可能な暗号化保存もしません。専用のパスワードハッシュ関数で、ソルトを含む一方向の値にします。

```text
入力パスワード
  ↓ password hash
復元できないハッシュ値 → DBへ保存
```

ログイン時は、入力パスワードを保存済みハッシュと検証します。単純なSHA-256を直接使うのではなく、Argon2やbcryptなど、パスワード用途の遅いアルゴリズムをライブラリ経由で使います。

### 11.3 JWTアクセストークン

アクセストークンは、ログイン後のAPI呼び出しで「認証済みであること」を示す短期間の証明書のようなものです。

JWTは概念上、次の3部分を持ちます。

```text
header.payload.signature
```

- header: 署名方式など
- payload: スタッフID、期限などのclaim
- signature: 内容が改ざんされていないことを検証する署名

payloadは暗号化されているとは限りません。パスワードや不要な個人情報を入れてはいけません。

### 11.4 ログインからユーザー特定まで

```text
1. IDとパスワードを受け取る
2. DBからスタッフを探す
3. パスワードハッシュを検証する
4. スタッフIDと有効期限を含むJWTへ署名する
5. アクセストークンを返す

以後のリクエスト:
6. Authorizationヘッダーからトークンを得る
7. 署名と期限を検証する
8. payloadのスタッフIDでDBを検索する
9. 現在も有効なスタッフか確認する
10. ルートへ現在のスタッフを渡す
```

トークン内のroleだけを永久に信用すると、DBで権限を変更しても古いトークンの権限が期限まで残る場合があります。MVPでは、現在のスタッフをDBから取得し、現在のroleで認可する流れが理解しやすく安全です。

### 11.5 ロールと個別権限

MVPは次の3ロールで開始します。

- 店員
- 副店長
- 店長

個別権限を最初から自由に組み合わせる方式は柔軟ですが、テーブル、管理画面、競合ルール、テストが増えます。「締切後キャンセルを一部店員へ付与」は具体的な必要が出た段階で追加するのが妥当です。

そのときは次の選択肢があります。

| 方式 | 長所 | 短所 |
| --- | --- | --- |
| スタッフにbooleanを1列追加 | 単純 | 権限が増えるたび列が増える |
| permissionsと中間テーブル | 柔軟 | 認可処理と管理が複雑 |
| 役職を追加 | 理解しやすい場合がある | 実際の組織役職と権限が混ざる |

### 11.6 キャンセル権限の考え方

現在の方針をルールへ分解します。

```text
予約がすでにキャンセル済み → 全員不可
来店済み → キャンセル不可
副店長または店長 → 締切後や予約開始後でもキャンセル可
店員 → 店舗設定の「開始X分前」以前ならキャンセル可
将来の個別権限あり店員 → 締切後も可
```

「X時間」よりDBでは「キャンセル締切分数」として整数で持つと、90分前などにも対応できます。

来店しなかった予約を副店長・店長がキャンセル扱いにすることも、MVPでは可能とします。ただし、キャンセルと無断不来店を将来別集計したくなった場合は、`no_show`を独立状態にするほうが意味を保てます。どちらの操作でも、操作者と変更前後を監査ログへ残します。

## 12. 店舗予約ドメインの設計

### 12.1 MVPの中心テーブル候補

| テーブル | 責務 |
| --- | --- |
| `stores` | 店舗と店舗単位の設定 |
| `staff` | ログインするスタッフと役割 |
| `customers` | 顧客情報 |
| `tables` | 席名、定員、有効状態 |
| `reservations` | 顧客、時間、人数、状態など |
| `reservation_tables` | 予約と席の多対多 |
| `business_hours` | 曜日ごとの複数営業時間区間 |
| `closed_dates` | 営業日単位の臨時休業 |
| `audit_logs` | 操作履歴 |

単店舗MVPでも`store_id`を関連データへ持たせると、後の複数店舗化で全テーブルを作り直す危険を減らせます。ただし、店舗切り替えAPIや複雑なテナント管理まではMVPへ含めません。

### 12.2 予約の状態

最低限は次の状態です。

- `reserved`: 予約中
- `visited`: 来店済み
- `cancelled`: キャンセル

「来なかった」はキャンセル理由とは意味が異なるため、必要性が明らかになったら`no_show`を独立状態として追加する余地があります。

状態変更は自由な文字列更新ではなく、遷移として考えます。

```text
reserved ──→ visited
    │
    └──────→ cancelled
```

来店済みやキャンセル済みから予約中へ戻す操作は、誤操作修正の要件と権限を決めるまで許可しないほうが安全です。

### 12.3 顧客変更を許可する場面

予約に紐づく顧客の変更は、たとえば次の場面で必要です。

- 電話を受けた担当者が、同姓の別顧客を誤って選んだ
- 幹事が変わり、連絡先を新しい代表者へ変更した
- 仮登録した顧客から、既存の正式な顧客レコードへ付け替えたい

変更を許可するなら、変更前後の`customer_id`を監査ログへ残します。

### 12.4 日時の保存

予約日時はタイムゾーンを含む日時として扱う方針が安全です。

- API入力: タイムゾーン付きISO 8601を基本にする
- DB: PostgreSQLの`timestamp with time zone`相当
- 店舗の業務判定: 店舗タイムゾーンへ変換して曜日・営業日を判定

単店舗で日本だけでも、「何のタイムゾーンか」を曖昧にしない習慣が将来の事故を減らします。

## 13. 営業時間、営業日、10分単位

### 13.1 複数営業時間区間

昼営業と夜営業を表すには、1曜日に複数行を持てる設計にします。

```text
月曜日 11:30 - 15:00
月曜日 17:00 - 23:00
```

1曜日1行に昼・夜の列を増やす設計は、3区間目が必要になったとき列追加が必要です。1区間1行なら行を追加できます。

### 13.2 日付をまたぐ営業時間

```text
金曜日 18:00 - 翌02:00
```

終了時刻が開始時刻より小さい場合に「翌日」と解釈する方法と、`closes_next_day`のような明示的な列を持つ方法があります。

| 方式 | 長所 | 短所 |
| --- | --- | --- |
| 時刻の大小で推測 | 列が少ない | 同時刻を24時間営業とするか休みとするか曖昧 |
| 翌日フラグ | 意味が明確 | 入力項目と検証が1つ増える |

初心者向けMVPでは、曖昧さを減らす明示的な方法が理解しやすいです。

### 13.3 営業日単位の臨時休業

深夜営業では、暦日と営業日が異なることがあります。

```text
金曜営業: 金曜18:00 ～ 土曜02:00
```

この全体を「金曜日の営業」と考えるなら、金曜日を臨時休業にしたとき土曜00:00～02:00も休業です。

予約日時から、どの営業時間区間に属するかを先に探し、その区間の営業日を求めてから`closed_dates`を確認します。

### 13.4 営業時間内の判定

予約の開始だけが営業時間内でも、終了が閉店後なら不正です。

```text
営業時間区間の開始 <= 予約開始
かつ
予約終了 <= 営業時間区間の終了
```

予約全体が同じ一つの営業時間区間へ収まることを確認します。昼と夜の間の休憩をまたぐ予約は許可しません。

### 13.5 10分単位の判定

最低限、開始と終了の分が10の倍数で、秒・マイクロ秒が0であることを確認します。

```text
minute % 10 == 0
second == 0
microsecond == 0
```

API側で丸めて保存すると、利用者が指定した時刻と異なる予約が黙って作られます。原則はエラーを返し、正しい入力を求めます。

### 確認問題

1. 23:00～翌01:00の予約は、どの日付の臨時休業を確認しますか。
2. 14:50～17:10が昼営業と夜営業をまたぐ場合、許可すべきでしょうか。
3. 18:00:30を自動で18:00へ丸めると、どんな問題がありますか。

## 14. 空席検索と席の組み合わせ

### 14.1 空席検索の入力

- 日付または開始日時
- 終了日時
- 人数

「日付、開始時刻、終了時刻」を別々に受ける案もありますが、サービス内部ではタイムゾーン付きの開始日時と終了日時へ組み立てて扱います。

### 14.2 処理の段階

```text
1. 日時と人数を検証する
2. 営業時間内か確認する
3. 臨時休業でないか確認する
4. 有効な席を取得する
5. 時間が重なる予約で使われている席を除く
6. 残った席から、定員を満たす組み合わせを探す
7. 少なくとも1組を返す
```

### 14.3 席の組み合わせ

例として空席が次の3席だとします。

```text
A: 2人
B: 4人
C: 6人
希望: 5人
```

候補は`A+B`、`A+C`、`B+C`、`C`などです。すべて返すと数が増えるため、まず1組を選ぶ順位を決めます。

現在の候補ルールです。

1. 使用する席数が少ない
2. 余る定員が少ない
3. それでも同じなら、席名などで安定した順序にする

この例では、席数1の`C`が先です。

### 14.4 組み合わせ探索の疑似コード

```text
空席を安定した順に並べる

使用席数 = 1 から空席数まで繰り返す:
    その席数で作れる組み合わせを調べる
    合計定員が人数以上の候補だけ残す
    候補があれば余り定員が最小のものを返す

候補がなければ空席なし
```

これは小規模店舗なら理解しやすい方法です。席数が非常に多いと組み合わせ数が急増するため、上限や席グループなど別の工夫が必要になります。MVPで先に複雑な最適化はしません。

### 14.5 検索結果と予約確定は別

空席検索の直後に、別の人が同じ席を予約する可能性があります。

```text
空席検索時: 空いていた
      ↓ 別リクエストが予約
予約確定時: もう空いていない
```

したがって、予約作成時にも必ず再検証します。空席検索結果は保証ではなく候補です。

## 15. 時間重複とダブルブッキング

このシステムで特に重要な応用章です。3段階に分けて学びます。

### 15.1 第1段階: 単純な重複チェック

半開区間`[start, end)`として扱うと、既存予約が18:00に終わり、新規予約が18:00に始まる場合は重複しません。

重複条件は次のとおりです。

```text
既存の開始 < 新規の終了
かつ
既存の終了 > 新規の開始
```

時間軸で見ると理解しやすくなります。

```text
既存:      |----------|
新規:           |----------|  重複する

既存:      |----------|
新規:                 |----|  境界が同じだけなので重複しない
```

キャンセル済み予約を問い合わせから除外します。

疑似コードです。

```text
selected_table_idsのどれかを使う予約を探す
かつ status != cancelled
かつ existing.start < new.end
かつ existing.end > new.start

1件でもあれば409 Conflict
なければ予約を作る
```

まずはこの実装と通常のテストで、重複条件そのものを理解します。

### 15.2 第2段階: SELECTだけでは防げないことを確認

同時に2リクエストが来ると、次の競合が起こります。

```text
リクエストA                リクエストB
重複SELECT → なし
                           重複SELECT → なし
INSERT
                           INSERT
COMMIT
                           COMMIT
```

どちらのSELECT時点にも、相手の未確定予約は見えません。両方が成功し、ダブルブッキングになります。これは「確認してから更新する」処理に起こるレースコンディションです。

### 15.3 第3段階: 同時リクエスト対策の比較

#### 方法A: 席の行をロックしてから再確認

選択された`tables`行を`SELECT ... FOR UPDATE`でロックし、そのトランザクション内で重複を再確認します。

```text
BEGIN
  対象の席をID順にFOR UPDATE
  重複予約をSELECT
  なければ予約と席割当をINSERT
  監査ログをINSERT
COMMIT
```

同じ席を使う別リクエストは、先のトランザクションが終了するまで待ちます。待った後に重複を再確認するため、後から来た側は競合を発見できます。

長所:

- 正規化した予約・中間テーブル構造を保ちやすい
- 「ロック対象の資源＝席」が明確
- 学習時に処理を追いやすい

注意点:

- すべての予約作成・日時変更・席変更が同じロック規則を守る必要がある
- 複数席をロックするときはID順など一定順序にし、デッドロックを減らす
- トランザクションを開いたまま外部API呼び出しなどをしない

存在する「予約行」だけをロックする方法では、まだ予約が1件もない席を守れません。そこで常に存在する席の行をロックします。

#### 方法B: PostgreSQLの排他制約

PostgreSQLのrange型と`EXCLUDE USING gist`を使うと、同じ資源について時間範囲が重なる行をDB自身に拒否させられます。

概念例です。

```text
同じequipment_id（=）
かつ
貸出期間が重なる（&&）
組み合わせを禁止する
```

長所:

- アプリを経由しない書き込みにも強い
- 同時実行時もDBが最終的に拒否する

注意点:

- 予約時間は`reservations`、席IDは中間テーブルにあるため、そのままでは1行の制約にできない
- 制約用の割当テーブルへ席ID・時間範囲・有効状態を持たせる設計もあるが、予約変更やキャンセル時の同期が必要
- キャンセル済みを除外するpartial constraintの条件設計が必要
- Alembicの自動生成だけに頼らず、マイグレーションを手で確認する

DB制約は強力ですが、モデル設計への影響を理解してから導入します。

#### 方法C: SERIALIZABLE分離レベル

並行処理を、直列に実行した場合と同等に見せる強い分離レベルです。競合時は一方がserialization failureになり、トランザクション全体を最初から再試行する必要があります。

長所:

- 複雑な整合性ルールをDBが検出できる場合がある

注意点:

- 失敗は異常ではなく通常の競合として起こり得る
- 安全なリトライ設計が必要
- 負荷と競合率を考える必要がある

#### 方法D: PostgreSQL Advisory Lock

アプリが決めたキーに対して、トランザクション単位の論理ロックを取る方法です。

長所:

- ロック専用行がなくても資源単位に調整できる

注意点:

- ロックキーの作り方と取得順序を正しく設計する必要がある
- DB制約のように自動で守られるわけではなく、全コード経路が規則を守る必要がある
- 初学者には行ロックより意図が見えにくい

### 15.4 MVPでの学習順

1. アプリ側の単純SELECT重複チェックを実装する
2. 通常の重複テストを通す
3. 2接続を使った同時実行テストで破れることを確認する
4. 選択席の行ロックとトランザクション内再確認を追加する
5. 同時実行テストで片方だけ成功することを確認する
6. 発展課題として排他制約案と比較する

これなら、最初から高度なコードを貼り付けず、「なぜ対策が必要か」を実際の失敗から学べます。

### 15.5 日時変更にも同じ対策が必要

予約作成だけ守っても、日時変更や席変更で重複を作れたら意味がありません。

変更前の席と変更後の席を一定順序でロックし、自分自身の予約を重複検索から除外して再確認します。

### 確認問題

1. 予約行がないとき、既存予約への`FOR UPDATE`だけではなぜ守れませんか。
2. 2席を使う予約同士が逆順でロックすると、何が起きる可能性がありますか。
3. 空席検索時にロックし続ける設計が現実的でない理由を考えてください。
4. 排他制約を中間テーブルへ単純に置けない理由を説明してください。

## 16. 操作履歴（監査ログ）

### 16.1 監査ログの目的

アプリの通常ログは、エラー調査や動作確認に使います。監査ログは「誰が、何を、どう変えたか」を業務上追跡するデータです。

最低限の項目です。

- 操作者ID
- 操作種別
- 対象種別
- 対象ID
- 操作日時
- 変更前
- 変更後

### 16.2 JSONBで変更前後を保存する

PostgreSQLの`jsonb`へスナップショットを保存する方法は、対象ごとに列構造が違っても一つの監査テーブルで扱えます。

```json
{
  "status": "reserved",
  "customer_id": 12,
  "start_at": "2030-04-01T18:00:00+09:00"
}
```

長所:

- 予約、顧客、営業時間など異なる対象を保存できる
- 変更当時の状態を残しやすい
- 後から項目が増えても監査テーブルの列追加が不要な場合が多い

短所:

- 型や外部キーをJSON内部へ強く適用しにくい
- 特定項目の横断検索は通常列より複雑
- 個人情報や秘密情報を丸ごと保存する危険がある

### 16.3 差分だけか、全体スナップショットか

| 方式 | 長所 | 短所 |
| --- | --- | --- |
| 変更項目だけ | 容量が小さい | その時点の全体像を復元しにくい |
| 変更前後の全体 | 読みやすく証跡が明確 | 容量が増え、機密情報混入に注意 |

MVPでは、監査対象として安全な項目を選び、変更前後のスナップショットを保存する方法が理解しやすいです。パスワードハッシュ、アクセストークン、DB秘密情報は絶対に含めません。

### 16.4 同じトランザクションへ入れる

業務データの変更と監査ログは、同じトランザクションで保存します。

```text
予約変更成功 + 監査ログ失敗 = 全体をrollback
```

別々にcommitすると、変更はあるのに履歴がない状態が生まれます。

### 16.5 監査ログ自体の変更

通常のスタッフ向けAPIから、監査ログを更新・削除できないようにします。DB管理者まで含む完全な改ざん防止は別の高度な運用課題ですが、少なくともアプリの通常操作からは追記専用にします。

## 17. バリデーションを層で分ける

すべての検証をPydanticへ押し込まず、必要な情報に応じて分けます。

### 17.1 API入力だけで判断できるもの

- 人数が1以上
- 終了日時が開始日時より後
- 席IDに重複がない
- 10分単位
- メールアドレスの形式

Pydanticスキーマが担当しやすい範囲です。

### 17.2 DBを読まないと判断できないもの

- 顧客が存在する
- 席が存在する
- 席が有効
- 合計定員が人数以上
- 営業時間内
- 臨時休業日ではない
- 他予約と時間が重複しない

サービス層がSessionを使って確認します。

### 17.3 DB制約でも守るもの

- 外部キー
- 必須列
- 人数や定員のCHECK
- 中間テーブルの組み合わせ重複
- 同時実行に強い競合制約を採用する場合の排他制約

### 17.4 検証順序

安価で分かりやすい検証から行うと、無駄なDB問い合わせを減らし、利用者へ適切なエラーを返せます。

```text
入力形式
  ↓
単項目・項目間ルール
  ↓
参照先の存在
  ↓
店舗ルール
  ↓
競合チェック
  ↓
保存
```

ただし同時実行対策では、ロックを取った後に競合を再確認する必要があります。「一度確認したから十分」ではありません。

## 18. pytestによるテスト

### 18.1 テストの基本形

```text
Arrange: 前提データを用意
Act:     操作する
Assert:  結果を確認
```

別題材の例です。

```python
def test_item_name_is_returned(client):
    # Arrange
    payload = {"name": "会議用マイク", "capacity": 1}

    # Act
    response = client.post("/items", json=payload)

    # Assert
    assert response.status_code == 201
    assert response.json()["name"] == "会議用マイク"
```

### 18.2 正常系と異常系

正常に登録できるテストだけでは、制約が守られるか分かりません。

- 正常な顧客を登録できる
- 必須値なしは失敗する
- 存在しない顧客の予約は失敗する
- 定員不足は失敗する
- 権限なしは失敗する
- 失敗時にDBへ途中データが残らない

### 18.3 単体テストと結合テスト

| 種類 | 確認するもの | 特徴 |
| --- | --- | --- |
| 単体テスト | 小さな関数や業務計算 | 速い、原因を絞りやすい |
| 結合テスト | API、DB、トランザクション | 現実に近い、準備が多い |

10分単位や席組み合わせの純粋関数は単体テストに向いています。外部キー、行ロック、排他制約は実際のPostgreSQLを使う結合テストが必要です。SQLiteだけではPostgreSQL固有の挙動を確認できません。

### 18.4 fixture

fixtureは、テストで繰り返す準備や後片付けを共有する仕組みです。

- テスト用DB Session
- TestClient
- 店舗データ
- スタッフデータ
- 顧客と席
- 認証ヘッダー

fixtureが大きくなりすぎると、テストの前提が見えにくくなります。各テストに必要な最小の前提を選びます。

### 18.5 テストの独立性

テストは実行順序に依存させません。

```text
悪い例:
test_1で顧客を作り、test_2がその顧客を前提にする

良い例:
各テストが必要な顧客を自分のfixtureで用意する
```

### 18.6 同時実行テスト

二重予約対策のテストには、別々のDB接続と、ほぼ同時に競合箇所へ到達させる同期点が必要です。

概念的な流れです。

```text
スレッドA ─ Session A ─┐
                       ├─ 同じ席・同じ時間を予約
スレッドB ─ Session B ─┘

期待結果:
片方だけ成功
もう片方は409または競合例外
DB内の有効予約は1件
```

同じSessionを2スレッドで共有してはいけません。テストが偶然順番に動いただけでは競合を再現できないため、barrierなどで開始点を合わせます。

### 18.7 テスト実行コマンド

```powershell
# 全テスト
.\.venv\Scripts\python.exe -m pytest

# 詳細表示
.\.venv\Scripts\python.exe -m pytest -v

# 1ファイル
.\.venv\Scripts\python.exe -m pytest tests\test_health.py -v

# 名前で絞る
.\.venv\Scripts\python.exe -m pytest -k overlap -v
```

## 19. エラーの読み方とデバッグ

### 19.1 エラーを直す前に分類する

| 層 | 例 |
| --- | --- |
| Python | `SyntaxError`、`NameError` |
| import | パッケージ未導入、モジュールパス違い |
| 設定 | 必須環境変数なし、型変換失敗 |
| 接続 | DB停止、認証失敗、ポート違い |
| SQL/ORM | 列名違い、外部キー違反 |
| 業務 | 定員不足、営業時間外 |
| HTTP | 期待と異なるステータスやJSON |

分類せずにコードを変えると、別の問題を増やしやすくなります。

### 19.2 tracebackは下から読む

Pythonのtracebackは、最後の行に例外の種類と概要があり、その上に自分のコードの呼び出し位置があります。

1. 一番下の例外名とメッセージを読む
2. 下から上へ、自分のプロジェクト内ファイルを探す
3. その行へ届いた値を確認する
4. 原因の仮説を一つ立てる
5. 最小の確認を行う

秘密値は表示しません。DB設定なら、値そのものではなく「変数が存在するか」「ポートが整数か」などを確認します。

### 19.3 接続問題の切り分け

```powershell
# コンテナ状態
docker compose ps

# PostgreSQLのログ
docker compose logs db

# Python側の依存関係
.\.venv\Scripts\python.exe -m pip check

# テスト
.\.venv\Scripts\python.exe -m pytest -v
```

確認は「Docker → PostgreSQL → Pythonドライバー → SQLAlchemy → アプリ」の順で、下の層から積み上げます。

## 20. Docker Composeの役割

### 20.1 イメージ、コンテナ、ボリューム

| 用語 | 意味 |
| --- | --- |
| イメージ | コンテナを作るための読み取り専用テンプレート |
| コンテナ | イメージから起動した実行環境 |
| ボリューム | コンテナを作り直しても残すデータ領域 |

PostgreSQLコンテナを削除しても、名前付きボリュームを削除しなければDBデータを残せます。

### 20.2 よく使うコマンド

```powershell
# 起動
docker compose up -d

# 状態
docker compose ps

# ログ
docker compose logs db

# 停止してコンテナを削除（ボリュームは残る）
docker compose down
```

`docker compose down -v`はボリュームも削除し、DBデータを消します。学習データを消してよいと確認できた場合だけ使います。

### 20.3 ヘルスチェック

コンテナが「起動中」でも、PostgreSQLが接続受付可能とは限りません。ヘルスチェックは、サービスが実際に利用可能かを確認します。

ただし、DBがHealthyでもアプリ側のユーザー名やパスワードが間違っていれば接続は失敗します。

## 21. Gitと秘密情報

### 21.1 小さくコミットする

学習段階ごとにコミットすると、何を学んだ変更か追いやすくなります。

```text
chore: add database dependencies
feat: add application settings
feat: add database session
test: verify database connection
```

1コミットへ環境設定、顧客CRUD、認証を全部入れないようにします。

### 21.2 commit前の確認

```powershell
git status
git diff
git diff --staged
```

確認するものです。

- `.env`が含まれていないか
- パスワードや秘密鍵がコードにないか
- デバッグ用printが残っていないか
- 関係ないファイルを変更していないか
- テストが成功するか

### 21.3 一度公開した秘密情報

秘密情報をGitへcommitした場合、後のcommitで削除するだけでは履歴に残ります。秘密値を無効化・変更し、必要なら履歴から除去する対応が必要です。

## 24. 用語集

| 用語 | 短い意味 |
| --- | --- |
| API | プログラム同士が決めた形式でやり取りする窓口 |
| Endpoint | メソッドとパスで特定されるAPIの入口 |
| JSON | APIでよく使うデータ表現 |
| Schema | データの形や制約を表す設計 |
| ORM | PythonオブジェクトとDBテーブルを対応させる仕組み |
| Driver | 特定のDBと通信するライブラリ |
| Engine | SQLAlchemyのDB接続設定と接続プールの中心 |
| Session | 一つの作業単位でORM操作とトランザクションを管理するもの |
| Transaction | 複数DB操作を全部成功または全部失敗にするまとまり |
| Migration | DB構造変更の履歴と適用手順 |
| Validation | 入力や状態がルールを満たすか確認すること |
| Authentication | 誰であるかを確認すること |
| Authorization | その操作を許可されているか確認すること |
| JWT | 署名付きclaimを運ぶトークン形式 |
| Hash | 元に戻すことを前提としない一方向変換 |
| Foreign Key | 別テーブルの行への参照を守る制約 |
| Index | 検索を速くする補助構造 |
| Race Condition | 実行順によって結果が変わる同時実行の問題 |
| Lock | 他処理との同時変更を調整する仕組み |
| Audit Log | 誰が何をどう変えたかを残す業務上の履歴 |
