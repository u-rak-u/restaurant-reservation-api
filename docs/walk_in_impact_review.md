# 予約なし利用追加による要件影響の再確認

## 1. 目的

予約なし利用をMVPへ追加したことで、完了済みとしていた要件のうち再検討が必要になった範囲と、その決定結果を記録する。
予約なし利用に関するW-01からW-09をDB設計前に確定し、後続設計が参照できる判断根拠として残す。

## 2. 現在の状態

**完了**

次の基本方針は確定済みとする。

- 予約なし利用を予約とは別の業務データとして管理する。
- 顧客の氏名、電話番号、予約番号、確認コード、QRコードを持たせない。
- スタッフが来店時に登録し、将来の予約なし利用を事前登録しない。
- 予約と同じ物理テーブル、配置場所、連結可能関係を使用する。
- 利用中の席を予約の自動再配置によって動かさない。
- 待ち行列、注文、会計、顧客プロフィールをMVPに含めない。

次の項目はウォークイン追加前には存在しなかった判断であり、W-01からW-09までの再検討を完了して確定状態としている。

## 3. 再検討する項目

### W-01 利用開始条件と営業時間

**確定**

- 各営業時間帯に開店、最終入店、ラストオーダー、閉店を設定する。
- 予約なし利用は、受付日時が最終入店日時以前で、予定終了日時が同じ連続営業時間帯の閉店日時以前の場合だけ受け付けられる。
- 最終入店日時ちょうどの受付と、閉店日時ちょうどの利用終了を許可する。5名以上は最終入店以前に受付を完了していれば、準備後の予定利用開始が最終入店を過ぎてもよい。
- 日付をまたぐ場合は、実日時を変更せず営業時間の開始日に属する営業日として扱う。
- 定休日と臨時休業では受け付けられず、特別営業時間では同時間帯に明示した最終入店とラストオーダーを使用する。
- 貸切中は対象範囲の席候補が競合するため受け付けられない。貸切自体には最終入店とラストオーダーによる受付制限を適用しない。
- ラストオーダーは案内と受付判定の前提となる設定だけを管理し、注文内容と実際の注文時刻はMVPで扱わない。

### W-02 予定利用時間

**確定**

- 初期値90分、最小60分、最大180分、10分単位とする。
- 予定利用時間は予定利用開始・終了日時の差から求め、分数列へ重複保存しない。
- 予定利用時間は利用開始前にだけ選択し、開始後の延長と短縮をMVPに含めない。
- 90分未満では終了予定時刻を顧客へ案内し、受付を確定した登録スタッフと受付日時を案内確認の主体・日時として記録する。
- 早期退店は予定終了を変更せず、利用終了操作によって処理する。
- 予定終了10分前を終了間近、予定終了後を時間超過として表示する。
- 時間超過しても自動終了せず、実際の利用終了まで席を占有中として新しい利用へ割り当てない。
- 後続予約がある場合は強い警告を表示し、退席案内または席移動は現場で対応する。

### W-03 人数変更と13名以上

**確定**

- `preparing` または `active` の現在人数は1名以上12名以下で変更できる。全員が利用をやめる場合は0名へ変更せず、`preparing` では理由付き受付中止、`active` では利用終了として扱う。
- 減員しても席を解放せず、増員は現在の割り当て定員内に限り通常スタッフが人数だけを変更できる。
- `preparing` 中に5名未満へ減っても、状態、予定利用開始日時、適用済み転換時間を変更しない。
- 割り当て定員を超える追加参加者は、別の予約なし利用として空席を探索する。
- 13名以上はスタッフが各1名以上12名以下へ分割して入力し、全員分を収容できる場合だけ同じトランザクションで全件を作成する。
- 分割した各件を恒久的に関連付けず、変更と利用終了は個別に行い、近接席も保証しない。
- スタッフは離れた席になる可能性を案内し、自動配置を使う限り合計人数だけを理由とする責任者承認を要求しない。

### W-04 席配置と転換時間

**確定**

- 1名から4名は受付と同時に `active`、5名以上は受付と同時に `preparing` とし、準備中から席を確保する。受付確定を準備開始として扱い、別の準備開始操作または準備開始日時は設けない。
- 5名以上の予定利用開始日時は受付日時から店舗設定の大人数転換時間が経過した日時とし、予定終了日時はそこから予定利用時間を加えて求める。
- 適用した利用前・利用後転換時間と席の占有期間は席配置世代へ保存し、予約なし利用本体へ重複保存しない。1名から4名は両方0分、5名以上は受付時点の店舗設定値とし、設定変更、人数変更または席移動でも自動変更しない。
- 準備が遅れても予定終了日時を自動延長せず、予定利用開始日時を過ぎた `preparing` を警告表示する。
- 5名以上は利用終了後も、実際の終了日時から大人数転換時間が経過するまで席を確保し、経過後に清掃完了操作なしで自動的に解放する。
- 早期終了時は終了後転換時間を実際の終了日時から計算し直すが、既存予約の席配置は組み直さない。
- 時間超過後の実終了によって後続予約との占有重複が生じても、実終了を拒否せず現実の競合として保存する。強い警告を表示し、重なりが解消するまで追加の新規割り当てを拒否する。
- `preparing`、`active`、利用終了後転換時間中の席は、新規受付による自動再配置の対象にしない。

### W-05 操作権限

**確定**

- 通常スタッフは、自動選択された席で受付を確定し、必要な準備後の利用開始と利用終了を行える。
- `preparing` の受付中止は通常スタッフが行えるが、理由を必須とし、履歴を削除せず `aborted` にする。
- 当日運用責任者以上は、受付時に競合しない別候補を選択できる。
- 当日運用責任者以上は、安全上または顧客対応上の理由を記録し、競合を再検証して `active` な予約なし利用を別の席へ移動できる。
- 利用終了を通常操作で取り消さず、誤終了は例外案件として提起する。営業中に占有を継続する場合は、元の記録を戻さず新しい予約なし利用を作る。

### W-06 営業設定、貸切、臨時休業との関係

**確定**

- 貸切は対象範囲と予約停止時間が `preparing`、`active`、利用終了後転換時間中の席と重なる場合に拒否し、管理責任者以上でも競合を上書きしない。
- 通常営業時間または特別営業時間の変更で、既存予約または `preparing`、`active` の予約なし利用が営業時間外になる場合は変更を拒否する。
- 受付済みの予約なし利用へ変更後の最終入店時刻だけを遡って適用せず、終了後転換時間は営業時間外へ延びてもよい。
- 臨時休業は `preparing` または `active` が存在しても登録でき、対象営業日の新しい予約、貸切、予約なし利用を停止する。
- 臨時休業によって既存の予約なし利用を自動終了・自動中止せず、個別の例外案件も自動作成しない。未終了の店内利用がある間は強い警告を表示する。
- `preparing` は理由付き受付中止、`active` は実際の退店時の利用終了によって現場で処理し、終了後転換時間中は対応対象にしない。
- 貸切、営業時間変更、臨時休業、予約なし利用受付は店舗ロック後に関連データを再取得して競合を判定する。

### W-07 状態訂正と例外案件

**確定**

- 例外案件は共通集約とし、`arrival_issue`、`walk_in_record_correction`、`no_show_review`、`temporary_closure_response` の4種類に分ける。
- 審査状態は `open`、`proposed`、`approved`、`rejected`、`resolved` とする。履歴訂正は当日運用責任者の提起後に管理責任者以上が承認または却下する。
- 臨時休業との矛盾解消や後からの通常来店確認など、解消条件をシステムが検証できる場合だけ、承認なしの `resolved` を許可する。
- 予約の来店記録と予約なし利用の訂正は、同じ審査基盤を使うが、資格情報、正常操作、訂正結果が異なるため別の案件種別とする。
- `preparing` または `active` の人数訂正と、当日運用責任者以上による理由付き席移動は通常操作とし、通常状態遷移で直せない過去記録だけを訂正案件にする。
- `completed` または `aborted` を通常操作で元へ戻さない。誤終了後も利用が続く場合は、当日運用責任者以上が元の利用と関連付けた新しい `active` の予約なし利用を作成する。
- 新しい利用は元の現在人数、予定終了日時、適用済み転換時間を引き継ぎ、新しい標準利用時間を与えない。
- 同じ席が競合しない場合だけ、元の席解放または終了後転換時間を新しい席配置計画へ引き継ぐ。既に別の利用へ確定した席は上書きせず、実際に移動できる別候補がなければ継続登録を拒否する。
- 訂正を承認しても元の利用、終了操作、席配置履歴を削除せず、訂正済みの関係を追記し、集計では新旧記録を1つの連続利用として扱えるようにする。

### W-08 保持期間と監査

**確定**

- 予約なし利用本体、人数、利用日時、席配置、開始・変更・終了・訂正の監査履歴を、確定終了から3年保持する。
- 訂正で複数の予約なし利用と例外案件が関連する場合は、すべての利用と案件が終了した最も遅い日時を起算点とし、関連記録を同じ削除単位として扱う。
- `preparing`、`active`、`open`、`proposed`、削除保留中の記録は削除しない。
- 期限後は個別記録を削除し、営業月、曜日、時間帯、人数帯ごとの件数、人数、平均利用時間、席稼働、時間超過、訂正件数など、個別利用を復元できない集計だけを保持できる。
- 元の利用ID、正確な来退店時刻、個別席、操作スタッフ、理由、自由記述、例外案件ID、再結合用ハッシュを統計へ残さない。
- 日次削除ジョブは関連記録の完全な終了を再検証し、統計を冪等に保存してから、関連する利用、席配置、監査履歴、例外案件を途中で分断せず処理する。

### W-09 スタッフ画面とMVP境界

**確定**

- 予約と予約なし利用は同じ「今日の営業」時系列一覧へ表示し、種類、色、表示名を分けたうえで全件、予約のみ、予約なし利用のみへ絞り込めるようにする。
- `preparing` は準備中、予定開始超過は準備遅延、`active` は利用中、予定終了10分前から終了間近、予定終了超過は時間超過として表示する。
- `completed` 後に転換時間が残っている利用は転換中として再利用可能日時を表示する。準備遅延、終了間近、時間超過、転換中は基本状態へ追加しない派生表示とする。
- 受付画面では人数、予定利用時間、短時間利用の案内確認、13名以上の分割人数を入力し、自動席、開始・終了予定、準備時間、自動再配置の有無、席が離れる可能性を確認してから確定する。
- 画面上の候補は仮押さえにせず、確定時にAPIが再計算する。通常スタッフは自動候補だけを使い、当日運用責任者以上だけが別候補を選択できる。
- 通常スタッフには利用開始、理由付き受付中止、定員内人数変更、利用終了を提供し、当日運用責任者以上には理由付き席移動、例外提起、占有継続登録を提供する。
- 満席、営業時間、最終入店、閉店、貸切、臨時休業、同時更新を区別して受付不可理由を表示し、同時更新だけ再試行を案内する。
- 待ち行列、将来の空席保証、利用時間の延長・短縮、平面座標を使ったフロアマップはMVPに含めない。
- 画面で権限外操作を隠しても、API側の認証、認可、状態遷移、競合検証を省略しない。

## 4. 再検討しない既決事項

次の要件は予約なし利用を追加しても意味が変わらないため、確定状態を維持する。

- 顧客アカウントをMVPで作らない方針
- 予約番号、予約確認コード、QRコードの用途と安全性
- 通常予約のオンライン取消と電話受付
- SMS、メール、電話対応管理をMVP後へ回す方針
- 通常予約の受付開始、受付締切、変更・キャンセル締切
- 通常予約と貸切予約を共通の予約集約で扱う方針
- 貸切の資格情報の受け渡しと再発行方法
- 無断キャンセル履歴を使った利用制限のMVP範囲

## 5. 完了後の次作業

1. 要件からエンティティ、値オブジェクト、状態遷移、集約境界を最終整理する。
2. テーブル、制約、削除方針を設計する。
3. 予約、予約なし利用、席配置、営業時間、権限、例外、監査、保持期限の関係をER図へまとめる。

## 6. 実用性評価

予約なし利用を席計算へ含めること自体は、実店舗の空席とシステム上の空席を一致させるために有効である。
ただし、上記を決めずに実装すると、終了超過で予約客の席がなくなる、通常スタッフが誤操作を復旧できない、貸切と利用中席が競合するなどの運用上の欠陥が残る。

DB設計と本格実装の前に再検討を完了したため、予約モデル、席配置制約、API権限を実装後に作り直す危険を抑えられる。
一方、統合された当日一覧は混雑時間帯に情報量が増えるため、40席の試作データを使って絞り込み、警告の優先順位、操作ミスの起きにくさを確認する必要がある。
